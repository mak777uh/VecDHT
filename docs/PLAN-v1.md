# План реализации v1 и пилота выплат (для исполнителя кода)

Дата: 2026-10-25. Основание: панель критики из 7 ролей (114 замечаний R-01…R-114, реестр вне репо),
закрытие `E-0114` (`supports`, `bab9e51`), `docs/STATUS-v1.md`, `ROADMAP.md`, решения владельца ниже.
Этот файл — очередь работ. Он не заменяет `AGENTS.md`: прочитай его первым и соблюдай 11 правил.

## 0. Решения владельца (не пересматривать без него)

1. **v1 = сеть VecDHT (горизонт H1).** Команда «запусти узел», сценарий на двух машинах, производитель
   отзыва, тег. Выплаты — v1.1 (пилот H2), вторая дорожка, не блокирует тег v1.
2. **Исполнитель назван заранее.** Открытой гонки нет ⇒ нет submission bond, commit-reveal, выбора
   победителя (`OPEN-V9-5` остаётся отложенным). Залог ставится после выбора исполнителя: `term_hash`
   содержит ключ бенефициара.
3. **Цепь пилота — EVM: anvil (локально) → Sepolia. Инструмент — Foundry.** Контракт держит залог сам,
   пересчитывает `term_hash` через прекомпиль sha256, платит ровно один раз, делает refund после окна.
   Ed25519-квитанцию проверяет офлайн-мост (Rust `check_payout_claim`), контракту вердикт подтверждает
   **secp256k1-аттестатор**. Это доверие, и в спеке оно обязано быть названо словом «доверие».
   Ed25519 в Solidity, ZK, оптимистическая схема, Bitcoin, Solana/TON/NEAR — после пилота.
4. **Первый образ верификатора — `lean_proof`.** Собирается в CI (Docker на ubuntu-раннере GitHub),
   digest пинится. Локально Docker нет — образ локально не собирать.

## 1. Правила исполнения (коротко)

- Каждая карточка = гипотеза `H-XXXX` + эксперимент `E-XXXX` с порогом **до** прогона (`lab/templates/`),
  `python lab/cycle-gate.py gate H-XXXX` до замера, лог в `lab/logs/`, коммит с `Experiment: E-XXXX`.
- Проверка: `cargo test --workspace` и `cargo clippy --workspace --all-targets -- -D warnings`;
  полная — `bash lab/workspace-verify.sh E-XXXX`.
- Windows: каждая команда начинается с `export PATH=/c/Users/Admin/mingw64/bin:$PATH` (иначе линковка
  падает на `GetHostNameW`). Docker, forge, anvil локально **не установлены** — Foundry-карточки
  исполняются в CI или после установки Foundry (объявить владельцу).
- Перед циклом и после: `bash lab/disk-report.sh` (диск, RAM, pagefile). `cargo clean` — только
  объявив владельцу. Свободно ~31 000 МБ; порог ≥ 15 000 МБ.
- Файлы писать с LF (`.gitattributes`); проверять `grep -c $'\r' <файл>` = 0.
- Спеку менять отдельным коммитом после замера; v8-спека имеет зеркало (`lab/check-spec-mirror.sh`).
- `lab/check-text-clean.sh <файлы>` до коммита (ловит смешение алфавитов).

**Инварианты, которые нельзя двигать ни одной карточкой** (их сдвиг = провал карточки):

- A: байты записи заказа — 217 байт V01, якорь `order_ref` V01 = `4167d021a099e6efcbce24212117757136eb0823e3dd5d756ed3a2caf6f2ac70`;
  новые поля в запись заказа **не добавлять** (R-06, R-29 отброшены именно поэтому).
- B: формула `term_hash` (измерена `E-0114`, 31/31) не меняется.
- C: старый `registry_root` остаётся валиден; новый описатель цепи = новый корень, перепин отдельным циклом.
- D: закрытый список кодов — 18 (`ErrorCode::all()`), новых кодов не вводить.
- E: fail closed — `DEFAULT_TRUSTED_CHAINS = []`, неизвестная цепь → `E_ESCROW_UNKNOWN`.
- Lean: формулировка всегда «доказано для модели, соответствие модели и кода не проверено», пока нет
  названного исполняемого прибора соответствия.

## 2. Порядок работ

```

Т1 (ledger)  ─────────┼─> дорожка A: A0 → A1 (+A2) → A3 → A1c → A4 → A6 → A5 → A7 (тег v1)
                      └─> дорожка B: B1 → B2 ─┬─> B3 → B4 → B5 → B6 → B7
```

## 4. Дорожка A — v1 (H1)

Справочник по коду: CLI — `crates/vecdht-cli/src/` (команды в таблице `COMMANDS` в `lib.rs`, исполнение
через `(cmd.run)(&p, &mut out)`; `agent run` = `agent_cmd.rs::exec_run`/`serve`). Шард-узел собирается
так, как в тесте `crates/vecdht-net/tests/s182_p1_scale.rs::build`: `ShardNode::open(dir, shard, id,
peer, params, authority_set, holders)` → genesis-кадр членства → `NetService::new(id, Role::IndexNode,
Some(cert), vec![node], authorities, cfg)`. В продукте сейчас **нет** вызова ни `publish_revoke`
(`vecdht-net/src/service.rs`), ни `revoked_dir` (в `agent.rs` стоит `None`), ни `with_centroids`
(`vecdht-node/src/node.rs`).

### A1. Подкоманда `node run` (шард-узел)

Цель: оператор поднимает индексный узел одной командой. Флаги: `--dir` (каталог узла), `--seed` или
`--key` (идентичность; ключ не в git), `--shard`, `--listen`, `--bootstrap`, `--cert` (файл NodeCert),
`--authorities` (файл), `--genesis` (файл кадра членства), `--artifact` (каталог с `centroid.bin`).
Обязательно: `NetConfig.revoked_dir = Some(<dir>)` (закрывает OQ п. 46 (в)); `denylist.bin` в том же
каталоге. Порог: интеграционный тест в `crates/vecdht-cli/tests/`: узел из CLI + агент `publish`→`find`
по QUIC на 127.0.0.1 находит запись; рестарт узла с тем же `--dir` сохраняет отзыв и бан.
Запрет: тестовые ключи `testing::*` в продуктовый путь не тащить — только из файлов.

**Сделано:** `E-0119` (`supports`, 2026-10-26) — `node run` собирает узел из `--cert`/`--genesis`,
проверяет их до открытия порта, печатает `NODE_READY`/`NODE_STATUS` в stdout, а `--dir` отдан и
индексу, и `denylist.bin`, и `revocation.bin`. Отличия от текста карточки: набор авторитетов берётся
из `--artifact` (как у `revoke`), отдельного `--authorities` нет; центроидов у узла по-прежнему нет —
это A2.
Хвосты карточки переданы: «рестарт сохраняет отзыв» закрыт `E-0120` (A3), «бан» ждёт производителя
бана (`OPEN-QUESTIONS` п. 65, хвост 2), «подпись кадра genesis проверяется лишь на наличие» —
`OPEN-QUESTIONS` п. 64, хвост 2.

### A2. Загрузка `centroid.bin` (H-0109, OQ п. 53.2)

**Сделано:** `E-0121` (`supports`, 2026-10-26) — `node_cmd.rs` вызывает `with_centroids` после
genesis, `NODE_STATUS` печатает `cluster_reassigned`/`cluster_unverified`; оракул
`crates/vecdht-cli/tests/node_centroids.rs` (два теста: артефакт без `centroid.bin` — код 2 с именем
файла и без каталога узла; два живых `node run` + настоящий `Agent`, честная публикация
`cluster_reassigned=0`, подделка `cluster_id` пересчитана и находится по честному кластеру,

узла и клиента и `artifact remap` — отдельные вопросы.

### A3. Производитель отзыва `revoke` (H-0110, OQ п. 45/46)

Подкоманда `revoke --cert <nonce|файл> --authority-keys <файлы> --to <multiaddr>`: собирает `CertRevoke`
с пороговой подписью авторитетов (§15) и рассылает через `publish_revoke`. Порог (из ROADMAP H1):
живой узел отказывает отозванному ключу **без рестарта**, и после рестарта тоже; ключи авторитета только
из файлов вне репо. Отдельно `H-0096`: ошибка записи `revocation.bin` (каталог только на чтение) —
порог «дверь отказывает, а не пропускает»; если код пропускает — `refutes`, решение владельцу.

**Сделано:** `E-0120` (`supports`, 2026-10-26) — команда `revoke` в `revoke_cmd.rs`, оракул
`crates/vecdht-cli/tests/revoke_publish.rs` (два живых процесса `node run` на QUIC). Измерено: отзыв,
собранный CLI и разосланный по control-теме эфемерным агентом, применяется живым узлом без рестарта
(`revocations` 0→1, `revocation.bin` на диске, причина отказа `cert is revoked by nonce`), дверь
перестаёт принимать тот же кредашиал, а после рестарта из того же `--dir` без bootstrap отказ
повторяется; недонабранный порог и ключ вне набора — код 2 и файла нет. Отличия от текста карточки:
вместо `--cert <nonce|файл>` — `--cert FILE` / `--nonce HEX32` (одно значение — один флаг); вместо
`--authority-keys` — общие с `cert`/`genesis` `--key-file`/`--dev-keys` (один язык для одного порога);
набор авторитетов — из `--artifact`, а не отдельным файлом (удостоверять обязан тот же набор, что
подписал кредашиалы). Хвосты: подпись кадра отзыва не проверяется, ошибка записи `revocation.bin`
(`H-0096`) измерена карточкой `E-0136`, вердикт `refutes` (носитель `lab/logs/e0136-all.log`: отказ записи откатывает nonce из памяти, файла состояния нет, сервис продолжает обслуживать; дыра остаётся в очереди, политика — за владельцем, `OPEN-QUESTIONS` п. 73), отзыв адресует nonce, а не владельца — `OPEN-QUESTIONS` п. 65.

### A1c. Lease после рестарта (OQ п. 42) — закрыто (`E-0124`, `ADR-0065`, вердикт `supports`)

Проблема: `open_with_admission` поднимает с диска цепочку членства, но `lease` остаётся `None`;
`serving_epoch()` → `None`, и `handle_publish` отбивает кадр на проверке эпизоды, не доходя до
`check_publish`. Ответ `EPOCH_STALE` на всё неотличим от узла, который ещё не дозвался гранта.

Цель: после рестарта с тем же `--dir` узел либо возвращает право обслуживать эпизоду из
**подписанных** грантов, либо наблюдаемо говорит «не primary, жду грант» (код + строка журнала);
третьего поведения («молча отказ на всё») быть не должно. Порог: тест в `crates/vecdht-cli/tests/`
— узел из `node run` получает грант, `publish` проходит; рестарт с тем же `--dir` без bootstrap:
`publish` либо проходит, либо отказ называет состояние и не выдаёт себя за отсутствие права; в
числе — PRE_FIX на дереве `E-0120`, где перезапуск обязан воспроизвести `EPOCH_STALE`. Контракт
хранения гранта — отдельным ADR, если форма не совпадёт с уже подписанным кадром членства.

Сделано (`E-0124`, `ADR-0065`): `lease.bin` — ровно подписанный кадр `LeaseGrant`, который primary
рассылает по проводу; при открытии он проходит `Lease::verify` против принятой эпохи и сверяется с
`membership.primary`, любой отказ оставляет `lease = None`. Приборы — `crates/vecdht-node/tests/lease_after_restart.rs`
(возобновление primary, три посадки, реплика без гранта) и `crates/vecdht-cli/tests/node_lease_status.rs`
(два настоящих процесса `node run`, публикация до и после рестарта с тем же `--dir`); PRE_FIX на
`d8d3087` красный по пяти узловым фактам, после правки оба прибора зелёные дважды (`STABLE=1`,
36 ожиданий, 0 расхождений). Контракт `restart_recovery.rs` переписан осознанно как ветка «рестарт
без гранта» (файл удаляется в тесте, комментарий называет ADR). Порог карточки отдельно фиксирует,
чего правка не делает: окно `lease_buckets` (90 с), а не бессрочное право, и хвост расхождения
цепочек («у меня грант эпохи E, у мира E+1») — в `OPEN-QUESTIONS` п. 42.

### B1. Недостающие векторы носителя (R-59 и др.)

В `docs/PAID_PAYOUT-VECTORS.md` (генератор — `crates/vecdht-orders/tests/payout_claim_vectors.rs`,
команда с `V9P_VECTORS_OUT=<temp>`; в `docs/` писать только после сверки) добавить векторы:
квитанция другого заказа / другой подачи → `E_RECEIPT_INVALID`; связка называет другой образ;
свидетельство про другой `term_hash`; цепь свидетельства ≠ цепь заказа; `E_UNSUPPORTED_ASSET`;
подача от чужого ключа B' → `E_HASH_MISMATCH` (R-03); подмена `escrow_ref` в требовании →
`E_HASH_MISMATCH` (R-01); `deadline+3600` проходит, `+3601` → `E_DEADLINE_PASSED`; изменён только
`note` дескриптора → решение то же (R-43); граничные подписи Ed25519 (неканоничный S, малый порядок)
через Rust и через Python-мост (R-37, у нас `verify`, не `verify_strict`).
Порог: Python-мост `lab/v9-payout-bridge.py` совпадает с Rust на **всех** векторах; 12 старых `E_REPLAY`
зелёные; якорь V01 неизменен. Расхождение Rust/Python на граничной подписи — не чинить молча, записать
и выбрать строгий профиль отдельным ADR.

### B2. Образ `lean_proof` в CI (OPEN-V9-3/4/6, R-103)

Два прогона на двух раннерах дают один digest и одинаковые квитанции (`stdout_sha256`) на 3 заказах.

### B3. Контракт эскроу на Foundry (OPEN-V9-8, R-02/17/18/19/20/23/36/77/109)

Каталог `contracts/escrow/` (Foundry). Интерфейс: `lock(termHash, recipient, deadline)` payable/ERC-20,
`release(...)`, `refund(termHash)`, события `Locked/Released/Refunded`, `view state(termHash)`.
Правила:
- один залог на `term_hash` (повторный `lock` — revert) (R-01 остаток, R-20);
- `term_hash` пересчитывается в контракте из байт заказа через прекомпиль sha256 (тот же порядок полей,
  что `vecdht_orders::term_hash`); вектор V01 из носителя обязан дать тот же хеш в Solidity;
- `release` требует подпись secp256k1-аттестатора над (`term_hash`, `recipient`, `chain_id`, адрес контракта);
- адрес получателя покрыт проверяемой контрактом подписью (R-23/R-41) — подмена `recipient` → revert;
- `escrow_ref` для EVM = адрес контракта (20) ‖ id залога (32) = 52 байта; поле в заказе уже непрозрачное,
  байты заказа не меняются (R-18);
- время = `block.timestamp`; `release` только до `deadline+3600`, `refund` только после
  `deadline+3600+запас` — окна не пересекаются (R-02, R-19, R-36);
- `Released` и `Refunded` взаимоисключающие и финальные; reentrancy-guard.
Тесты (forge): недостаточный залог, неверный `term_hash`, повторный `release`, `refund→release`,
`release→refund`, чужой контракт/цепь, подмена получателя, граница `+3600/+3601`, два параллельных
`release` → ровно одна выплата. Шаг (5) моста с witness и без (чтение состояния контракта) даёт одно
решение (R-17). Порог: все тесты зелёные в CI-job `contracts`.

### B7. Сквозной сценарий anvil → Sepolia (R-96/97)

Скрипт: заказ → залог → подача → квитанция образа B2 → аттестатор → `release` → событие. Сначала anvil
в CI. Sepolia — только с явного разрешения владельца, тестовые средства, ключи только у владельца,

журнал связывает `submission_ref` с событием цепи. Цепь вносится в доверенный корень только после этого
прибора (R-48).

### Ловушки дорожки B (найдены разведкой кода, учесть до B1)

1. **Шаг (5) в Rust и в мосте расходится.** Мост проверяет `settle_asset_tag` описателя против актива
   заказа (→ `E_UNSUPPORTED_ASSET`), Rust смотрит только `trust.chains` и вызывает `check_escrow` с
   активом заказа — в Rust эта ветка недостижима. Вектор на неё даст `MIRROR_MISS`. Сначала решить
   (ADR), кто прав, и выровнять Rust, затем добавлять вектор. Байты не меняются, меняется решение.
2. **`min_amount` описателя не проверяет никто** (ни Rust, ни мост). Решить в том же ADR: проверять или
   убрать из смысла поля.
3. **Новые векторы ломают зашитые числа:** генератор (`replays == 12`, `payouts ≥ 7`), мост
   (`KEYPAIR_*_EQ` = len−1, ровно один keypair 7 и 9, `DOMAIN_ROWS=5`, `LAYOUT_OBJECTS=4`,
   `STEP_ROWS=7`), посадчик (`V9CTL_MIRROR_MATCH x/N`). Мост делает `escrow_ref.decode("utf-8")` —
   не-UTF-8 даёт выход 2; генератор зовёт `canonical_json().unwrap()` — не-ASCII в `toolchain` уронит его.
4. **`lab/expectations/e0114.tsv` и `lab/e0114-run.sh` не править** — цикл закрыт. B1 = новый цикл
   (`H-0115` зарезервирован, `OPEN-QUESTIONS` п. 60) со своим TSV и helper'ом.
5. **Подпись квитанции:** Rust подписывает пересобранный JSON, мост проверяет полученные байты
   (совпадение — отдельный факт `V9C_RECEIPT_JSON_EQ`). Не «упрощать» к одному виду без вектора.
6. **Версия Lean:** квитанции в векторах пишут `toolchain = leanprover/lean4:v4.9.1`, а CI-модели
   используют `v4.36.0-rc1`. В B2 выбрать версию образа явно и записать; `image_digest` в векторах —
   заглушка `0x2a…`, настоящий digest появится только после B2.
7. **Записка `DESIGN-2026-10-25-chain-binding.md` расходится с кодом** (лист реестра без `0x00`, код
   шага 5, нет шага (0)). Нормативны код и `docs/PAID_PAYOUT-VECTORS.md`; в К0 переносить текст из
   носителя, а не из записки.
8. В EVM (B3) `u64`/`u128` в `term_hash` — little-endian: в Solidity байты переставлять вручную; проверка —
   вектор V01 даёт тот же `term_hash`.
9. `verify.yml` пишет «orders 16» тестов, фактически 24 — поправить комментарий в Т1.
