# AGENTS.md — контракт для агентов

Этот репозиторий — протокол и научный стенд одновременно. Спека фиксирует контракт, тесты
играют роль оракулов, `lab/` хранит память между агентами. Человек читает README; агент обязан
прочитать ещё и этот файл, `lab/README.md` и §19 спеки, прежде чем менять код.

## Порядок чтения

1. `README.md` — что уже стоит и какие границы честные.
2. `docs/VecDHT-SPEC-v8.md` — конституция: контракты, числа, §19 (как проверять), §20 (что не делать).
3. `lab/README.md` — протокол гипотез, экспериментов и решений.
4. `lab/lean-rubric.md` — когда формальная модель обязательна, а когда была бы декорацией.
5. `lab/hypotheses/`, `lab/experiments/`, `lab/decisions/` — что уже проверено и почему.
6. Только потом — код и ветка.

## Одиннадцать правил

1. **Истина — в коде, тестах и воспроизводимом прогоне.** README, lab-записи и отчёты — карты,
   а не источник чисел. Число без команды, окружения и коммита — не результат.
2. **Один вопрос — одно изменение.** Архитектурная правка начинается с гипотезы
   (`lab/hypotheses/H-XXXX-*.md`) и pre-registration в эксперименте (`lab/experiments/E-XXXX-*.md`)
   до прогона. Порог нельзя придумывать после того, как увидел результат.
3. **Гейт не ослабляется.** Нельзя менять порог, `#[ignore]`-сценарий или проверку так, чтобы
   «стало зелёным». Новый гейт или смена порога — отдельный ADR с обоснованием; старые результаты
   сохраняются рядом.
4. **Отрицательный результат — тоже результат.** Опровергнутая гипотеза остаётся в `lab/` с
   вердиктом `refutes` (статус гипотезы — `refuted`; словарь объявлен в `lab/README.md`, шаг 4).
   Записи append-only: исправление — новая секция, а не переписанная история.
5. **Спека — конституция.** Меняешь контракт — сначала ADR, затем спека
   `docs/VecDHT-SPEC-v8.md` и её зеркало `C:\Users\Admin\OneDrive\Desktop\VecDHT-SPEC-v8.md`,
   `diff -q` должен быть чистым в том же коммите. Проверка — `./lab/check-spec-mirror.sh`
   (`--fix` обновляет зеркало из оригинала): зеркало вне git, поэтому его расхождение не видно
   ни в `git status`, ни в CI.
6. **Один писатель на область.** Ветка = единица работы (`exp/E-XXXX-…`, `adr/ADR-XXXX-…`,
   `fix/…`). Не редактируй чужие lab-записи и не переиспользуй чужие артефакты. Пересечение по
   `vecdht-wire`/`vecdht-crypto`/`vecdht-index` — повод сначала договориться, а не «поправить по пути».
7. **`main` всегда зелёный.** Прямой push — только по явному поручению владельца репозитория;
   по умолчанию — ветка и PR по шаблону `.github/pull_request_template.md`. Чужую ветку не
   переписывай force-push'ем.
8. **Не выдумывай механизмы.** Если в v1 нет penalty table, сигнала расхождения владельцев или
   verifiable re-computation — так и пиши в границах. «Почти работает» и «должно работать» не
   считаются проверкой.
9. **Секреты, ключи и веса — не в git.** В репозиторий едут код, спецификация, манифесты и
   lab-записи; большие артефакты — вне, со ссылкой и хэшем.
10. **Сомневаешься — пиши гипотезу, а не код.** Дешёвая проверка на бумаге лучше дорогой правки,
    которую потом придётся откатывать.
11. **Круг, а не догадка: боль → источники → рубрика Lean → оракул.** Прежде чем
    пре-регистрировать `H-XXXX`, обязан быть исполнен такой порядок: (а) сформулировать боль
    одной фразой — какую дыру в v1 закрываем; (б) поискать, как её решали другие:
    `python lab/sources.py hunt "<боль>" --github --paths <файлы>` — статьи идут в класс
    «бумага», чужой репозиторий в «реализация» с пином на sha, и `python lab/library.py add`
    не примет строку с пустым `gives`, то есть прочитанное надо сформулировать; (в) ответить на
    четыре вопроса `lab/lean-rubric.md` и записать ответ в шапку карточки полем `lean:` — четыре
    «да» делают модель Lean обязательной до пре-регистрации; (г) только потом писать оракул.
    Механическая проверка — `python lab/cycle-gate.py H-XXXX` (выход 0; сам гейт проверяется
    командой `python lab/cycle-gate.py selftest`). Карточка без принятого решения по Lean —
    не карточка, а источник без строки в индексе — не источник.

## Что считается проверкой

```
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
```

Тяжёлые гейты запускаются отдельно и записываются в эксперимент с точной командой:

```
cargo test --release -p vecdht-node --test adversarial -- --ignored --nocapture
```

На Windows сборка требует mingw-w64 в `PATH` (см. README, раздел «Сборка»). Если гейт не
запускался в этом окружении — это не «пройден», а «не проверялся здесь».

Приборы лаборатории проверяются так же, как код, и стоят в `lab/workspace-verify.sh`:

```
bash lab/lean-check.sh                 # все модели lab/lean/: компилируются, sorry=0
python lab/cycle-gate.py selftest      # гейт круга отбивает посаженные нарушения
python lab/library.py check            # схема индекса источников (класс, пин, путь, бюджет)
python lab/library.py verify           # ссылка существует и принадлежит тому, что заявлено
python lab/library.py digest           # классы источников + § спеки без литературной сверки
```

## Куда писать результат

- гипотеза: `lab/hypotheses/H-XXXX-<slug>.md` (шаблон — `lab/templates/hypothesis.md`);
- прогон: `lab/experiments/E-XXXX-<slug>.md` (шаблон — `lab/templates/experiment.md`);
- архитектурное решение: `lab/decisions/ADR-XXXX-<slug>.md` (шаблон — `lab/templates/adr.md`).

В коммите указывай `Experiment: E-XXXX` и/или `ADR: ADR-XXXX`, чтобы историю можно было связать с
доказательством. Подробности жизненного цикла — `lab/README.md`.
