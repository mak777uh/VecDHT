# VecDHT

P2P-семантический поиск и rendezvous агентов: узел публикует интент (embeddings + короткий
текст), другой узел находит его по смыслу, без обязательного центра. Чистый Rust, ядро протокола
реализовано один раз — языковые привязки вызывают его, а не переписывают байтовые форматы.

Спецификация: [docs/VecDHT-SPEC-v8.md](docs/VecDHT-SPEC-v8.md). Она же — источник чисел и
контрактов в коде; там же приложение «что удалено из v7.5 и почему».

## Статус

v8 пишется по этапам P0–P7 из §18 спеки. В `main` только то, что собирается и тестируется:
байтовый слой протокола (`vecdht-wire`), слой детерминизма (`vecdht-crypto`), подписанный артефакт
сети (`vecdht-artifact`), одноузловой индекс шарда (`vecdht-index`), машина шарда (`vecdht-node`),
транспорт на настоящем libp2p (`vecdht-net`), контракт инференса (`vecdht-embed`), CLI оператора
(`vecdht-cli`, включая `agent publish/find/session/run`) и три мишени замеров (`benches`) — 497 теста
зелёных (три игнорируемых: полный PoW-майнинг CLI, 10-минутный гейт P5 и гейт P0(ii), которому
нужны веса и корпус вне git), закрыты гейты P2–P5 (включая транспорт и adversarial-набор §19.3),
детерминированная половина P0, гейт (v) на реальных весах и оба измеренных гейта P0 — (i) forward
и (ii) recall на реальном корпусе. Гейт (ii) измерен и **провален** (0.8303 при nprobe=16,
`E-0004`); claim §8.6 снят (`ADR-0003`), а не порог ослаблен. Масштабная проверка 807k идёт

## Замеры (`benches/`, §19.5)

Замеры не содержат порогов и не запускаются `cargo test`: у мишеней `test = false`, потому что
число — это число, а не предикат. Прогон целиком (несколько минут):

```
cargo bench -p vecdht-benches                                          # быстрый стенд, все три мишени
VEC_DHT_BENCH_SCALE=20 cargo bench -p vecdht-benches --bench wire       # числа для спеки
VEC_DHT_BENCH_SCALE=20 cargo bench -p vecdht-benches --bench index
VEC_DHT_BENCH_SCALE=20 cargo bench -p vecdht-benches --bench p0
```

Что прогон дал и что из этого следует для спеки: `pow_ok` = 7 МХеш/с на ядро (а не 200, как
предполагалось), `verify_body` ed25519 ≈ 20 400/с, group commit ≤32 опсов на fsync = 21 200 опсов/с
против 815 при fsync на каждый, RAM 443.6 Б на живую запись (бюджет §8.2 — 449 Б), полный скан
шарда 81 920 записей = 6.9 мс. Полная таблица с методикой прогона и оговорками — §19.5 спеки.

Эти абсолютные числа принадлежат хосту, а не коду, и это проверено прямым повтором: на следующий
день тот же бинарник на том же стенде, но с загруженной машиной, дал `pow_ok` 3,0–3,7 МХеш/с,
`Publish::decode` в 2.8 раза медленнее и ed25519-verify 1 426/с вместо 20 400 (на порядок хуже —
проверка подписи это длинная цепочка зависимых операций, и вытеснение потока стоит ей всей
цепочки). Отсюда правила, которые стоят в спеке: калибровочное число берётся только насыщенным
циклом (≥2 000 000 попыток) на свободном железе и в манифест идёт меньший из двух прогонов (§15.1),
а в текст переживают только отношения, не зависящие от хоста — `Find::decode` дороже
`Publish::decode` в 1.4–1.7×, group commit быстрее fsync-на-каждый-опс в 23–26×, RAM на запись
437–443 Б против бюджета 449 Б, полный скан тождественен brute-force всегда (инвариант, не
измерение).

## Гейты P0 (`vecdht-embed`, §18.1)

Детерминированная половина пайплайна §6.2 (шаги 1–3 и 6–8) собирается и тестируется без весов:
forward — единственный недетерминированный шаг — изолирован за feature `candle`, и именно поэтому
гейт (iv) измеряется раньше, чем появились веса.

```
cargo test -p vecdht-embed                    # unit + harness, быстрый режим (4 записи/кластер)
VEC_DHT_P0_FULL=1 cargo test --release -p vecdht-embed --features candle -- --nocapture
# (i)/(v) требуют весов вне git; RAYON_NUM_THREADS задаёт число потоков forward
RAYON_NUM_THREADS=1 VEC_DHT_MODEL_DIR=<...> cargo test --release -p vecdht-embed \
  --features candle measure_i_real_inference_throughput -- --ignored --nocapture
# (ii) требует корпус и held-out запросы вне git; подготовка MS MARCO — E-0004/E-0006
RAYON_NUM_THREADS=4 VEC_DHT_MODEL_DIR=<...> \
  VEC_DHT_P0_CORPUS=<corpus-50k.txt> VEC_DHT_P0_QUERIES=<queries-1k.txt> \
  cargo test --release -p vecdht-embed --features candle \
  gate_ii_real_corpus_recall -- --ignored --nocapture
# опции лестницы: VEC_DHT_P0_NLIST=512, VEC_DHT_P0_SHARD_COMPLETE=1 (те же данные)
```

Полный прогон поднимает корпус до гейтного размера (1024 кластера × 50 = 51 200 записей, 200
запросов) и включает временные asserted; в debug-профиле время не гейтуется намеренно — там та же
операция стоит на два порядка дороже, и «масштабированный» порог ничего не доказывал бы.

Замеренные числа (тот же хост, release):

* (iv) **1000/1000** побайтово идентичных 384-байтных выходов на потоках 1/2/4/8/16, плюс отдельная
  проверка, что между вызовами нет состояния (обратный порядок подачи, повторные прогоны).
  Межплатформенная часть гейта (AVX-512 / AVX2 / NEON) требует трёх машин и не закрыта;
* чувствительность сетки Δ=1/127 (§6.3): возмущение каждой координаты не более чем на 1e-5 меняет
  **0.17 координаты из 384** в среднем (покоординатная доля 4.5e-4 против оценки спеки 2.5e-3),
  максимум 3; при однородном сдвиге `cluster_id` не меняется ни в одной из 2000 записей. Это то
  число, на котором держится вся маршрутизация, и оно подтверждено до сетевого кода;
* (i) целочисленная половина: квантование + assign по 1024 int8-центроидов — **p50 0.108 мс,
  p99 0.215 мс** при бюджете 0.3 мс (§6.1). Реальный forward (тексты 27–77 токенов, tokenizer +
  CLS) — **10.96–11.96 emb/s** на потоке (p50 73–74 мс, p95 127–142 мс), 17.82–18.09 на 4 потоках,
  16.22–16.54 на 16: масштабирование насыщается после 4. Для планирования принят минимум 5 emb/s на
  поток, корпус 50k текстов на 4 потоках ≈42 мин. 100 emb/s из v7.5 не достигнуты, бюджет §6.1
  оказался консервативным в 3.7–12 раз относительно оценки 1–3 emb/s на ядро (`E-0003`);
* (ii) recall@10 на 50 000 MS MARCO queries измерен и **не достигнут**: **0.8303** при nlist=1024
  и nprobe=16 против порога 0.95 (`E-0004`). Полный скан в том же int8 даёт 1.0000, то есть потеря
  целиком в зондировании, а не в квантовании; кривая — 0.6479 / 0.8303 / 0.8961 / 0.9439 / 0.9730 /
  0.9913 при nprobe 4 / 16 / 32 / 64 / 128 / 256. Порог 0.95 достигается только между 64 и 128
  зондами, ценой 42–57 шардов из 64. Лестница исчерпана: nprobe 24/32, nlist=512 и shard-complete
  (0.8645; 0.9189 с nlist=512) не спасают (`E-0005`). Вывод — recall ограничен **долей
  ближайших к запросу кластеров**, попавшей в скан, а не числом просмотренных кандидатов:
  shard-complete сканирует 11 264 кандидата → 0.8645, а стандартный nprobe=128 сканирует 6 644 →
  0.9730 (кандидатов меньше, recall выше на 10,9 п.п.; уточнение — `ADR-0003`, раздел «Уточнение
  механики»). Раз карта `shard = cluster_id / 16` пространственно бессвязна, следующий механизм —
  связная карта шардов (`H-0007`/`E-0007`), а не подкрутка бюджета. Claim §8.6 снят (`ADR-0003`),
  nprobe=16
  остаётся default по latency, а не по recall. Масштаб 807 596 запросов проверяется отдельно
  (`H-0006`/`E-0006`): 50k при nlist=1024 — это ~49 записей на кластер, и опыт отвечает, лечит ли
  плотность провал. Синтетический стенд по-прежнему проверяет только механику (полный скан ==
  brute-force, монотонность), его число в спеку не входит;
* (iii) проверен контракт реранка (перестановка шортлиста без смены множества, равенство скоров →
  ANN-порядок, NaN — ошибка) и метрика nDCG@10; дельта ≥ +8% требует кросс-энкодера;
* (v) **HF-совпадение измерено**: `gate_v_against_hf_reference` на пяти зафиксированных текстах
  (кириллица, английский, короткий, мультиязычный, 256 токенов) даёт косинус **1.000000 на
  каждом**, минимум 1.000000 при пороге 0.999. Для запуска нужны `VEC_DHT_MODEL_DIR` и
  `VEC_DHT_HF_REFERENCE`; веса и референс — вне git, их хеши и протокол — в `E-0002`. Upstream
  candle 0.10.2 игнорирует `hidden_activation: silu` и даёт 0.860040, поэтому backbone
  вендоренный (`ADR-0002`). Это совпадение выходов; стоимость forward измерена отдельно в (i)
  (`E-0003`).

Ни один порог §18.1 в тестах не ослаблен: (ii) остаётся 0.95 и потому красный, неизмеренные
гейты помечены как неизмеренные, а не как пройденные.

## Гейты P3 (`vecdht-index`, §18.4 и §19.1)

Отдельные test-таргеты, потому что и память, и время меряются на уровне процесса:
`#[global_allocator]` считает аллокации всего бинаря, а тесты внутри одного бинаря идут
параллельно.

```
cargo test -p vecdht-index --test crash_matrix     # матрица §10.5, 10 точек + property-тест
cargo test -p vecdht-index --test determinism      # кросс-часовой GC, slot-стабильность, dedup
cargo test -p vecdht-index --test memory_budget    # 1M записей ≤ 428 МБ (±5%)
cargo test --release -p vecdht-index --test search_latency   # search ≤ 0.3 мс на 1104 записях
```

Замеренные числа на этом хосте (`x86_64-pc-windows-gnu`, rustc 1.99.1):

* память: арена 404.4 МиБ + списки 4.0 + dedup 8.0 + bitmap 0.1 = **416.5 МиБ**, 436.7 Б на живую
  запись против 449 Б таблицы §8.2; учёт аллокатора совпадает с разбивкой индекса до байта,
  после `drop` память возвращается;
* `search` nprobe = 16 кластеров, 1104 записи, top_k = 10: **p50 0.066 мс, p95 0.109 мс**
  (порог 0.3 мс). В debug-профиле временной гейт выключен намеренно: там та же операция стоит
  ~22 мс, и «масштабированный» порог ничего не доказывал бы — в debug остаются инварианты
  (равномерность кластеров, полнота `top_k`, стоимость, линейная по nprobe);
* crash-матрица: 10 точек + property `recover(disk) == replay(all ops)`. Число сидов property-теста
  зависит от профиля (12 в debug, 36 в release), потому что 36 × 90 опсов с fsync в debug — это
  ~135 с на одном ядре; классы падений покрыты полностью в обоих профилях.

Тесты «два узла» (кросс-часовой GC, два прогона одного потока) исполняются в одном процессе на
двух каталогах: это проверка детерминизма состояния, а не проверка совместимости двух машин.
Гейт §18.3 «golden-векторы совпали на двух разных машинах» по-прежнему не закрыт — для него нужен
второй хост.

## Гейты P4 (`vecdht-node`, §18.5 и §19.2)

```
cargo test -p vecdht-node --test gates_p4            # 4 сценария: handoff, W=2/R=3, fencing, seed
cargo test -p vecdht-node --test gates_p4 -- --nocapture   # с измеренным числом handoff
```

Сеть здесь модельная (`LocalNet`): одна стоимость доставки, `tick` только на границе
16-секундного бакета, `kill` закрывает соединение и шлёт оставшимся событие `peer_lost` (§9.8).
Именно поэтому замер handoff честный: время считается до `PublishAck` у агента, а не до «мы
догадались, что primary умер, по истечении lease в 90 с».

Замеренные числа (тот же хост, debug-профиль, `LATENCY = 1 с`):

* **handoff = 5 с** при пороге 10 с. Из них 4 с — четыре перехода доставки (запрос → primary →
  реплика → ack реплики → ack агенту), на сам election остаётся ~1 с: событие `peer_lost`
  запускает предложение сразу, а `election_timeout` в 60 с — только верхняя граница для случая
  «события нет, есть тишина»;
* три реплики сходятся по `applied_seq`, `owner → slot` и выдаче `search`; при W=2 подтверждение
  требует второй копии — после убийства обеих реплик запись остаётся в WAL primary, но `PublishAck`
  агент не получает (§9.4: W=2 из R=3 не превращается в W=1);
* рестарт с `epoch < max_epoch_served`: `grant_epoch` ⇒ `StoreError::StaleEpoch`, publish ⇒
  `EPOCH_STALE`, `serving_epoch = None`, пока цепочка не догонит диск (§9.2);
* уход всех ⇒ пустой состав в `epoch + 1`, `last_snapshot_seq > 0` у каждого seed, холодный
  `WalPullRequest{from_seq = 0}` догоняет снапшот по кускам и даёт тот же индекс, что у seed (§9.5, §9.7).

Пороги гейтов — числа из плана, и менять их ради зелёного вывода нельзя: непроходящий сценарий
трактуется как дефект протокола или реализации. PoW в этих тестах майнится под сложность 8 из
тестового манифеста: узел обязан следовать артефакту (§11.2), и 24 бита «для честности» сделали бы
из интеграционного теста бенчмарк blake3.

Golden-векторы сравниваются с фикстурами `crates/*/tests/golden/*.txt`, которые лежат в
репозитории: любое изменение кодека, квантования или канонического JSON видно как побайтовый diff,
и обновить фикстуру можно только явно.

```
VEC_DHT_GOLDEN=1 cargo test --release -p vecdht-wire     --test golden_vectors
VEC_DHT_GOLDEN=1 cargo test --release -p vecdht-crypto   --test golden_vectors
VEC_DHT_GOLDEN=1 cargo test --release -p vecdht-artifact --test golden_artifact
```

Долгий фаззинг гейта P2 (§20: 30 минут без паник) в `cargo test` по умолчанию не входит — там
бюджет по итерациям, секунды. Длительный прогон задаётся временем и сидом:

```
VEC_DHT_FUZZ_SECS=1800 VEC_DHT_FUZZ_SEED=1 \
  cargo test --release -p vecdht-wire --test fuzz_decode -- --nocapture
VEC_DHT_FUZZ_SECS=1800 VEC_DHT_FUZZ_SEED=1 \
  cargo test --release -p vecdht-crypto --test fuzz_verify -- --nocapture
VEC_DHT_FUZZ_SECS=1800 VEC_DHT_FUZZ_SEED=1 \
  cargo test --release -p vecdht-artifact --test fuzz_decode -- --nocapture
```

Декодер проверяется инвариантом каноничности: принятые байты пересобираются в себя (хвост после
length-prefix-кадра относится к следующему кадру, поэтому он в инвариант не входит). Крипто-слой
— инвариантами свойств: подпись на произвольных байтах не проходит, квант всегда в сетке,
`l2_sq` не переполняется, порог PoW монотонен по битам, `verify_cert` пропускает только
подписанный авторитетом, своевременный и не отозванный кредашиал.

Инвариант «принятое = пересобранное» уже окупился: на мутациях манифеста фаззер нашёл, что
`hex::decode` принимает заглавные буквы, а `hex::encode` всегда отдаёт строчные — то есть манифест
с `0A…` в hex-поле читался и пересобирался уже другими байтами, то есть подписывался бы другим
документом. Разбор hex-полей теперь требует строчные `[0-9a-f]`, а `Manifest::decode` вдобавок
сверяет весь документ с его же пересборкой (см. `uppercase_hex_is_not_canonical`).

`cargo` требует C-линковщика, потому что `blake3` собирает нативный код, а на `x86_64-pc-windows-gnu`
его ещё и надо найти. На Windows два варианта: установить Visual Studio Build Tools (toolchain
`msvc`), либо положить рядом полный standalone mingw-w64 и поставить его `bin` в `PATH` раньше
любого другого gcc — сборки из-под miniconda не хватает (нет `libws2_32.a`, линкер 2.25 не тянет
современный libstd, а тестовые таргеты с proc-macro DLL не линкуются вовсе:
`PATH="/c/Users/Admin/mingw64/bin:$PATH" cargo test`).

## Транспорт P5 (`vecdht-net`)

```
cargo test -p vecdht-net --test transport     # 10 сценариев на настоящем libp2p, ~10 с
```

Мок-транспорта здесь нет: тесты поднимают два-три `NetService` в одном `current_thread`-рантайме
(как и узел в бою — `SharedAdmission` намеренно `Rc`) и соединяют их по QUIC. Проверяется то, что
нельзя проверить на `LocalNet` из P4:

* `PeerId` выводит транспорт, а `NodeCert` привязывает к нему прикладного владельца; чужой
  `owner_ed25519` при подлинных подписях авторитетов отвергается на handshake, кадры такого пира
  получают `DENIED` (§4.1, §4.2). Асимметрия таблиц handshake — by design: проверить кредашиал
  узла может и тот, кому узел прав не даёт (это отдельно утверждается в тесте);
* publish идёт до `PublishAck` только при живой реплике: `w=2` означает «свой fsync + ack
  реплики», и узел без второго диска честно молчит. Тест держит три процесса и проверяет, что
  опс лёг в store реплики до того, как ack вернулся агенту (§9.4);
* `Find` отвечает кадром `MatchResult` и ровно одним `RendezvousAccept` на каждый match (§12.3);
* agent-клиент находит primary шарда через Kademlia-provider-запись §7.4; запись переобъявляется
  при изменении таблицы маршрутизации, а не только по 180-секундному таймеру;
* подписанный `Publish` в gossip-теме шарда доходит до primary и проверяется по подписи тела, а не
  по автору конверта (§5.3);
* закрытие QUIC-соединения доходит до `ShardNode::peer_lost`: primary узнаёт о смерти реплики
  событием транспорта, а не по истечении lease (§9.8);
* весь путь §12 на живом QUIC и PoW 20: агент публикует запись до ack, второй агент находит её
  через подписанный `Find`, получает приём на пару `(seeker, target, slot)` и открывает по нему
  прямой аутентифицированный канал; чужой `owner_ed25519` в приёме не проходит проверку;
* `CertRevoke` §4.2 в отдельной control-теме: порог 3-of-5 проверяется на приёме, поэтому
  ослабленный 2-of-5 отвергается и не сбрасывает ни одного соединения. Отзыв носителя `nonce`
  рвёт его соединения и снимает его с провайдер-записей, а узел, чей собственный кредашиал
  отозван, перестаёт отвечать, подписывать тики и объявлять шарды; повторный handshake к нему
  не проходит.

Честная граница: relay/DCUtR из §16.3 не подняты — адреса распространяются identify/Kademlia, и
путь через NAT без прямого dial не проверен. Множество отзывов живёт в памяти процесса: оно
переживает смену эпохи (§11.4), но не рестарт — после перезапуска узел снова узнаёт отзыв только
из повторной рассылки `CertRevoke`. Цепочка ротации самих ключей авторитета по-прежнему не
определена (§20.2, строка 8). `agent publish/find/session/run` в CLI и `Agent.publish/find/session`
в SDK работают по-настоящему: `run` поднимает listener и шагает вне вызовов, но смыслового слоя
входящих нет — `IntentTextRequest` узлом не обслуживается, поэтому сессии принимаются, а
содержательных ответов на них процесс не даёт. `node` (машина шарда с bootstrap членства и genesis)
остаётся на P6, а SDK пока не умеет веса — только явный суррогат.

## Adversarial §19.3 и гейт P5

`crates/vecdht-node/tests/adversarial.rs` — семь быстрых сценариев и полный гейт §18.6 под
`#[ignore]`. Быстрые проверяют то, у чего в v1 есть проверяемое следствие в коде:

* pre-farmed PoW: nonce, намайненный для другого шарда, эпизоды, срока или слота, отвергается
  `POW_INVALID`; подмена `vec_q` при старом `intent_id` — тоже, и индекс не меняется (§11.1);
* чужой `preprocessing_version` не входит ни в индекс, ни в matching: `Publish` и `Find`
  получают `MODEL_MISMATCH`, а не пустой результат (§6.7, §15.3). Проверка стоит в узле, а не
  только в handshake: `Publish`/`Find` приходят и от агентов;
* `ReplicateOp` со старой эпизодой или от чужого подписанта не применяется и не получает ack —
  молчание вместо oracle «эпоха принята/нет» (§9.2);
* тысяча DHT-подобных `Find` от разных ключей не двигает членство и не пишет в индекс: оно
  приходит только из подписанной цепочки (§9.2);
* лгущий index-node не может выдать свой текст за текст владельца: `IntentTextResponse`
  проверяется по ключу владельца до того, как текст попадёт в контекст (§6.6, §14.2);
* rendezvous-приём, выпущенный на пару `(seeker, target)`, не открывается другой цели и
  расходуется ровно один раз, даже если TTL ещё не истёк (§12.3);
* масштабированный sybil: 16 независимых ключей, `M=256`, узловой бюджет 100 admits/с —
  ровно `M` живых записей, все сверх потолка вытеснены, память арены после `M` не растёт,
  легитимный Find остаётся в бюджете §12.6, а более дорогая запись вытесняет дешёвую.

Полный гейт §18.6 — не «примерно столько записей», а верхняя граница на реальном CPU:

```
VECDHT_P5_SECONDS=600 VECDHT_P5_CORES=16 VECDHT_P5_BITS=20 \
  cargo test --release -p vecdht-node --test adversarial p5_gate -- --ignored --nocapture
```

Прогон 2026-10-20 на i7-10700 (8 физических ядер / 16 потоков), 600 с, 20 бит:
**31 891** попытка, **31 680** принято, **211** `BUSY`, **0** вытеснений, store = 31 680,
p50 легитимного `Find` = **2.25 мс**. Порог ≤ 64 000 выполнен с запасом ×2.0; узловой бюджет
100 admits/с не насыщен — потолок задаёт CPU (≈3,5 МХеш/с на поток, ≈3,3 кадра/с), как и предсказывает §18.6
для стенда 3,0–3,7 МХеш/с. Вытеснений нет потому, что `M=2 000 000` не достигнут; механика
`pow_bits`-evict проверена отдельно масштабированным сценарием.

Честная граница: в v1 нет penalty/reputation table, сигнала расхождения владельцев одного
кластера и verifiable re-computation `l2_sq` агентом (агент не скачивает байты записи). Набор
фиксирует криптографический барьер, который делает ложь бесполезной уже сейчас — подпись
владельца и привязку PoW; перечисленные три механизма остаются работой P6/P7 и не объявлены
проверенными.

## Лаборатория

Архитектурные изменения идут через научный контур `lab/`: гипотеза (`H-XXXX`) → эксперимент с
порогом, зафиксированным до прогона (`E-XXXX`) → решение (`ADR-XXXX`). Гейты остаются
единственным оракулом, записи append-only, отрицательный результат не удаляется. Контракт для
агентов — `AGENTS.md`; протокол и шаблоны — `lab/README.md` и `lab/templates/`.

Первый эксперимент — `E-0001` (гейт P5 выше), проверка контрактной модели — `E-0002` (гейт (v)),
стоимость реального forward — `E-0003` (гейт (i)), recall на 50k — `E-0004` и shard-complete —
`E-0005` (оба отрицательные, `H-0004`/`H-0005` опровергнуты), масштаб 807k — `E-0006`
(`H-0006`, идёт). Решения: `ADR-0001` (лабораторный контур), `ADR-0002` (вендоринг backbone),
`ADR-0003` (порог recall не ослаблен, claim §8.6 снят). Это не бюрократия ради
бюрократии: у агентов обнуляется контекст, и без записанного «какой командой, на каком железе, с
каким результатом» один и тот же вопрос проверяется заново.

## Что здесь не так, как в v7.5

Кратко, детали и измерения — в спеке:

* маршрутизация: SimHash-префикс заменён coarse-квантизатором из артефакта, шардов ровно 64;
* идентичность: `PeerId` остаётся тем, что выводит libp2p, роль даёт подписанный `NodeCert`;
* индекс: PQ удалён, хранится int8-вектор, recall перестаёт быть функцией квантования;
* PoW: Argon2id удалён, blake3 с привязкой nonce к `(owner, shard, epoch, slot, expiry)`;
  сложность переснята замером — 18–24 с default 20 ≈ 0,15–0,35 с CPU на publish (было «24 бита ≈ 84 мс»
  на выдуманной константе 200 МХеш/с; измерено 3,0–7 МХеш/с, §19.5);
* детерминизм: фиксированная точка Δ=1/127 вместо обещания bit-identical float-инференса;
* приватность: формулировка честно ослаблена — index-node читает то, что держит (honest-but-curious).
