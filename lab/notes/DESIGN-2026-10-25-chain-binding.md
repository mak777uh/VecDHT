# Стыковка блокчейнов для автовыплат: проект слоя над v9

> **Статус.** Проектное решение, пре-регистрируемый контур цикла. Это НЕ закрытый цикл и НЕ правка
> спеки: байтовые правила §V9.7 здесь не изменены, а дополнены объектами, которые ложатся **снаружи**
> канонической записи заказа. Ни одно измеренное число здесь не придумано; всё, что обязан доказать
> будущий цикл `E-0114`, вынесено в раздел «что измерить до правки спеки». Нормативным текст станет
> только после замера и отдельного ADR, по правилу «спека правится на измеренных фактах».
> **Родитель.** `docs/VecDHT-SPEC-v9.md` §V9.5 (квитанция), §V9.7 (интерфейс эскроу), §V9.8 (закрытый
> список кодов). Решение выбора победителя и экономика — `docs/PAID_ORDERS.md`.

## 0. Болевая точка, которую закрывает слой

Сегодня §V9.7 описывает интерфейс наблюдателя (`lookup/release/refund`), но не описывает **как решение
узла превращается в движение средств на внешней цепочке и как бенефициар получает выплату без
переписки с узлом**. Три конкретных провала, каждый — «нормативная строка без исполнителя»:

1. **Заказ не объявляет, какой ключ верификатора его оседлает.** Поле `verifier_pubkey` есть в
   квитанции (§V9.5), но в заказе его нет. Значит «квитанция подписана тем, кого ждал издатель» —
   это проверка извне, а не свойство байтов заказа; `E_RECEIPT_UNSIGNED` («verifier_pubkey не
   доверенный») висит над доверенным списком, которого в протоколе нет.
2. **Нет объекта, который сторонний мост цепочки мог бы проверить офлайн.** `release(order, to)` —
   вызов к наблюдателю. Перевод делает цепочка, и ей нужен не вызов, а **артефакт**: подписанные
   байты, из которых по §V9.5/§V9.8 выводится «выплата разрешена и кому».
3. **Бенефициар зависит от узла.** Пока нет подписанного требования, которое любой может разослать в
   mempool цепочки, автовыплата «без переписки» невозможна: нужен посредник, который знает адрес
   получателя и волю верификатора.

## 1. Инварианты, на которых держится элегантность (и которые нельзя нарушать)

- **A. Аддитивность байт-формата.** `PaidOrder::canonical_record()` (поля 1…13, §V9.2) не меняется
  ни на байт: иначе сдвинутся `order_ref`, все 30 векторов и закрытые циклы `E-0111`/`E-0113`. Всё
  новое живёт в **отдельных подписанных объектах** и в **непрозрачном `escrow_ref`** (поле 9), смысл
  которого определяет наблюдатель, а не канонический кодировщик заказа.
- **B. Судья не нужен.** Квитанция уже выводима из собственных полей (§V9.5). Новые объекты наследуют
  это правило: вердикт и право на выплату обязаны выводиться из байтов самого `PayoutClaim` +
  публичных данных заказа/цепочки, без обращения к узлу в момент проверки.
- **C. Реестр — данные, не код.** Добавление цепочки не имеет права делать недействительными уже
  опубликованные заказы. Поэтому заказ пинит **корень реестра**, а не «разрешён ли chain_id».
- **D. Закрытый список кодов.** Ни один новый объект не вводит девятнадцатый код: каждая неудачная
  проверка обязана маппиться на существующие 18 (§V9.8). Это проверяется машиной — см. «что
  измерить», порог (5).
- **E. Fail closed по умолчанию.** Как `DEFAULT_TRUSTED_CHAINS = []`: пустой реестр цепочек и пустой
  набор доверенных наблюдателей — легальное состояние, в котором выплата просто не проходит
  (`E_ESCROW_UNKNOWN`), а не «протокол сломан».

## 2. Объекты слоя

Все — канонические байты с SHA-256-доменом в стиле `vecdht/<имя>/v1` + `0x00`, подписанные Ed25519
(32-байтный verification key, 64-байтная подпись), как `Receipt`. Ни один не входит в
`canonical_record` заказа.

### 2.1 `VerifierBinding` — подпись издателя: «этот заказ оседлает вот этот верификатор»

```
DOMAIN_BINDING = "vecdht/paid_order_binding/v1"
VerifierBinding {
    order_ref        : Hash,   // привязка к заказу (поле 2 canonical_record уже есть)
    verifier_pubkey  : PubKey, // 32 байта — тот самый ключ, чья квитанция принимается
    image_digest     : Hash,   // дублирует поле 3 заказа для локальной сверки моста
    term_hash        : Hash,   // см. 2.2 — единая связка «заказ ⇄ деньги»
    signature        : 64,     // издатель, ключ = поле 12 canonical_record.publisher
}
```

Закрывает провал (1): соответствие «ключ квитанции = ключ, которого ждал издатель» становится
свойством подписанного артефакта, а не внешнего списка. Если `receipt.verifier_pubkey ≠
binding.verifier_pubkey` → `E_RECEIPT_UNSIGNED` (существующий код).

### 2.2 `term_hash` — единственная связка заказа с деньгами

Канонический SHA-256 кортежа, одинаково пересчитываемый издателем, наблюдателем и мостом цепочки:

```
DOMAIN_TERM = "vecdht/paid_order_term/v1"     // 25 байт, как и остальные домены слоя
term_hash = sha256( DOMAIN_TERM ‖ 0x00 ‖ order_ref ‖ chain_id(8 LE) ‖ asset_bytes ‖
                    beneficiary_pubkey(32) ‖ amount(16 LE) ‖ escrow_ref_len(4 LE) ‖ escrow_ref )
```

`asset_bytes` — ровно те tagged-байты, что поле 8 `canonical_record` (тег `0` native / `1` token +
`chain_id` + `address[20]`), **включая его собственный терминатор `0x00`**, чтобы не заводить второе
кодирование актива. `chain_id(8 LE)` перед ним — `Asset::chain_id()` (для `native` это 0 по §V9.2),
то есть число цепи, на которой мост блокирует залог; для `token` оно дублирует поле актива, и это
намеренно: у моста есть цепь, а формы актива он не разбирает. `beneficiary_pubkey` —
verification key принятого исполнителя (поле подачи, не заказа). `escrow_ref` — непрозрачные байты
поля 9. Один `term_hash` связывает: что заказано, на какой цепи, каким активом, кому, сколько, по
какой ссылке залога. Мост цепочки блокируется именно на него.

### 2.3 `ChainDescriptor` + `registry_root` — реестр как данные

```
DOMAIN_CHAIN = "vecdht/chain_registry/v1"
ChainDescriptor { chain_id: u64, name: string, bridge_code: u16, settle_asset_tag: u8,
                  min_amount: u128, note: string }
// реестр — отсортированный по chain_id список; корень — тот же merkle-корень, что §V9.4 для
// множества файлов (детерминированная сборка листьев = sha256(DOMAIN_CHAIN ‖ descriptor_bytes)).
registry_root = artifact_set_hash( описатели реестра )
```

Правило (C): заказ/`EscrowWitness` пинит `registry_root`. Добавление цепочки порождает новый корень;
старые свидетельства остаются валидны против своего корня. `registry_root` вне доверенного набора
наблюдателя → `E_ESCROW_UNKNOWN` (существующий код). `bridge_code` — 16-битное поле, чтобы мост знал
параметры разблокировки, не переписывая протокол; неизвентный `bridge_code` не новый код ошибки, а
`E_UNSUPPORTED_ASSET` на уровне актива (актив не поддержан формой из описателя).

### 2.4 `EscrowWitness` — подпись наблюдателя: «залог есть, заблокирован, достаточен»

```
DOMAIN_WITNESS = "vecdht/escrow_witness/v1"
EscrowWitness {
    term_hash      : Hash,   // для какого контракта связки свидетельствуем
    chain_id       : u64,    // = EscrowState.chain_id
    status         : u8,     // 0 not_funded / 1 locked / 2 released / 3 refunded (4 состояния, не 5)
    amount_on_chain: u128,   // сколько реально залочено
    block_ref      : bytes,  // непрозрачная метка высоты/хеша блока цепочки, для аудита
    registry_root  : Hash,
    observer_pubkey: PubKey, // ключ наблюдателя
    signature      : 64,     // наблюдатель
}
```

Это сериализуемое отражение `EscrowState` + результата `check_escrow`. Наблюдатель ничего не
подписывает о вердикте — только о залоге. Несовпадение `amount_on_chain < reward.amount` при
`locked` → `E_ESCROW_INSUFFICIENT`; `status ∈ {released, refunded}` → `E_REPLAY` («уже распорядили»);
`chain_id`/`registry_root` вне доверенного → `E_ESCROW_UNKNOWN`. Все — существующие коды.

### 2.5 `PayoutClaim` — требование бенефициара: артефакт, который мост проверяет офлайн

```
DOMAIN_CLAIM = "vecdht/payout_claim/v1"
PayoutClaim {
    term_hash   : Hash,
    order_ref   : Hash,
    receipt     : Receipt,        // встроен целиком (§V9.5) — источник verdict'а
    binding     : VerifierBinding,// встроен — источник «кого ждал издатель»
    witness     : EscrowWitness,  // встроен — источник «залог достаточен и locked»
    beneficiary : PubKey,         // == submission.submitter == получатель release
    signature   : 64,             // подпись бенефициара (исполнителя)
}
```

**Замыкает провалы (2) и (3).** Мост цепочки, не доверяя никому, исполняет чистую функцию:

1. восстановить `term_hash` из (order fields + beneficiary + witness.chain_id/amount) и сверить с
   `PayoutClaim.term_hash` → иначе `E_HASH_MISMATCH`;
2. `Receipt.derive()` (§V9.5) → вердикт обязан быть `pass` и равен напечатанному → иначе
   `E_VERDICT_MISMATCH`;
3. `receipt.verifier_pubkey == binding.verifier_pubkey` и подпись квитанции валидна → иначе
   `E_RECEIPT_UNSIGNED`;
4. `binding.order_ref == order_ref`, подпись binding'а ключом `order.publisher` валидна → иначе
   `E_RECEIPT_INVALID`;
5. `witness.term_hash == term_hash`, подпись наблюдателя в доверенном наборе, `status == locked`,
   `amount_on_chain ≥ reward.amount`, `registry_root` доверен → иначе `E_ESCROW_UNKNOWN` /
   `E_ESCROW_INSUFFICIENT` / `E_RECEIPT_UNSIGNED`;
6. `now ≤ deadline + PAYBACK_WINDOW_SECONDS` → иначе `E_DEADLINE_PASSED`.

Ни один шаг не обращается к узлу VecDHT. Любой, у кого есть эти байты, пересчитывает решение.
Бенефициар рассылает `PayoutClaim` в mempool сам — «без переписки» выполнено: адрес получателя
берётся из подписанных байтов (`beneficiary`), а не из разговора с узлом. Повторная рассылка того же
`term_hash` после разблокировки мост отсекает по `E_REPLAY` в свидетельстве (двойная трата держится
на уровне цепочки + статусе `released`).

## 3. Как это стыкуется с разными цепочками, не меняя протокол

`bridge_code` описателя — единственное, что знает мост о конкретной цепочке. Классы:

- **цепи с нативным Ed25519-VERIFY на контракте** (few): мост сам проверяет подписи `PayoutClaim`
  полностью офлайн — эталонный путь «без переписки»;
- **EVM-подобные** (secp256k1): Ed25519-подписи объектов v9 на контракт не ложатся. Мост хранит
  только `term_hash` и `registry_root`, а соответствие «получатель = адрес на этой цепи» — обязательство
  наблюдателя, засвидетельствованное в `EscrowWitness`. Честная граница: на таких цепях шаг (5)
  опирается на доверенного наблюдателя, не на криптографику получателя → пункт `OPEN-V9-18`
  (relay/привязка адресов без Ed25519);
- **цепи без детерминированного времени на блоке**: шаг (6) требует оракула времени → отдельный
  `OPEN-V9-19`.

Реестр как данные (2.3) означает: «добавить цепочку» = опубликовать новый `registry_root` и ADR про
набор наблюдателей; существующие заказы и свидетельства не протухают.

## 4. Почему слой элегантен (сводка)

1. **Один `term_hash`** вместо нескольких параллельных идентификаторов: заказ, залог, выплата,
   мост — всё сходятся в одном байте-корне.
2. **Квитанция остаётся единственным источником вердикта**; новые объекты не судят, а связывают.
3. **Реестр — данные**: расширение набора цепочек не трогает байты и не инвалидирует прошлое.
4. **Закрытый список не вскрыт**: 0 новых кодов, все отказы маппятся на 18 (§V9.8).
5. **Автовыплата = чистая функция над байтами**: мост и бенефициар не зависят от живого узла.

## 5. Что измерить до правки спеки (пре-регистрация `H-0114` / `E-0114`)

Пороги фиксируются **до** замера; изменение порога = новый эксперимент. Кандидаты (значения —
намерения, не результат):

1. **Сверка byte-форматом.** Сторонняя реализация только на `hashlib` (как `E-0113`) обязана
   пересобрать `term_hash`, `registry_root` и канонические байты `VerifierBinding`/`EscrowWitness`/
   `PayoutClaim` из спеки и векторов → `V9C_INDEP_MATCH=1` (строгий, 1).
2. **Стабильность носителя.** `PayoutClaim`-векторы побайтово воспроизводимы дважды на неизменном
   дереве → `V9C_CARRIER_SHA` стабилен, `VECTOR_STABLE=1`.
3. **Чистая функция вывода выплаты.** Для каждого вектора `PayoutClaim` мост-эмулятор (python)
   выдаёт вердикт, совпадающий с Rust `check` → `V9C_MIRROR_EQ=1`.
4. **Двойная выплата.** Второй `PayoutClaim` на тот же `term_hash` после `released` → `E_REPLAY` в
   100 % векторов (`V9C_DOUBLE_REPLAY = ожидаемое_число`).
5. **Закрытость кодов.** Объединение кодов, выведенных на всех `PayoutClaim`-векторах, ⊆ 18; ни один
   вектор не печатает код вне списка → `V9C_CODES_SUBSET=1`, посадка 19-го имени обязана отбиваться
   (`V9C_CODE_GUARD_DECOY=1`).
6. **Аддитивность.** `sha256` канонической записи `PaidOrder` (поле 1…13) НЕ изменился относительно
   `E-0113` → `V9C_ORDER_REF_UNCHANGED=1` (иначе закрытые циклы легитимно краснеют и нужен отдельный
   перепин).

Ресурсный порог (по правилу хоста) обязан назвать три числа: свободный диск, RAM, pagefile — и не
начинать уборку `target/`, пока диск не оказался причиной.

## 6. Чего этот слой НЕ утверждает

- Нет реализованного наблюдателя, моста и набора доверенных ключей — `DEFAULT_TRUSTED_CHAINS = []`
  остаётся; слой описывает интерфейс и байты, а не разворачивает сеть.
- Нет escrow-контракта ни на одной цепочке, нет testnet, нет картинки верификатора.
- Соответствие модели Lean (если её заведут для `term_hash`/реестра) и кода — не проверено прибором
  (правило владельца 2026-10-24); любая теорема здесь будет «для модели».
- Перевод средств делает цепочка; узел VecDHT не держит ключей и не подписывает транзакции — §V9.7
  сохранён без изменений по этому инварианту.

## 7. Реестр новых открытых пунктов (для секции OPEN-QUESTIONS после замера)

Нумерация продолжается за `OPEN-V9-17`, который зарегистрирован в
`lab/decisions/OPEN-QUESTIONS.md` п. 59. Первая версия этого раздела занимала `OPEN-V9-11…13`
под свои смыслы и тем самым вскрывала чужие номера; посадку поймал новый класс стража
(`promise-double-definition` — один номер определён строкой описания в двух файлах), поэтому
номера здесь сдвинуты, а прежние значения не переопределены.

- `OPEN-V9-18` — relay/привязка адресов на цепях без Ed25519-VERIFY (шаг 5 опирается на наблюдателя);
- `OPEN-V9-19` — оракул времени для шага (6) на цепях без детерминированного времени блока;
- `OPEN-V9-20` — порядок приоритета, если один заказ имеет два действительных залога (два witness);
- `OPEN-V9-21` — производитель `PayoutClaim` (кто собирает связку) и сеть её доставки —
  пересечение с волной C («нет команды, поднимающей узел-шард»).
