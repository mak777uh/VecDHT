# E-0056 — дыра lease-таблицы возвращается после `prune` по TTL: на бакете 19 полная таблица, на бакете 20 выдача разом

## План прогона

Оракул `crates/vecdht-node/tests/ceiling_prune_recovery.rs`, helper `lab/e0056-run.sh`
(helper исполняет команду целиком — урок `e0049`; структура секций скопирована с зелёных
`e0050`/`e0051`: BUILD `--no-run` → RUN `--nocapture` → ИНВЕНТАРЬ → КОНТРОЛЬ
`-p vecdht-node`). Харнес — одиночный primary (`primary_on`, как в `E-0044`…`E-0049`),
три записи бакета 0, таблица забита всеми `MAX_ACCEPTS` строками бакета 0 вручную.
Лог: `lab/logs/e0056-all.log` (append-only). Пороги заморожены в `H-0056` до первого
замера; коммит пре-регистрации пушится до измерений.

## Прогон

Один зачётный прогон `e0056-run.sh` (rev `fcc171b`, BUILD `--no-run` EXIT=0 → RUN
`--nocapture` EXIT=0, 35.7 с → ИНВЕНТАРЬ → КОНТРОЛЬ `-p vecdht-node` EXIT=0). ДИАГНОЗ'ов
нет: все четыре порога совпали с предсказанием с первого замера. Строка итога из лога:
`refused_full 3→6→6→6`, выдача `0 / 0 / 3 / 3(побайтовый повтор)`, `live 100 000 → 100 000 → 3 → 3`.
Инвентарь подтвердил арифметику: `Issuer::prune` — `cutoff = now.checked_sub(self.ttl_buckets)`,
`buckets(sec) = sec.div_ceil(16)` (`config.rs`), `rendezvous_ttl = 300` (`config.rs:143`);
`falsifier (е)` в оракуле сверяет обе константы до замеров. Верификация воркспейса:
562 ok / TEST_EXIT=0 / CLIPPY_REAL_EXIT=0.

## Что это значит

Десятое подтверждение §12.3 подряд: потолок lease-таблицы — не постоянная ловушка, а
lease в прямом смысле. Полная таблица бакета 0 блокирует выдачу ровно до бакета
`buckets(ttl_sec)` включительно (на `now = 19` — отказов уже 6, приёмы ещё не вышли),
но на `now = 20` `prune` снимает все 100 000 строк разом — разом, а не по мере старения,
потому что выбрасываются целые бакеты, а не записи. После снятия потолок перестаёт
мешать: тот же seeker сразу получает 3 приёма (по числу живых находок), выдаются они
новым бакетом `issued_bucket = 20`, повтор в том же бакете — идемпотентность (`seen`
обходит `cap`) отдаёт те же байты. Различающий порог (2) подтвердил граничную арифметику
`checked_sub` (`0 < 19-19` ложно, `0 < 20-19` истинно) против альтернативы «скользящий
TTL по секундам» — при ней бакет 0 начал бы истекать до `now = 19`. Никаких расхождений
спеки с кодом здесь нет: §12.3 обещает потолок и TTL-жизнь приёмов, код и оракул
согласованы; правка спеки не нужна.

## Границы

Мерялось взаимодействие выдачи с `prune` на живом `on_frame`-пути одиночного primary,
а не юнит-поведение `Issuer::prune` напрямую. Таблица заполнена вручную строками бакета 0
на чужих ключах (`issue(junk, identity(90), …)`) — в бою таблица наполнялась бы бакетами
разных моментов, тогда prune освобождал бы дыры постепенно (по одному бакету за шаг), а не
разом; «разом» здесь — следствие синхронного заполнения, сам механизм (бакеты `< cutoff`
уходят целиком) из инвентаря лога. Порог (3) подтверждает только возврат дыры для того же
seeker'а; расход выпущенных после prune приёмов через `Spend` — территория `E-0044`…`E-0047`.
