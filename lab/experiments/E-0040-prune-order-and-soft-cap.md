## Границы

- Мерялась локальная политика объекта `Admission` на подменённых лимитах (`with_limits(_, 3, 1)`),
  не узел и не сеть: `MAX_TRACKED_PEERS = 65 536` в прогоне не достигался (арифметика правила
  не зависит от константы, константа защищена compile-time assert'ом памяти).
- Порядок жертв среди idle-строк **неотличимо из публичного API** (порог (4) как раз это
  измеряет): отличие зафиксировано только internal-тестом, читающим приватный `per_peer`.
  Поэтому вывод — дефект документации (`admission.rs:195/:344` обещают отбор по `seen_sec`),
  а не дыра квоты: поле `seen_sec` — мёртвый код, его можно удалить без изменения поведения.
- «Атакующий выбирает адрес — значит выбирает, какие его idle-строки переживут prune» —
  записано как следствие порядка обхода, но измерено только в том смысле, что порядок
  байтовый: никакого квотного преимущества из этого не извлечено (все idle-строки равны
  новой), отдельной атаки не строилось.
- 20-секундное окно «активная строка не вытесняется» взято из манифеста (burst 20, refill 1/с);
  при других параметрах окно другое — формула `burst/rps`, правок порога не было.
- Не проверялось: взаимодействие prune с denylist (строки уходят, запрет остаётся — закрыто
  ранее unit-тестом `denylist`), CPU-цена обхода при 65 536 строк (это память/профиль, не правило).
