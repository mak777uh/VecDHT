# E-0036 — `release`-профиль для `clusters_of_shard`: ноль паник, шестнадцать пустых списков, 65 выходов

## Гипотеза

См. `H-0036`.

## Стенд (правок измерительного гейта нет)

`crates/vecdht-crypto/tests/shard_number_release.rs`: один цикл по всем `0…65 535` входам,
`catch_unwind` с заглушённым panic-хуком, разбор на «паника / пустой список / непустой список»,
сравнение непустых с `clusters_of_shard(s % SHARDS)`, накопление множества различных выходов. В
debug-профиле тест печатает строку пропуска и не содержит утверждений. Константы берутся из
`vecdht-wire::constants`, `CLUSTERS_PER_SHARD` и `SHARDS` не переписываются в тест. Правок
`clusters_of_shard`, `Cargo.toml` (профили) и гейтных порогов нет.

## Прогон

Пре-регистрация (`964a844`) залита до прогона. Отклонение в порядке, зафиксированное честно: этот
пре-регистрационный коммит ушёл с **несобирающимся** тестовым файлом — проверка компиляции
откладывалась, потому что `target/` был занят полной верификацией main, а я не стал ждать.
Компиляция упала на `E0277` (`mismatches[..]` без `&` — несайзированная ветка в `eprintln!`),
правка вошла в `8265051`. Замеров к тому моменту не было ни одного, пороги не тронуты.

Хронология:

1. Полная верификация main (`lab/logs/workspace-verify-2026-10-22.log`): первый захват exit-кодов
   был снят с pipeline (`… | grep`; `echo $?` от `grep`), поэтому ничего не утверждал; настоящий
   прогон показал `cargo test --workspace` = 101 (из-за файла E-0036) и `cargo clippy --workspace
   --all-targets -- -D warnings` = 101 (4 × `unnecessary_cast` в
   `crates/vecdht-index/tests/geometry_rotation.rs:170,173,348,362`). После правок обоих — `0`/`0`
   (раздел «ВЕРИФИКАЦИЯ ПОСЛЕ ПРАВОК»). Это и есть первая причина, по которой цикл про release
   оказался не косметическим: **чистота main по всей сборке раньше не проверялась**.
2. `lab/e0036-run.sh` на дереве `8265051`, release, `EXIT=0`. Строки оракула из
   `lab/logs/e0036-all.log`, дословно:
   * `## release: паник 0, пустых списков 16 (первые [4095, 8191, 12287, 16383]), несоответствий маски 0 ##`
   * `## release: различных выходов 65, ожидалось 65 (64 законных списка + пустой) ##`
   * `## время перебора 0.0 с ##`
3. **КОНТРОЛЬ 1 (`cargo test -j 2 --release -p vecdht-crypto`) — КРАСНЫЙ.** Упал
   `shard_number_admission` (E-0034): тест утверждал `try_clusters(4095).is_err()` и
   `panicked.contains(&4095)` без привязки к профилю, а в release там пустой список вместо паники.
   `cargo test` останавливается на первом упавшем таргете, поэтому `shard_number_exhaustive` (E-0035)
   в том прогоне не дошёл до своей assertion-строки — он красный по той же причине
   (`first_panic == Some(4095)`, `last_ok == Some(4094)`).
4. Правка: в обоих файлах пороги, специфичные для debug, обёрнуты в `if cfg!(debug_assertions)`, а
   в `else`-ветке стоят утверждения, которые даёт `E-0036` (пустой список на 4095 и 65 535, полный
   набор `{4095 + 4096·k}`, живое верхнее множество целиком, `last_ok = 65 535`). В `E-0035`
   дополнительно потребовалось вести `last_ok` и по верхнему циклу — в debug этот цикл никогда не
   возвращает список, поэтому debug-формулировка порога (2) не изменилась. Две мои собственные
   ошибки при правке зафиксированы в логе и в истории: `Some(Vec::new())` вместо `Ok(Vec::new())`
   (`try_clusters` возвращает `Result`) и `24_576` вместо `61 441` размеров верхнего множества.
5. Повторный контроль (раздел «ДОПОЛНЕНИЕ ПОСЛЕ ПРОГОНА» в `lab/logs/e0036-all.log`):
   `DEBUG_TEST_EXIT=0`, `RELEASE_TEST_EXIT=0`, `CLIPPY_DEBUG_EXIT=0`, `CLIPPY_RELEASE_EXIT=0`;
   debug-ветка нового теста печатает «пропуск» и не притворяется измерением (`КОНТРОЛЬ 2`).

## Результат

Порог | Заявлено до прогона | Снято (release) | Итог
---|---|---|---
(1) паники | ровно 0 по всему входу | `паник 0` | выполнен
(2) пустые списки | ровно 16, позиции `{4095 + 4096·k, k = 0…15}` | `пустых списков 16`, первые `[4095, 8191, 12 287, 16 383]`, последняя 65 535; совпадение со всем множеством проверялось `assert_eq!` по вектору | выполнен
(3) непустые выходы | 0 несоответствий маске, все длины 16 | `несоответствий маски 0` | выполнен
(4) различные выходы | ровно 65 | `различных выходов 65` | выполнен

Фальсификаторы (а)…(г) не сработали → `H-0036` подтверждается. Справочный расчёт из `run.sh`
(не замер) совпал с перебором: 16 позиций замыкания `base + 16`, первая 4095, последняя 65 535.

Итог по существу: в поставляемом профиле у `clusters_of_shard` **нет аварийного исхода вовсе**.
Весь вход `u16` — это тихий результат: 64 замаскированных законных списка плюс пустой список в
16 точках, где `base = 65 520`. Debug-граница «от 4095 узел упадёт», на которую опиралась формулировка
`E-0034` («граница риска»), в поставке не существует: `release`-сборка не падает, а отдаёт пустоту.

Второй итог, методический и, возможно, более полезный: `cargo test --workspace` в debug не
проверяет release-поведение тестов, а часть гейтов (§19.1, `search_latency`) живут именно в
release. Пока оракулы проверялись по одному crate в debug, два из них (`E-0034`, `E-0035`) были
красными в release и никто этого не видел.

## Границы результата

* Измерено поведение `vecdht-crypto::quant::clusters_of_shard` в `release`-профиле данной машины
  (rustc 1.99.1, windows-gnu, `overflow-checks` по умолчанию выключены). Если сборка когда-нибудь
  получит `overflow-checks = true` в `[profile.release]`, выводы этого цикла перестают относиться к
  поставке — проверка стоит в `run.sh` как печать профиля, но не как assert.
* Оракул вызывает функцию напрямую. Достижимость из сети (что кадр с таким номером доходит до
  вызова) не измерялась и в этом цикле: фальсификатор (а) `E-0034` остаётся открытым. Слово
  «уязвимость» здесь не употребляется по той же причине, что и в `E-0034`.
* Пустой список как *последствие* для владельца (`node.rs:986` → `IvfIndex::search(q, clusters)`)
  в этом цикле не измерялся: здесь зафиксировано только то, что такой выход функция производит.
  Что делает узел с пустым или раздутым списком `Find` — отдельный пре-регистрационный цикл.
* Правки в `shard_number_admission.rs` и `shard_number_exhaustive.rs` не меняют их debug-выводов:
  снятые в `E-0034`/`E-0035` числа остались прежними, изменён только способ не утверждать
  debug-семантику в release.
* Профиль-гейтинг — это не «ослабление порога», но и не усиление: в release-прогоне старого теста
  порог (4)/(2) не проверялся вовсе (он падал), теперь проверяется их release-аналог. Оба набора
  утверждений видны в коде и в этом файле.
