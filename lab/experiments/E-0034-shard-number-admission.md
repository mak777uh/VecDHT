# E-0034 — номер шарда вне диапазона: маска в `clusters_of_shard`, 3 проверки на 13 сообщений

## Гипотеза

См. `H-0034`.

## Стенд (правок измерительного гейта нет)

Новый тестовый файл `crates/vecdht-crypto/tests/shard_number_admission.rs`: один тест, который по
набору номеров `{0, 1, 63, 64, 80, 128, 1024, 4094, 4095, 65535}` снимает либо список кластеров, либо
панику переполнения (`catch_unwind` с глушителем хука, чтобы прогон не обрывался на границе), и
сравнивает полученные списки со списками шарда `shard % SHARDS`. `crypto` зависит от `wire`, поэтому
и сообщения, и константы (`SHARDS`, `CLUSTERS_PER_SHARD`, `NLIST`) видны отсюда; сеть, корпус и
`candle` не поднимаются. Сборка debug — это часть замера: в release та же арифметика `u16` была бы
тихим кольцом вместо паники. Правок `clusters_of_shard`, `messages.rs`, `node.rs`, гейтных порогов нет.

## Прогон

Одно усилие, `lab/e0034-run.sh` на дереве `68cb4e5` (пре-регистрация залита до запуска; оракул до
прогона только компилировался `--no-run`), `EXIT=0`, тест за 0,00 с:

```
probes [0, 1, 63, 64, 80, 128, 1024, 4094, 4095, 65535]
  замаскировано в чужой законный список 5: 64→0, 80→16, 128→0, 1024→0, 4094→62
  паника переполнения u16: [4095, 65535]   (при 4094 список строится)
is_valid_shard вне vecdht-crypto (нетестовый код): 0 сайтов
pub shard: u16 в messages.rs: 13 сообщений; проверок shard >= SHARDS при декоде: 3
  с проверкой: LeaseGrant, SnapshotOffer, ReplicateAck
  без проверки: ProtocolError, PublishAck, MatchResult, WalPullRequest, WalPullResponse,
                ReplicateOp, DeleteOp, MembershipUpdate, LeaveNotice, RendezvousAccept
node.rs: 8 сайтов сверки «!= self.shard» (466, 673, 877, 981, 1053, 1158, 1245, 1303)
контроль cargo test -p vecdht-crypto: 46+4+3+1 зелёные
```

Оговорка к порогу (1): предрегистрированное счётное правило («grep по нетестовому коду») отдалит 4 строки,
потому что одна из них — вызов внутри `#[cfg(test)] mod tests` в `quant.rs:407`, а фильтр скрипта
вырезает только `/tests/` и объявления `fn`. По существу порог выполнен: вызовов из собранного кода
ровно 3, все в `cli/src/index_cmd.rs`, и во всех трёх номер уже прошёл `dir_and_shard` с проверкой
`shard >= SHARDS` (`index_cmd.rs:88`). Правка порога под удобный ответ не делалась.

## Результат

Гипотеза подтверждена. Маска `% NLIST` материальна: любой из пяти снятых внедиапазонных номеров
побайтово даёт список кластеров законного шарда `shard % 64` (64 → кластеры 0–15, 80 → 16 кластеров
шарда 16, 4094 → кластеры шарда 62). Функция не сообщает, что номер чужой, — она молча подменяет
один шард другим. Граница риска по арифметике: `base = shard · 16` вместе с `base + 16` умещается в
`u16` до 4094 включительно, при 4095 и выше — паника переполнения в debug (и тихое кольцо в release,
что хуже: там вместо паники был бы ещё один замаскированный список).

Guard `is_valid_shard` в протокольном коде не вызывается нигде (0 сайтов вне `vecdht-crypto`), а
диапазонную проверку при декоде имеют 3 сообщения из 13 с полем `shard`. Всё, что закрывает путь
сегодня, — два других слоя: операторский CLI проверяет `--shard` сам, а приёмка в `node.rs` сверяет
номер со своим (`!= self.shard`, 8 сайтов), то есть чужой номер отбивается не как «вне диапазона», а
как «не мой». При подъёме `SHARDS` (стадия 1) ни тот, ни другой слой не станет границей автоматически:
CLI-проверка и `BadEnum`'ы в `messages.rs` уже написаны через константу, а маска в `clusters_of_shard`
— через `NLIST`, и именно она превращает «чужой номер» в «чужой список» при любом значении констант.

Практического следствия в этом прогоне нет и не заявляется: reachability из сети не проверялась
(в этом и был смысл ограничения стенда), а изменение `clusters_of_shard` на явную ошибку при
`!is_valid_shard(shard)` — правка протокольного кода, она требует решения владельца, а не цикла
измерения.

## Границы результата

Снят набор из десяти номеров, а не всё пространство `u16`: утверждение «каждый внедиапазонный номер
до 4094 отображается в `shard % 64`» следует из арифметики (`(s·16) mod 1024 = 16·(s mod 64)` при
`s ≤ 4094`) и подтверждено на пяти точках, но полным перебором 64…4094 не проверялось.

Числа 13/3/8 — результат grep'а по `messages.rs` и `node.rs` в текущем дереве; они считают строки с
заданным шаблоном, а не все способы выразить проверку (например, сверка могла быть встроена в
условие `&&` другой ветки). Для 13 сообщений список с проверками и без напечатан в логе поимённо,
так что пересчёт открыт.

Пугающее слово «уязвимость» здесь не используется намеренно: чтобы оно стало уместным, нужен
доказанный путь от декода непроверенного сообщения до `clusters_of_shard` (фальсификатор (а)), а его
этот прогон не проверял. Это ровно то, что стоит проверить следующим, если гипотеза «остаётся
только остаток класса (H)» кого-то не устраивает.

Workspace-проверка (`cargo test --workspace`, `cargo clippy --workspace --all-targets`) по-прежнему
отложена до конца `E-0027`; в этом цикле зелёным проверено `vecdht-crypto` целиком плюс
`clippy -p vecdht-crypto --all-targets -- -D warnings`.

## Дополнение после E-0036: этот оракул был красен в release-профиле (append-only, порог не меняется)

`E-0036` в своём контроле 1 (`cargo test --release -p vecdht-crypto`) показал, что
`crates/vecdht-crypto/tests/shard_number_admission.rs` падает вне debug: пороги (3) и (4)
утверждали `try_clusters(4095).is_err()` и наличие 4095 в снимке паник, а в release арифметика
`u16` кольцевая и на этом входе пустой список. Debug-прогон workspace этого не ловил.

Снято и зафиксировано в `E-0036` (тот же перебор в release): паник 0, пустых списков ровно 16 на
`{4095 + 4096·k}`, замаскированные списки ниже границы — те же, что в таблице этого прогона.
После правки debug-формулировки этого эксперимента сохранены дословно, для release добавлена
отдельная ветка утверждений. Существенно для вывода: строка этого файла о «границе риска от 4095»
в поставке не работает — `release`-узел на 4095 не падает, а получает пустой список.
