# E-0035 — полный перебор `u16` для `clusters_of_shard`: два исхода, граница на 4095, 64 различных выхода

## Гипотеза

См. `H-0035`.

## Стенд (правок измерительного гейта нет)

Новый тестовый файл `crates/vecdht-crypto/tests/shard_number_exhaustive.rs`: два цикла по всему
входу `u16` (4095 значений нижнего множества и 61 441 верхнего), каждый вызов через
`catch_unwind` с заглушённым panic-хуком, сравнение с `clusters_of_shard(s % SHARDS)`, накопление
множества различных выходов и позиция первой паники. Ни сети, ни корпуса, ни `candle`; `CLUSTERS_PER_SHARD`,
`SHARDS`, `NLIST` берутся из `vecdht-wire::constants`, а не переписываются в тест. Правок
`clusters_of_shard` и гейтных порогов нет.

## Прогон

Пре-регистрация (`a4fb1d3`) залита и запушена до первого замера; до прогона допускался только
`cargo test --no-run`. Хронология по шагам, включая две неудачные попытки, потому что они часть
дисциплины, а не детали сборки:

1. **Сборка до прогона — падение компиляции.** Первая попытка `--no-run` дала `E0277`:
   `the trait bound usize: From<i32> is not satisfied` в строке 70 — `usize::from(4095)` вывелся в
   `i32` (литерал без суффикса). Исправлено на `4095_usize.saturating_sub(unexpected_panic.len())`.
   К этому моменту не снято ни одного замера, порог не тронут.
2. **Прогон оракула (`lab/e0035-run.sh`, дерево `a4fb1d3`) — `EXIT=0`.** Строки `##` из
   `lab/logs/e0035-all.log`, дословно:
   * `## перебор 0..=4094: без паники 4095, несоответствий маски 0, неожиданных паник 0, различных
     выходов 64 ##`
   * `## перебор 4095..=65535: паник нет у 0 значений (первые []); первая паника зафиксирована на
     Some(4095); последний законный список — на Some(4094) ##`
   * `## время перебора 0.3 с ##`
   Контроль `cargo test -j 2 -p vecdht-crypto`: полностью зелёный (46 + 4 + 3 + 1 + 1 + 0).
   Справочный расчёт границы из того же лога (не замер): `base + 16` умещается при `s ≤ 4094`,
   `base` умещается при `s ≤ 4095`, без паники 4095 значений из 65 536.
3. **`clippy -D warnings` после прогона — 2 падения.** `useless_borrows_in_formatting` в строках 79
   и 95 (лишний `&` перед `no_panic.iter().copied().take(4|8).collect::<Vec<_>>()` внутри
   `eprintln!`/`assert!`). Убраны, `clippy -j 2 -p vecdht-crypto --all-targets -- -D warnings`
   дал `CLIPPY_EXIT=0`. Это правка форматирования аргументов печати, она не могла изменить
   поведение перебора, и поэтому порог не смягчается, а перебор снят заново.
4. **Повторный замер после lint-правки** (тот же лог, раздел «ДОПОЛНЕНИЕ ПОСЛЕ ПРОГОНА»): строки
   `##` совпали с прогоном 2 дословно, время — 0.2 с, `RERUN_EXIT=0`, контроль crypto снова
   полностью зелёный. Пороги нигде не переписывались задним числом.

## Результат

Порог | Заявлено до прогона | Снято | Итог
---|---|---|---
(1) нижнее множество | неожиданная паника = 0, несоответствий маске = 0, все списки длины 16 | `без паники 4095, несоответствий маски 0, неожиданных паник 0` (длина проверялась на каждом значении, попадание в `mismatches` означало бы провал) | выполнен
(2) верхнее множество | значений без паники = 0, первая паника ровно на 4095, последний живой номер ровно 4094 | `паник нет у 0 значений (первые [])`, `первая паника … Some(4095)`, `последний законный список … Some(4094)` | выполнен
(3) множество выходов | различных выходов на `0…4094` ровно 64 | `различных выходов 64` | выполнен

Фальсификаторы (а), (б), (в) не сработали ни один → `H-0035` подтверждается.

Содержательный итог: у `clusters_of_shard` ровно два исхода на всём входе `u16`. Ниже 4095 — молча
легальный список шарда `s mod 64` (чужой номер открывается чужим списком, это и есть маска из
`E-0034`, теперь на всех 4095 значениях, а не на пяти точках), от 4095 — паника арифметики `u16`
в debug. Никакого третьего поведения, ни одного «почти легального» или усечённого списка перебор не
нашёл: 65 536 входов порождают ровно 64 различных выхода, и все они — законные списки.

## Границы результата

* Профиль — `debug`. Для `release` заявлено заранее и не замерено: переполнение `u16` там кольцевое,
  поэтому верхнее множество должно вести себя не как авария, а как ещё один замаскированный список;
  это арифметическое рассуждение, а не результат этого прогона. Проверка отдельно
  предрегистрируется (`H-0036`/`E-0036`) — рука `E-0027` к моменту закрытия этого цикла
  завершилась, ядра свободны.
* Оракул вызывает функцию. Сеть в этом цикле не проверялась: что кадр с чужим номером шарда
  проходит декодирование и доходит до вызова — вопрос `E-0034`-а (а), он остаётся непроверенным
  (три из тринадцати сообщений с полем `shard` проверяют диапазон на декоде, `node.rs` сравнивает
  `!= self.shard`). Слово «уязвимость» здесь так же не употребляется, как в `E-0034`.
* Перебор покрывает вход `clusters_of_shard`, а не все места, куда номер шарда приходит извне:
  `shard_of_cluster`, `% SHARDS` в вызывающем коде и ceiling-проверки в `messages.rs` этим прогоном
  не измерены.
* Порог (3) доказывает полноту множества выходов только на нижнем множестве: входы выше 4094 в
  debug ничего не порождают, поэтому «64 выхода» — это не «всего 64 списка во всём мире», а
  «весь легальный образ функции исчерпан нижним множеством».
* Стоимость метода: 65 536 `catch_unwind` за 0.3 с — опасение из пре-регистрации («около шестидесяти
  тысяч unwind'ов может встать в разумное время») не реализовалось, перебор не минутный и не
  потребовал сокращения выборки.
