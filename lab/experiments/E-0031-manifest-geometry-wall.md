# E-0031 — стена стадии 1: валидатор манифеста, мёртвый потолок шардов и граница значения в кредашиале

## Гипотеза

См. `H-0031`.

## Стенд (правок измерительного гейта нет)

Новый тестовый файл `crates/vecdht-artifact/tests/geometry_wall.rs`; `vecdht-embed` (стенд гейта),
манифест-кодек и `check()` не правятся — тест только вызывает существующий публичный API
(`reference_manifest()`, `Manifest::check()`, `NodeCert::encode/decode`, `covers_shard`). Сетка
троек согласована (`nlist = clusters_per_shard · shards`) и ограничена `u16`; подмена геометрии
делается напрямую в поля `Routing` (все `pub`) — ровно так значение пришло бы из манифеста после
стадии 1. Сборка `-j 2`, потому что в это время из другого дерева идёт тяжёлая рука `E-0027`.

Классификация отказа берётся из варианта `ManifestError::CodecMismatch { field, expected, actual }`:
`field` называет проверку, которая сработала (в теле `check()` порядок фиксирован: `nlist` → `cps` →
`shards` → разбиение → … → потолок). Это даёт наблюдаемое «кто отверг», но не различает по строке
проверки 735 и 858, потому что обе требуют `= 64` — именно это и является пунктом (2).

## Прогон

Первая попытка — сразу зелёная (оракул писался после сверки API с кодом, а не по памяти;
компиляция 1,77 с, тест 0,03 с, `EXIT=0`). `base_commit dd352df`, дерево `dd352df`, debug, `-j 2`,
`RAYON_NUM_THREADS=2`; лог — `lab/logs/e0031-all.log`. Правок стенда после запуска нет, порог не
изменялся.

**Пункт (1)** — сетка из 36 согласованных троек (`cps ∈ {1,2,4,8,16,32}` × `shards ∈ {8,16,32,64,128,256}`,
`nlist = cps·shards`): прошла **1** — `nlist=1024 cps=16 shards=64`. Контроль стенда (эталонный
манифест проходит `check()`) пройден. Распределение отвергнувших полей:
`routing.nlist` — **32**, `routing.clusters_per_shard` — **3**, `routing.shards` — **0**,
отказов «не равенство константе» (то есть от проверки разбиения `:738` или иной) — **0**.
Фальсификаторы (а) и (г) не сработали.

**Пункт (2)** — `MAX_CERT_SHARDS = 64`, `SHARDS = 64` (совпадают числом, поэтому отказ ветки `:858`
и отказ `:735` наблюдением неразличимы: оба выдают `CodecMismatch` с `expected = 64`).
Прошедших манифестов с `shards > потолка` — **0**. Все 12 троек сетки, где `shards` перешагивает
потолок, отвергнуты более ранними равенствами (`routing.nlist` в 10 случаях,
`routing.clusters_per_shard` в двух). Различающий случай `nlist = 1024, cps = 8, shards = 128` (единственный, где `nlist` легален
и `shards > 64`) отвергнут проверкой `routing.clusters_per_shard` (кодек 16, манифест 8) — то есть
до ветки `:858` дело не доходит и там, где она была бы нужна. Фальсификатор (б) не сработал.

**Пункт (3)** — `NodeCert::decode` на списке из одного номера `= SHARDS` (64) отвергает:
`BadEnum { value: 64, what: "shard" }` при длине списка 1 (потолок длины `:86` тут ни при чём —
отказывает проверка значения `:92`). Последний легальный номер `[63]` проходит `encode → decode`,
`covers_shard(63) = true`, `covers_shard(64) = false`. Пустой список проходит `decode` и
`covers_shard()` даёт `true` и на `SHARDS`, и на `60 000`. Фальсификатор (в) не сработал.

**Контроль**: `cargo test -j 2 -p vecdht-artifact` — зелёный (37 + 4 (14,14 с) + 3 + 2, 0 failed).
Инвентарь (справочно): `SHARDS` — 53 сайта, `NLIST` — 66, `CLUSTERS_PER_SHARD` — 38,
`MAX_CERT_SHARDS` — 8 в нетестовом коде; сайты геометрии в `manifest.rs` — `725/726`, `728-732`,
`735/736`, `738-739`, `858-862`; граница номера шарда в кредашиале — `cert.rs:86` (длина), `:92`
(значение), `:128` (`covers_shard`).

## Результат

Порог выполнен по всем четырём пунктам: **(1) 1/36**, **(2) 0 манифестов выше потолка и
`MAX_CERT_SHARDS == SHARDS`**, **(3) значение 64 отвергнуто, 63 принят**, **(4) контроль стенда
зелёный**. `H-0031` подтверждена.

Что даёт прогон сверх пре-регистрации: в сетке **ни разу не сработала** проверка
`routing.shards != SHARDS` (`:735`) — её затеняют `:725` и `:728`. Валидатор формально содержит три
равенства константам, но независимы из них два: при `nlist == NLIST` и `cps == CLUSTERS_PER_SHARD`
сверка разбиения `:738` вынуждает `shards == NLIST / CLUSTERS_PER_SHARD == SHARDS`. Значит
минимальный набор правки стадии 1 в манифесте — **две** проверки (`:725`, `:728`) плюс **одна**
согласованность (`:738`, оставить), а `:735` и `:858` — проверки, которые после правки обязаны
стать ограничениями диапазона (или быть удалены как дубли): сегодня они не работают никогда.
Одновременно подтверждается практическое следствие: ось `shards` для роста `nlist` закрыта трижды
(равенство `:735`, ветка `:858`, значения шардов в кредашиале `cert.rs:92`), остаётся ось
`clusters_per_shard` — та, на которой `E-0030` измерил расхождение двух карт на 1016 кластерах из
1024 и которую `E-0030` же показал живущей в пути `Agent::find`.

## Границы результата

Манифест рождается в `check()`, а не в парсере: `Routing::from_json` (`manifest.rs:404-406`)
пропускает любые значения в диапазоне `1..=u16::MAX`, так что «манифест можно написать другой
геометрией» — верно, и отвергается он только на валидации; этот прогон измерял именно `check()`.
Пороги сети, recall и байты кадров здесь не измерялись: вывод касается только допуска значений.
Ветка «удалить `:735`/`:858` и поднять `SHARDS`» не проверена — при подъёме константы `SHARDS`
потолок `MAX_CERT_SHARDS` обязан перестать совпадать с ним числом, и ни один существующий тест этого
не требует (в этом и состоит находка пункта (2)). Класс (H) в части `crypto/quant.rs:164-165`
(`u16`-переполнение при больших геометриях) по-прежнему не измерен: оракул работал на диапазоне
троек, а не на арифметике отображения. Открытым остаётся и §14.4 (iv) — отсутствие per-cluster
admission cap (§20.2, строка 4), для него нужен тяжёлый прогон, а он заблокирован идущей
цепочкой `E-0027`.
