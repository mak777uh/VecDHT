# ADR-0011 — §12.3 и гейт §18.6 переписаны констатацией: расход приёма — API
# встраивателя; кадра предъявления в v8 нет, живой узел `Spend` не зовёт

## Контекст

Пять измеренных фактов (`E-0045`, единый прогон, все секции `EXIT=0`):

1. в продуктовом `src/` вызовов `Spend`/`consume` нет: `node.rs` и `session.rs` — ноль
   вхождений, `agent.rs` — единственное вхождение является докс-комментарием
   («та же граница, что у `Spend::consume` в узле», `agent.rs:267`); тип живёт в
   `rendezvous.rs` и ре-экспорте `lib.rs:55`;
2. `IntentTextRequest` несёт ровно `query_id: u64, target_ed25519: [u8;32], slot: u32`
   (`messages.rs:470–474`): поля для приёма/кадра приёма нет — предъявить его протокольно
   нечем;
3. relay-путь узла документированно не принимает `IntentText*` и `RendezvousAccept`
   (`node.rs:1397–1398`, §4.3) — на узле-издателе расход физически невозможен, а узел-цель
   таких кадров не разбирает;
4. поведение (`accept_presentation_api_only`): корректно адресованный запрос **без**
   приёма проходит `session::parse_request` → `Ok`, `sign_response`/`verify_response`
   отдают текст; единственный фильтр стороны цели — адресат (`WrongTarget`); при этом
   библиотека исправна: `Spend::consume` того же кадра — `Ok`, затем `Err(AlreadySpent)`;
5. `check_accept_policy` в `vecdht-net` проверяет приём **seeker'ом** перед предъявлением
   — это не расход целью и подотчётность цели не обеспечивает.

Семейство: третья фикция (`E-0042`, denylist) была «подотчётность без пути внесения»;
здесь — «подотчётность без пути предъявления»: обещание §12.3 «цель … проверяет
одноразовость расхода» и гейта §18.6 «rendezvous-приём проверяется целью и одноразовый»
невыполнимы штатным путём v1. Выпуск приёма при этом верен спеке целиком — это
подтверждено соседним `E-0044` (идемпотентность, потолок, graceful degradation).

## Решение

1. §12.3, абзац про предъявление: переписан констатацией — «в v8 нет кадра предъявления,
   `IntentTextRequest` несёт только `query_id/target_ed25519/slot`; полный набор проверок
   реализован в экспортируемом `Spend::consume`, который вызывает встраиватель; живой узел
   приём не принимает и расхода не делает (`E-0045`, `ADR-0011`)»; порядок проверок, ключ
   расхода и арифметика границы (`now = issued + ceil(ttl/16)`) оставлены без изменения —
   они истинны про тип;
2. гейт §18.6 (строка «rendezvous-приём проверяется целью и одноразовый»): переформулирован
   — выпуск идемпотентен с потолком (`E-0044`), расход — API встраивателя (`E-0045`);
3. сводная anti-replay-строка §14.3: «одноразовость `RendezvousAccept»» уточнена до
   «идемпотентность и потолок выпуска» + «расход — `Spend` как API встраивателя»;
4. зеркало `%USERPROFILE%\OneDrive\Desktop\VecDHT-SPEC-v8.md` синхронно, сверка строк
   побайтовая (TEXT_SYNC_OK);
5. гейты чисел не тронуты: пороги sybil-гейта §18.6 (≤ 64 000 записей, p50) остаются,
   ослабления формулировки «не больше» нет — меняется только утверждение о механизме,
   которого в коде нет.

## Открытое (owner-решение)

v1-минимум: либо завести кадр предъявления + вызов `Spend` в обработчике цели (тогда
гейт §18.6 возвращается к исходной формулировке), либо перенос расходной части в v2 —
по образцу `ADR-0009` (denylist) и `ADR-0010` (дедуп `query_id`). До решения владельца
спека фиксирует факт, а не намерение.
