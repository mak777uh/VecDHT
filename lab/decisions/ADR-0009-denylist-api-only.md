# ADR-0009 — подотчётность §11.4 (ii) переписана констатацией: denylist в v1 только API,
# ни наблюдения атаки, ни интерфейса узла, ни persistence у него нет

## Контекст

Спека (§11.4 (ii), §14.4 (3)) перечисляла denylist одной из трёх защит sybil-стойкости:
«узел может внести ключ в denylist после наблюдения атаки, и запрет переживает смену
эпизоды». `E-0042` измерил все три звена этой цепочки на живом узле:

1. «внести» могут только тесты: продуктовых вызовов `deny()`/`undeny()` во всех crates —
   ноль (инвентарь 4а); бинаря узла и wire-сообщения для списка нет (4б) — вызыватель
   возможен только при встраивании библиотеки;
2. «наблюдения атаки» не существует: кода, который хоть что-то решает по наблюдениям и
   вызывает список, нет ни в `node.rs`, ни в индексе (4б);
3. «переживает» истинно ровно в одном прочтении и ложно в другом: в живом процессе список
   не чистит ни одна операция (4в, и путь применения `MembershipUpdate` его не трогает),
   но при повторном открытии того же каталога цепочка членства и lease поднимаются с диска
   (`epoch()==Some(1)`), а denylist — пуст (`denylist_len()==0`), и внесённый «до» ключ
   больше не встречает `DENIED` на проводе (фактический код — `EPOCH_STALE`).

Это третья зафиксированная спека-фикция того же семейства: потолок кластеров на кадр
(`a9ef39c`), очередь `Find` с ограничением по времени (`E-0041`/`ADR-0008`), теперь —
denylist-подотчётность. Как и в двух предыдущих случаях, код менять нечем: реализуемая
часть (политика `Denied` в `check_publish`/`check_find`, идемпотентный `deny`, счётчик)
уже есть и работает — дыра только в тексте, который обещает автоматический и переживающий
механизм.

## Решение

Переписать §11.4 (ii) и §14.4 (3) констатацией измеряемого: подпись автора — есть; denylist —
API встраивателя (`Admission::deny`), без наблюдения атаки, без интерфейса узла, RAM-only,
переживает ротацию состава в живом процессе, не переживает перезапуск; ссылки на `E-0042` и
этот ADR. Строка «отзыв кредашиала» в §14.4 (3) убрана: кредашиала в v8 нет (та же спека,
§11.4: identity бесплатна). Таблица решений §20 (строка 5) остаётся исторической записью —
правки в реестре принятых решений задним числом хуже отдельного ADR.

Реализацию «наблюдения атаки» (порог, сигнал, интерфейс оператора) и persistence списка этот
ADR не вводит и не отменяет: это открытые вопросы v2, теперь — честно помеченные как
отсутствующие, а не присутствующие.

## Последствия

- Защита (ii) не участвует в рассуждениях о sybil-стойкости v1: реальные механизмы — (i) evict
  по `pow_bits` и (iii) клиентская cross-validation; оператор, читающий старую редакцию, не
  мог ожидать, что внесённый вручную запрет исчезнет при следующем старте узла.
- Для `E-0039` (нет узлового бюджета на чтение) это тот же сюжет: обещанный потолок существует
  на бумаге раньше, чем в коде; различие в том, что там потолок был у записи, а здесь — у
  подотчётности.
- Открытым остаётся решение владельца: вводить ли v1-минимум (например, чтение списка
  denylist'ов из конфига при старте — копейки кода против «переживает перезапуск») или
  перенести весь пункт в v2. Измерять цену можно будет после этого решения, не раньше.

## Альтернативы, отвергнутые

- *Молча оставить текст*: фикция того же класса уже дважды вела к неправильным рассуждениям о
  защите (cap, очередь); третий случай без правки — паттерн, а не редкость.
- *Реализовать persistence как часть закрытия замера*: смешивает измерение и фичу; правка
  текста без кода оставляла бы вопрос owner-решения открытым, поэтому он вынесен в
  «Последствия», а не сделан.
