# ADR-0013 — v1-минимум предъявления: поле `present` в `IntentTextRequest` и обязательный вход `serve_request`

status: accepted
date: 2026-10-22
relates: [E-0045, E-0046, E-0050, ADR-0011, ADR-0012, E-0051]

## Контекст

`E-0045` зафиксировал фикцию: «агент обязан показать приём цели — предъявить нечем»,
`ADR-0011` перенёс решение о v1-минимуме на владельца. `E-0050` добавил аргумент: приёмы
выпускает любой держатель шарда (роль не гейтана), а `E-0046`/`E-0050` — что приём
переживает потерю таблицы издателем; без предъявления вся эта машина одноразовости
никто не вызывает. Владелец решил: реализовывать (формулировка цикла 2026-10-22).

## Решение

Минимальный протокольный шаг, не трогающий числовые гейты §18.6:

1. `IntentTextRequest` получает поле `present: Vec<u8>` — полный байтовый подписанный
   кадр `RendezvousAccept`, лимит 512 Б (фактический кадр ~148 Б: тело 76 + заголовок 8 +
   подпись 64); пустое значение разборим, но не обслуживается.
2. Единственный правильный путь обслуживания на стороне цели —
   `session::serve_request(frame, me, issuers, now_bucket, &mut Spend)`: разбор →
   `NoAccept` при пустом `present` → `Spend::consume` по списку кандидатов-держателей
   (перебор только по `BadSignature`; `AlreadySpent`/`Expired`/`WrongTarget`/
   `TtlOutOfPolicy` отсекаются немедленно, как и в библиотеке) → `Ok(Grant)` — и только
   тогда цель считает запрос предъявленным. Ни один живой узел текст не носит (§12.4),
   поэтому принуждение живёт в API входа цели, а не в маршрутизации — это и есть
   «v1-минимум» из `ADR-0011`, честно ограниченный библиотекой встраивателя.
3. Совместимость: `encode_request`/`parse_request` сохраняются (разбор без обслуживания),
   закрытые оракулы `E-0045` не переписываются — к их доку добавляется аддендум, что
   фикция закрыта на уровне входа обслуживания, а не разбора.
4. Домен сообщения `b"vecdht/v8/text_req"` не меняется: v8 — неопубликованный черновик,
   смена формата без смены доменной строки уже практиковалась (`ADR-0011`).

Правка спеки: §12.3 (абзац «Агент обязан показать приём…») и сводная строка §19.1-гейта,
где было «кадра предъявления в v1 нет»; зеркало в том же коммите, TEXT_SYNC_OK.

## Открытое

Связка «ответ цели привязан к предъявленному приёму» (digest приёма внутри
`IntentTextResponse`) в этот минимум не входит — без неё seeker не может отличить
обслуженный запрос от другого; это кандидат ADR-0014 после измерения оверхеда `E-0051`.
