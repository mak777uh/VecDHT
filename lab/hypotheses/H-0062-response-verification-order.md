# H-0062 — порядок проверок `session::verify_response` (§12.4) и немедленные отказы входа цели (§12.3): `WrongKind`/`Malformed` как первая пара, лимит текста ищется по имени отказа

## Наблюдение

Спека §12.4 называет последовательность ЯВНО: «Ответ принимается только после проверки
вида кадра, наличия подписи, `owner_ed25519 == ожидаемого владельца`, подписи по ключу
владельца и UTF-8; лимит 1000 байт проверяется и при подписании, и при разборе». Код
повторяет её в docstring (`session.rs:163`): «вид кадра → наличие подписи → разбор тела →
ожидаемый владелец → подпись → UTF-8» с мотивировкой «Владелец сверяется до криптографии
намеренно: подпись чужого ключа не должна даже считаться, и ошибка обязана называть
источник, а не "подпись не сошлась"».

Ни одно из этих утверждений о ПОРЯДКЕ не измерялось: grep по `crates/*/tests/` даёт НОЛЬ
`TextError::WrongKind` и НОЛЬ `TextError::Malformed` (это первые две ветки пути), а
`Unsigned`/`BadSignature`/`WrongOwner`/`NotUtf8`/`TextTooLong` покрыты по одному факту без
различающих комбинаций (`session.rs` юнит-тесты, `adversarial.rs:338-360`). Отдельно:
сверхлимитный текст на разборе покрыт юнит-тестом кодека (`intent_text_over_limit_rejected`
→ `DecodeError::FieldTooLong`), но как он именуется на выходе `verify_response` не мерялось —
по коду это `Malformed` (`session.rs:175`), а собственная ветка `TextTooLong` в
`verify_response` (`session.rs:189`) — симметричный повтор, который не может сработать,
потому что декодер поля отсекает раньше.

На живом входе цели (`serve_request`) порядок тоже назван спекой («разбор → `NoAccept` при
пустом `present` → `Spend::consume` по списку держателей… перебор кандидатов только по
`BadSignature`; `AlreadySpent`/`Expired`/`WrongTarget`/`TtlOutOfPolicy` отсекаются
немедленно»), но измерялись только положительные ветки и `AlreadySpent`/`NotSignedByShardHolder`
(`E-0051`, `E-0054`): не мерилось, что немедленные отказы `consume` (`Malformed`, `WrongKind`)
проходят НАРУЖУ как `TextError::Spend(...)`, а не маскируются в `NotSignedByShardHolder`, и
что адресат сверяется раньше требования предъявления.

## Гипотеза (операционализируемое ядро)

O — ключ издателя ответа, E — чужой ключ, F — третий ключ; живой приём F0 от одиночного
primary (ttl=300). Пороги заморожены (полный текст — docstring оракула
`crates/vecdht-node/tests/response_verification_order.rs`):

| Шаг | Утверждение (порог) |
|---|---|
| (0) | честный кадр: `flags == 0x0001`, длина `8 + тело + 1 + 64`, байт `sig_len == 64`; `verify_response(_, &O)` → `Ok` с полями (O, «гранит», 7, «abcdef») |
| (1) | вид := `IntentTextRequest` при честном теле и честной подписи → `WrongKind`; тот же чужой вид БЕЗ подписи → `WrongKind` (вид раньше наличия подписи) |
| (2) | вид := 0xFE (нет в таблице §5.3) → `Malformed`, а не `WrongKind` |
| (3) | кадр усечён на 1 байт → `Malformed` |
| (4) | байт `sig_len` := 63 → `Malformed`, а не `Unsigned` |
| (5) | `encode_unsigned` → `Unsigned`; ложный `owner_ed25519` + отсутствие подписи → `Unsigned` (наличие подписи раньше владельца) |
| (6) | честный кадр O при ожидаемом E → `WrongOwner{expected: E, found: O}`; тот же кадр с инвертированным байтом текста при ожидаемом E → `WrongOwner`, а не `BadSignature` |
| (7) | честное тело O, подпись ключом F, ожидаемый O → `BadSignature` |
| (8) | текст 1001 байт с честной подписью O, ожидаемый O → `Malformed`, а НЕ `TextTooLong` |
| (9) | те же 1001 байт при ожидаемом E → `Malformed` (разбор тела раньше владельца) |
| (10) | `sign_response` с 1001 байтом → `TextTooLong(1001)` |
| (11) | запрос с пустым `present`, адресованный не этой цели → `WrongTarget`, а не `NoAccept` |
| (12) | `present` = 8 нулей (не кадр) → `Spend(Malformed)`, а не `NotSignedByShardHolder` |
| (13) | `present` = живой кадр с байтом вида := `Publish` (табличный чужой вид, в пределах лимита 512 Б) → `Spend(WrongKind)` |
| (14) | пустой `present` при верном адресате → `NoAccept` |
| (15) | живой приём предъявлен → `Ok`, `spent == 1`; повтор → `Spend(AlreadySpent)`; во всех (11)…(14) `spent == 0` |

Различающее ядро — (6)/(9): если бы подпись проверялась до сверки владельца, кадр с
испорченным текстом и чужим ожидаемым ключом дал бы `BadSignature`, а гипотеза (и код, и
спека) обещает `WrongOwner`; если бы владелец проверялся до разбора тела, сверхлимитный
текст дал бы `WrongOwner`, а не `Malformed`. Различающее имя отказа — (8) против (10): то же
число 1001 на двух концах зовётся по-разному, и это фиксирует, какой из двух гейтов живой.
Различающее на входе — (12)/(13): маскировка немедленного отказа в `NotSignedByShardHolder`
были бы нарушением §12.3 («перебор кандидатов только по `BadSignature`»).

## Фальсификаторы

(а) (1) дал `Unsigned`/`BadSignature` — вид кадра проверяется после подписи (порядок §12.4
нарушен);
(б) (2)/(3)/(4) дали не `Malformed` — заголовочные гейты пропущены;
(в) (5) с ложным владельцем дал `WrongOwner` — владелец раньше наличия подписи;
(г) (6) с испорченным текстом дал `BadSignature` — подпись чужого ключа всё-таки считается;
(д) (8) вернул `Ok` или `TextTooLong` — лимита на разборе нет либо он именуется иначе;
(е) (9) дал `WrongOwner` — владелец проверяется до разбора тела;
(ж) (12)/(13) дали `NotSignedByShardHolder` — немедленный отказ замаскирован перебором;
(з) (11) дал `NoAccept` — требование предъявления раньше адресата;
(и) (0)/(15) `IntentText`/`Grant` не связаны с полями честного кадра;
(й) `spent > 0` после (11)…(14) — отказ с побочным эффектом.

## Скоуп и границы замера

Меряются две экспортируемые функции цели/получателя (`verify_response`, `serve_request`) на
кадрах, полученных мутацией честных байтов; подделка подписи чужим ключом — одна ветка (7),
стойкость Ed25519 — территория `adversarial.rs`. Лимит 512 Б на `present` не измеряется (он
покрыт `present_serving_gate.rs`, порог (6)); фикстура для (13) сознательно выбрана так, чтобы
поместиться в лимит, — иначе отказом был бы разбор запроса, а не расход. `TextError::Structured`
и `Markup`/`LineBreak`/`Control`/`Empty`/`TooLong` относятся к разметке текста и не относятся к
этому порядку. Часы (`now_bucket = 0`) не двигаются — урок `E-0060`.

## Вердикт (2026-10-22, append)

Подтверждена ПЕРВЫМ замером (rev `bac964f`, 16:29; `E-0062`): пороги (0)…(15) совпали,
фальсификаторы (а)…(й) молчат, ДИАГНОЗ и поправка заморозки не понадобились. Порядок
§12.4 жив и различим по имени отказа на каждом шаге: вид раньше подписи (`WrongKind` на
подписанном и без-подписном чужом виде), заголовочные гейты раньше всего (`0xFE`/усечение/
`sig_len` 63 → `Malformed`), наличие подписи раньше владельца (ложный владелец без подписи
→ `Unsigned`), разбор тела раньше владельца (1001 байт при чужом ожидаемом → `Malformed`),
владелец раньше криптографии (испорченный текст при ложном ожидаемом → `WrongOwner`, не
`BadSignature`). Лимит на двух концах зовётся по-разному: `Malformed` на разборе против
`TextTooLong(1001)` на подписании — ветка `TextTooLong` в `verify_response` подтверждена
мёртвым повтором. На входе цели немедленные отказы `consume` (`Spend(Malformed)`,
`Spend(WrongKind)`) проходят наружу без маскировки в `NotSignedByShardHolder` (§12.3
«перебор кандидатов только по `BadSignature`» подтверждён в обе стороны), адресат раньше
предъявления (`WrongTarget`, не `NoAccept`), `spent == 0` после всех отказов. Шестнадцатое
подтверждение §12.3 подряд. Правка спеки не нужна: расхождения спека↔код не обнаружено.
Оговорка покрытия: различающие вторые клаузы порогов (5)/(6) ассертятся оракулом, базовые
первые клаузы — существующими юнит-тестами `session.rs` (те же ветки `:171`/`:176`);
замороженная формулировка не перенормировалась. Верификация 568 ok / clippy 0.
