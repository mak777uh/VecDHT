## Вопрос

§15 обещает порог авторитета 3-of-5 на трёх дверях: подпись артефакта (§15.1),
`NodeCert` (§4.2) и genesis-членство (§9.2, §15.2). Юнит-тесты каждой двери уже есть
(`threshold_signature_round_trip`, `foreign_authority_key_does_not_count`,
`genesis_needs_the_authority_threshold_and_nothing_else`, `one_signature_short_is_rejected`,
`duplicate_signature_from_same_key_does_not_reach_threshold`). Лабораторно не мерялся
**шов между дверями** — то, что нельзя увидеть изнутри одной двери:

1. `MembershipUpdate.sigs` — единственное место, где подпись несёт индекс, и §9.2
   (строка 969) задаёт его смысл: «позиция подписанта в наборе epoch−1 (для genesis —
   порядок ключей в `authorities` артефакта)». Для перехода `check_members` связывает
   индекс с ключом. Для genesis `check_authorities` вызывает только
   `check_indices` (диапазон + уникальность) и `count_valid` (подпись против **любого**
   ключа) — то есть индекс для genesis не проверяется вообще. Гипотеза-находка:
   genesis принимает подпись, заявленную под чужим индексом, и подписантами по индексам
   окажутся авторитеты, которые не подписывали.
2. Порог genesis берётся из `Params.authority_threshold`, а порог `NodeCert` — из
   `AuthoritySet.threshold`. `ShardNode::open` принимает обе структуры и не сверяет их.
   Через штатный `Params::from_manifest` они совпадают; через публичный `open` —
   могут не совпадать. Гипотеза-находка: узел, открытый с `authority_threshold=2` и
   3-of-5 набором, принимает genesis с двумя подписями.
3. Домены (`vecdht/v8/member`, `vecdht/v8/node_cert`, `vecdht/v8/artifact`) обязаны
   разделять двери: подпись одной двери не должна засчитываться на другой. Это
   проверяется не «на глаз», а подстановкой подписей между дверями.

## Разведка (до пре-регистрации)

* `Chain::check_authorities` (`membership.rs:206`): `check_indices(sigs, n)` — только
  `idx < n` и уникальность; затем `count_valid(payload, domain::MEMBER, &list)`.
  `AuthoritySet::count_valid` (`cert.rs:57`) для каждого ключа проверяет, есть ли
  **хоть одна** подпись из списка; индекс не участвует.
* `Chain::check_members` (`membership.rs:231`): для каждой пары `(idx, sig)` ключ берётся
  ровно `prev.members()[idx]` — привязка индекса к ключу. Асимметрия с genesis видна
  в одном файле.
* `Chain::validate` (`membership.rs:133`): `prev=None` ⇒ только genesis
  (`epoch == GENESIS_EPOCH`, непустой состав, `check_authorities`); `prev=Some` ⇒
  `epoch == prev+1` и `check_members`.
* `Params.authority_threshold` (`config.rs:106`) заполняется из
  `manifest.authority.threshold` (`config.rs:227`); `AuthoritySet` собирается из тех же
  `manifest.authority.keys/threshold` (`artifact/src/lib.rs:103`). В `ShardNode::open`
  (`node.rs:149/171`) обе структуры кладутся в `Chain` без сверки.
* `verify_cert` (`cert.rs:143`) использует `authorities.threshold`; `Artifact::verify`
  (`artifact/src/lib.rs:140`) — `manifest.authority.threshold`.
* Домены: `messages::domain::MEMBER = b"vecdht/v8/member"`, `DOMAIN_NODE_CERT =
  b"vecdht/v8/node_cert"`, `DOMAIN_ARTIFACT = b"vecdht/v8/artifact"`.
* `testing::genesis_update` (`testing.rs:160`) подписывает первыми
  `authority_set().threshold = 3` ключами с их настоящими индексами;
  `testing::node_cert` (`testing.rs:95`) — те же три ключа доменом `node_cert`.
* Манифест принимает `authority.threshold` из `1..=16` при
  `threshold ≤ keys.len()` (`manifest.rs:581`, `manifest.rs:828`); константы «3» в коде
  нет — 3-of-5 живёт в эталонном манифесте и в тексте спеки. Это не меняется этим
  циклом; фиксируется как граница.
* `MembershipUpdate` — единственная структура порога с индексами; у `NodeCert` и
  манифеста подписи — `Vec<[u8;64]>` без индексов.

## Замороженные пороги (до первого прогона)

Оракул `crates/vecdht-node/tests/s15_authority_seam.rs`, один процесс, каталоги
`vecdht-index-*`. Шард 7, PoW 8, сиды 1..=3 (тройка из E-0073/E-0074), `r=3`, `w=2`,
`membership_threshold=2`, `authority_threshold=3`, эталонный `AuthoritySet` 3-of-5.
Чужой ключ — seed 200. Кадр genesis несёт подпись первого тела (`testing::signed_frame`),
доставка вручную.

| # | Предсказание |
|---|---|
| (0) | База: `chain.validate(None, genesis)` → эпоха 1, 3 члена, primary — первый член; живой узел из тройки после genesis имеет `epoch()=Some(1)`, `is_member=true`, файл `membership.00000000000000000001.log`; повторное открытие по тому же каталогу даёт эпоху 1. Две другие двери с теми же ключами открыты: `verify_cert(node_cert(…), authority_set, genesis_hash, 100, no_revoke) = Ok(())`; `reference_manifest().authority.threshold = 3` при 5 ключах |
| (1) | Порог 3-of-5 точен и не ослаблен: при 1 подписи — `BelowThreshold{1,3}`, при 2 — `{2,3}`, при 3 — `Ok`; 2 подписи авторитетов + подпись seed 200 под свободным индексом 3 → `{2,3}`; три копии одной подписи авторитета под индексами 0,1,2 → `{1,3}`. Живой узел: 2-подписный genesis → `epoch()=None`, файла членства нет, `out` пуст; тот же узел после доставки 3-подписного того же тела → эпоха 1 (черновик слился, порог добрался) |
| (2) | Genesis принимает чужой индекс: подписи авторитетов 0,1,2 с заявленными индексами 2,3,4 (уникальны, `<5`) → `validate` = `Ok`, эпоха 1; живой узел принимает, файл членства несёт ровно индексы `[2,3,4]` и 3 подписи; при этом подпись под индексом 2 не проверяется ключом 2, под 3 — ключом 3, под 4 — ключом 4 (все — `false`), а ключами 0,1,2 — `true`. То есть индекс в genesis — метка без силы, тогда как §9.2 называет его позицией подписанта |
| (3) | Асимметрия перехода: тот же приём на эпохе 1→2 отвергается — три подписи членов эпохи 1 под индексами 1,2,0 дают `BelowThreshold{0,2}` (каждая подпись верна своему ключу, но не ключу заявленного индекса); живой узел остаётся на эпохе 1, файла эпохи 2 нет, возвращает ровно 2 конверта черновика. Исправленный переход того же состава с настоящими индексами 0,1 (и другим `generated_at`, чтобы не слиться с черновиком) принимается: эпоха 2, файл эпохи 2 есть, primary — первый член эпохи 2 |
| (4) | Двери не одалживают подписи: genesis-тело, подписанное теми же тремя ключами доменом `node_cert`, — `BelowThreshold{0,3}`; доменом `artifact` — `{0,3}`; подписи валидного `NodeCert` (3-of-5), вставленные в genesis, — `{0,3}`; подписи genesis, вставленные в `NodeCert`, — `CertError::BelowThreshold{0,3}`. При этом каждая дверь со своей подписью открывается: `verify_cert` = `Ok(())`, genesis = `Ok(3)` |
| (5) | Порог живёт в двух руках: `Chain{params: authority_threshold=2, authorities: 3-of-5}.validate(None, genesis с 2 подписями)` = `Ok(2)`; тот же список подписей через `AuthoritySet::check` = `BelowThreshold{2,3}` — две двери расходятся на одних байтах. Живой узел, открытый `ShardNode::open` с `params.authority_threshold=2` и `testing::authority_set()` (3-of-5), принимает 2-подписный genesis (эпоха 1, файл членства есть); узел, открытый штатными `testing::params` (порог 3), тот же кадр не принимает (`epoch()=None`) |
| (6) | Инвентарь: `check_authorities` не использует индекс подписи; `check_members` использует; `check_indices` — только диапазон и уникальность; `count_valid` дедуплицирует по ключу; `ShardNode::open` не сверяет `params.authority_threshold` с `authorities.threshold`; `Params::from_manifest` копирует порог из манифеста; `verify_cert` берёт `AuthoritySet.threshold`; `Artifact::verify` — манифестный; §9.2 строка 969, §15.1 строка 1419, §15.2 строка 1446; в коде нет константы 3 для авторитета; `git diff HEAD --stat -- crates/vecdht-wire` пуст; `git diff HEAD --stat -- docs/VecDHT-SPEC-v8.md` пуст; юнит-тесты дверей на месте и не переписывались |

## Фальсификаторы

- (а) 3-подписный genesis не принимается живым узлом или не персистится — (0) падает;
- (б) точные имена/числа отказов (1) другие — (1) падает;
- (в) 2-подписный genesis открывает шард на штатном узле — (1) падает;
- (г) подпись seed 200 или три копии одной подписи добирают порог — (1) падает;
- (д) genesis с индексами 2,3,4 отвергнут — (2) падает (находка опровергнута);
- (е) живой узел не принял genesis с чужим индексом или в файле другие индексы — (2) падает;
- (ж) переход с индексами 1,2,0 принят или исправленный переход не принят — (3) падает;
- (з) подпись чужой двери засчитывается или своя не засчитывается — (4) падает;
- (и) узел с `authority_threshold=2` не принимает 2 подписи, а штатный принимает — (5) падает;
- (к) `on_frame` вернул `Err` там, где предсказан `Ok`; в wire появился новый `Kind`/поле; спека или код изменены этим циклом — замер недействителен.

## Что это не доказывает

Один шард, один процесс, ручная доставка; транспорт не аутентифицирует `from`, поэтому
подмена индекса здесь — свойство **валидатора**, а не захват канала. Не меряется:
ротация набора авторитетов (в v1 не определена, §15.2/§20), `authority.threshold ≠ 3`
в подписанном манифесте (это политика сети, а не баг парсера), genesis с порогом из
манифеста 1..=16, отзыв кредашиала в цепочке, артефакт с чужими центроидами, несколько
шардов и повторный genesis после потери всего состава (§9.5 строка 11). Индексная
метка в genesis не даёт подделать подпись: без 3 настоящих ключей порог не берётся —
это и проверяет (1). Цена/последствия неверной атрибуции (кто «подписал» genesis в
аудите) не измеряются количественно.

## Вердикт

Подтверждена `E-0075` (2026-10-23, `5 passed; 0 failed`, пороги (0)…(6) совпали с первого
прогона). Обе гипотезы-находки подтвердились, обе — о шве, а не о дыре в целостности:

* **Индекс genesis не атрибутируется** (§9.2 строка 969 обещает «позицию подписанта в
  наборе `authorities`»): подписи авторов 0,1,2 под заявленными индексами 2,3,4 принимаются
  как genesis, и в персистентное членство ложится ровно `[2, 3, 4]`. Тот же приём на
  переходе 1→2 отвергается (`have = 0`) — `check_members` индекс связывает,
  `check_authorities` — нет. Это двенадцатая спека-фикция семейства.
* **Порог живёт в двух руках:** genesis спрашивает `Params.authority_threshold`,
  `NodeCert` — `AuthoritySet.threshold`, а `ShardNode::open` их не сверяет. На одних и тех
  же байтах genesis принят при пороге 2, `NodeCert` отвергнут (`{2,3}`). Штатный путь
  (`Params::from_manifest`) расхождение исключает; публичный `open` — нет.

Пороги не ослаблены: чужая доля и переупаковка одной подписи в три индекса порог не
добирают, домены `member`/`node_cert`/`artifact` подписями друг друга не кормятся.
Кандидаты `ADR-0022` (привязка индекса genesis к ключу) и `ADR-0023` (сверка порогов в
`open`) вынесены в `OPEN-QUESTIONS` п. 12–13; правки спеки и кода без слова владельца
не производятся.

Поправка заморозки (append, 2026-10-23): **пороги не менялись.** ДИАГНОЗ-1 — оракул не был
прогнан через `clippy --all-targets -- -D warnings` до коммита пре-регистрации (пропуск
процедуры, а не дефект замера): правка синтаксическая (`for i in 0..3` → `enumerate().take(3)`),
повторный прогон идентичен — 5 passed, 0 failed. Подробности и номера верификации — в
`E-0075`.
