# H-0028 — отсутствие валидатора диапазона на `MatchResult.shard` и `RendezvousAccept.shard`,
# найденное `E-0028`, не является дырой допуска: эти поля не читает ни один путь обработки,
# и стадия 1 обязана добавить им валидатор только вместе с первым читателем

## Гипотеза

`E-0028` измерил (пункт 2-а), что скалярный валидатор `shard >= SHARDS` стоит на
`SnapshotOffer` (`messages.rs:728`), `LeaseGrant` (`:664`) и `ReplicateAck` (`:801`), но его нет
на `MatchResult.shard` и `RendezvousAccept.shard`: кадры с `shard = 4095` декодируются без отказа.
Таблица класса (B) в `H-0027` приписывала строку `:664` кадру `RendezvousAccept` — это ошибка
инвентаря, а не свойства кода.

Дальше спека не утверждает всеобщей проверки: в `docs/VecDHT-SPEC-v8.md` `SHARDS` встречается только
в определении константы (`:477`) и в таблице чисел (`:1867`), ни одного требования «всякий поля
`shard` валидируется на декоде» там нет. Значит расхождение — код-внутреннее, и вопрос не «править
ли спеку», а «опасно ли молчаливое принятие».

Утверждение (проверяемое ядро): **поле `shard` в этих двух кадрах — мёртвое для управления
потоком**: путь обработки агента выбирает запись по `query_id` и по совпадению пира, а в
`verify_match_result` номер шарда передаётся локальным (`entry.shard`), не из кадра; кадр
`RendezvousAccept` узел только порождает, а принимает через тот же `_ => Ok(Vec::new())`, что
`ArtifactAnnounce` (`node.rs:1397`). Поэтому внедиапазонное значение не может ни провести чужой
результат, ни сместить роутинг: оно попадает лишь в байты, над которыми считается подпись
(то есть подделывает только того, кто сам её ставит), а на исход пути не влияет.

Следствие для стадии 1: добавлять валидатор диапазона к этим двум полям сейчас — правка без
читателя, то есть чисто косметическая и потенциально ломающая (ужесточение декода — смена
поведения для уже валидных по спеке кадров). Его вносят вместе с первым кодом, который начнёт
поле читать (потребитель `ArtifactAnnounce` и роутинг по геометрии — `E-0029+`).

## Фальсификатор

Достаточно одного пункта:

- **(а)** хотя бы один нетестовый читатель `res.shard` (поля декодированного `MatchResult`) или
  `.shard` принятого `RendezvousAccept` существует в `vecdht-net`/`vecdht-node`/`vecdht-index` —
  тогда дыра допуска реальна (или молчаливое расхождение роутинга), и фикс обязателен ДО стадии 1;
- **(б)**`verify_match_result` сверяет подпись по байтам, которые пересобираются из локального
  знания о шарде, а не по байтам кадра — тогда расхождение поля влияет на канон подписи, и
  вывод «поле мёртвое» неверен;
- **(в)**spec всё-таки требует проверки (строка с нормативным «обязан отвергнуть вне диапазона») —
  тогда это расхождение кода со спекой и нужен ADR, а не hypothesis.

## Оракул

Лёгкий, без сборки и без конкуренции с тяжёлой цепочкой `E-0027` (в этот момент из другого дерева
идёт `p0_real_corpus`): `lab/e0029-run.sh` — три grep-измерения по нетестовому коду, каждое
печатает найденные строки целиком, чтобы классификация (чтение значения против записи в лог/отчёт)
была видна в логе, а не выведена из числа:

1. чтения `.shard` у декодированного `MatchResult` в `agent.rs`/`node*.rs` (поимённо, с контекстом);
2. кто принимает `Kind::RendezvousAccept` на стороне узла и читает ли поле;
3. все места, где `verify_match_result` получает номер шарда (источник аргумента: локальный или из кадра).

Порог (фиксируется до прогона): успех — (1) ноль чтений значения по поля, влияющих на поток
управления (допускаются вхождения в строках отчётов/ошибок, каждое перечисляется записью),
(2) `RendezvousAccept` не имеет приёмника в `node` (ноль читателей вне производителя),
(3) аргумент `shard` в `verify_match_result` во всех вызовах — локальный (`entry.shard`/параметр
функции), а не `res.shard`. Провал хотя бы по одному — фикс валидатора становится отдельной
гипотезой и предшествует стадии 1.
