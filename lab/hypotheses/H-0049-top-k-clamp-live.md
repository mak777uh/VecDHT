# H-0049 — живой `Find` срезает `q.top_k` до `top_k_max = 64` и выдаёт ровно по приёму на находку

status: proposed
claim: "§12.3 обещает «по одному подписанному кадру `RendezvousAccept` на каждый `Match`
(до `top_k`)», а `node.rs:985` срезает `q.top_k` до `params.top_k_max` (манифест: 64,
`config.rs:337`). Существование clamp'а фиксировалось только как факт чтения (`E-0037`) и
как множитель в байтовой арифметике (`E-0026`: «узел обрезает его по top_k_max = 64»);
поведение живого пути при >64 записях в кластере не мерилось ни разу. Утверждение: при 70
живых записях в кластере 112 запрос `q.top_k = 1000` вернёт ровно 64 находки и ровно 64
кадра приёма, парами по префиксу отсортированного списка; `q.top_k = 32` — 32/32 без
изменения `live` (префиксные ключи уже в таблице); `q.top_k = 64` — тот же побайтовый
префикс, что и при 1000 (детерминированная сортировка), `refused_full = 0` во всём прогоне."
falsifiable: "(а) MatchResult отсутствует или длина ≠ min(q.top_k, 64); (б) приём выпущен
не по паре (owner, slot) находки того же индекса — «до top_k» врёт; (в) live() ≠ числу
уникальных выпущенных ключей либо refused_full > 0; (г) список при top_k=64 не является
побайтовым префиксом списка при top_k=1000 — сортировка зависит от запроса; (д) срезанный
список нарушает контракт (d2, slot)."
thresholds: "Зафиксированы до прогона (этот файл + оракул в том же коммите): пороги (1)
70 записей, find@1000 → matches=64, accepts=64, live=64; (2) монотонность (d2, slot) на
срезанном списке; (3) find@32 → 32/32, live остаётся 64; (4) find@64 → 64 побайтовых
повторов первых 64 кадров find@1000; refused_full=0 на всех трёх шагах. Фальсификаторы
(а)…(д) — встроенные assert'ы оракула."
links: [E-0026, E-0037, E-0044, E-0048, H-0048]
