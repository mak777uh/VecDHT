# H-0056 — дыра lease-таблицы возвращается после `prune` по TTL: на бакете 19 таблица всё ещё полная, на бакете 20 освобождается разом

## Наблюдение

`E-0044`/`E-0048`/`E-0053`/`E-0055` мерили поведение НА потолке (`refused_full`, побайтовый
повтор идемпотентности, композиция с clamp), но ни разу не мерили, что происходит с потолком
КОГДА СТРОКИ ТАБЛИЦЫ ИСТЕКАЮТ. В коде (`rendezvous.rs`, `Issuer::prune`) выбрасываются целые
бакеты при `bucket < now - ttl_buckets`; арифметика бакетов — `buckets(sec) = sec.div_ceil(16)`
(`config.rs`), `Params.rendezvous_ttl = 300` (`config.rs:143`) → `buckets(300) = 19`. Для строк
бакета 0 это значит: при `now = 19` условие `0 < 19 - 19 = 0` ложно, бакет 0 жив; при `now = 20`
— `0 < 1` истинно, все 100 000 строк бакета 0 уходят разом.

## Гипотеза (операационализируемое ядро)

Таблица, забитая ВСЕМИ `MAX_ACCEPTS` строками бакета 0 (дыры нет вовсе), ведёт себя так:

| Шаг | Утверждение (порог) |
|---|---|
| (1) `Find` при `now = 0` | приёмов 0, `refused_full` +3 (по числу находок), `live == MAX_ACCEPTS`, ошибок нет |
| (2) `Find` при `now = 19` (= `buckets(300)`) | приёмов 0 (бакет 0 ЕЩЁ не выброшен), `live == MAX_ACCEPTS`, `refused_full` ещё +3 |
| (3) `Find` при `now = 20` | приёмов ровно 3 (по числу живых находок), все с `issued_bucket = 20`, `live == 3` (100 000 строк бакета 0 выброшены разом), новых отказов нет |
| (4) повтор `Find` при `now = 20` | те же 3 кадра побайтово (идемпотентность `seen` обходит опустевшую таблицу), `live` остаётся 3, `refused_full` не меняется |

Порог (2) — различающий: он отличает «prune по бакетам» от «prune по секундам/скользящему
TTL». Если бы выдача появилась на `now = 19`, гипотеза о границе `checked_sub` ложна.

## Фальсификаторы

(а) `live != MAX_ACCEPTS` после заполнения — дыра осталась, тест нечестный.
(б) на `now = 0` или `now = 19` пустая выдача стала `Kind::Error` — маскировка потолка ошибкой.
(в) на `now = 19` приёмов больше нуля или `live < MAX_ACCEPTS` — бакет 0 выброшен раньше
границы, арифметика `buckets(300) = 19` неверна.
(г) на `now = 20` приёмов не 3 — prune не вернул дыру целиком (или вернул лишнее).
(д) на любом шаге `MatchResult.matches.len() != 3` — сами находки потерялись.
(ж) приём №i на шаге (3) не соответствует i-й паре `(owner, slot)` списка находок.
(з) кадр повтора на шаге (4) не побайтовый с прежним — идемпотентность сломана.
(е) `buckets(TTL_SEC) != 19` или `Params.rendezvous_ttl != 300` — границы бакетов взяты не из
той же арифметики, что у `Issuer`.

## Скоуп и границы замера

Одиночный primary (`SEEDS=[1,2,3]`, `SHARD=7`, `POW=8`), три записи бакета 0 от
`OWNER_SEEDS=[77,78,79]`, seeker `identity(88)`, таблица заполнена вручную строками
`issue(junk, identity(90), SHARD, 30_000+i, 0)` — бакет 0, чужие ключи. Мерится взаимодействие
выдачи с `prune` на живом `on_frame`-пути, не юнит-поведение `Issuer` напрямую.

## Вердикт (2026-10-22, append)

Подтверждена целиком, зачётный прогон с первого замера без ДИАГНОЗ'ов (`E-0056`):
все четыре порога совпали пословно — выдача `0 / 0 / 3 / 3(побайтовый повтор)`,
`live 100 000 → 100 000 → 3 → 3`, `refused_full 3→6→6→6`, `issued_bucket=20` у всех
трёх приёмов шага (3), ни одного `Kind::Error`. Различающий порог (2) отсёк альтернативу
«скользящий TTL по секундам»: на `now = buckets(300) = 19` бакет 0 ещё жив, prune
срабатывает ровно на `now = 20` (`checked_sub`-арифметика инвентаря подтверждена живым
поведением). Десятое подтверждение §12.3 подряд; расхождения спеки с кодом нет, правка
спеки не нужна. Ограничение: «разом» — следствие синхронного заполнения таблицы одним
бакетом; при боевом наполнении разными бакетами дыры возвращались бы по бакету за шаг.
