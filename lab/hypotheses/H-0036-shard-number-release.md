# H-0036 — в `release`-профиле (том, что собирается оператору) у `clusters_of_shard` третий исход:
# паник нет ни на одном входе `u16`, а на `s ≡ 4095 (mod 4096)` функция возвращает пустой список;
# всего различных выходов 65 = 64 законных списка + пустой

## Гипотеза

`E-0035` перечислил весь вход `u16`, но в debug-профиле, и сам зафиксировал это как границу:
«для `release` заявлено заранее и не замерено: переполнение `u16` там кольцевое». Проверка не
косметическая: оператор собирает и запускает `release` (`cargo build --release`, CI-гейты тоже
release-профиля), а значит поведение, которое охраняет «граница риска 4095» в отладке, в поставке
отсутствует. Профиль выбран в `Cargo.toml`: `[profile.release]` содержит только `lto = "thin"` и
`codegen-units = 1`, `overflow-checks` не переопределён — значит в release проверки арифметического
переполнения выключены, а в dev (`[profile.dev]` в workspace отсутствует) — включены по умолчанию.

Арифметика, подлежащая проверке перебором (`CLUSTERS_PER_SHARD = 16`, `NLIST = 1024`, `SHARDS = 64`,
модуль `u16` = 65 536 = 16 · 4096):

- `base = s · 16` в release равен `16s mod 65 536 = 16 · (s mod 4096)`, то есть никогда не паникует;
- правая граница `base + 16` равна `16 · (s mod 4096) + 16` и переполняется (замыкается в `0`) ровно
  когда `s mod 4096 = 4095`, то есть при `s ∈ {4095, 8191, 12 287, …, 65 535}` — таких ровно 16 из
  65 536. В этой точке диапазон `65 520..0` пуст, `map`/`collect` дают **пустой `Vec`**, и функция
  возвращает его как обычный результат: не ошибку, не панику;
- для остальных `s mod 4096 ≤ 4094` список побайтово равен `clusters_of_shard((s mod 4096) mod 64)`,
  а `4096 = 64 · 64`, поэтому `(s mod 4096) mod 64 = s mod 64` — то есть тот же законный список
  шарда `s mod 64`, что и в debug-переборе `E-0035`;
- значит множество различных выходов в release — 64 законных списка плюс пустой список, итого 65.

Утверждение (проверяемое ядро): в release-профиле перебор по всем `u16` не даёт ни одной паники,
даёт ровно 16 пустых списков — и ровно на `s ≡ 4095 (mod 4096)`, — а все непустые выходы совпадают
с замаскированным законным списком, так что выходов ровно 65.

## Почему это важнее, чем «просто ещё один профиль»

В debug чужой номер шарда — это либо тихая маска, либо громкая авария. В release громкой аварии
нет вообще, а тихая маска дополняется третьим исходом: **пустой список**. Владелец, который
сканирует ровно присланное (`node.rs:986` → `IvfIndex::search(q, clusters)`), при пустом списке не
делает никакой работы, и `E-0030` уже установил по коду, что пустой список покрытия не запрещает
(«пустой список покрывает любой номер»). Само это следствие — про сеть и про `Find`, а не про
`clusters_of_shard` — данным циклом **не** измеряется и предрегистрируется отдельно; здесь
проверяется только форма выхода функции в поставляемом профиле.

## Фальсификатор

Достаточно одного:

- **(а)** в release найдётся хотя бы один вход с паникой — тогда предположение о выключенных
  проверках переполнения неверно (или его переопределяет другой флаг/окружение), и перебор
  измеряет не поставку;
- **(б)** пустых списков не 16, или они стоят не на множестве `s ≡ 4095 (mod 4096)` — тогда
  арифметика диапазона устроена иначе, чем выведено (например, граница замыкается не в `0`);
- **(в)** среди непустых выходов найдётся список, не равный `clusters_of_shard(s % SHARDS)`, — тогда
  маска не единственный способ получить чужой список;
- **(г)** различных выходов не 65 — тогда где-то есть ещё один исход (усечённый список другой
  длины или дубликат там, где ожидаем нового не быть).

## Порог (фиксируется до прогона)

(1) паник по всему входу ровно 0; (2) пустых списков ровно 16, и множество их позиций побайтово
равно `{4095 + 4096·k | k = 0…15}`; (3) среди непустых выходов несоответствий маске
`clusters_of_shard(s % SHARDS)` ровно 0 и все они длины 16; (4) различных выходов ровно 65
(64 законных списка + пустой). Провал (1) = (а), (2) = (б), (3) = (в), (4) = (г). Пороги не
смягчаются задним числом: если release-арифметика окажется другой, это фиксируется как провал
гипотезы, а не как повод переписать ожидание.

## Вердикт (после E-0036) — `supported`

Снято на дереве `8265051`, `release`-профиль, `-j 2`; полный перебор 65 536 входов
(`lab/logs/e0036-all.log`), пороги (1)…(4) не менялись после прогона:

- **(а) не сработал:** паник по всему входу ровно 0 — предположение о выключенных проверках
  переполнения в `[profile.release]` подтверждено самим поведением, а не чтением `Cargo.toml`;
- **(б) не сработал:** пустых списков ровно 16, и их позиции побайтово равны
  `{4095 + 4096·k | k = 0…15}` — первые сняты как `[4095, 8191, 12 287, 16 383]`, последняя 65 535;
- **(в) не сработал:** среди непустых выходов несоответствий маске `clusters_of_shard(s % SHARDS)`
  ровно 0;
- **(г) не сработал:** различных выходов ровно 65 = 64 законных списка + пустой.

Вывод по существу: в поставляемом профиле у `clusters_of_shard` аварийного исхода нет вовсе — весь
вход `u16` даёт тихий результат, к списку из `E-0034`/`E-0035` добавляется пустой список в 16 точках.
Формулировка `E-0034` о «границе риска от 4095» в поставке не работает: `release` не падает.

Побочный результат цикла, не предсказанный как гипотеза: `КОНТРОЛЬ 1`
(`cargo test --release -p vecdht-crypto`) был красен до правки — оракулы `E-0034` и `E-0035`
утверждали debug-семантику без привязки к профилю. Debug-формулировки их порогов сохранены без
смягчения, для release добавлены утверждения, соответствующие измеренному здесь. Заодно первый
полный прогон `clippy --workspace --all-targets -D warnings` показал, что чистота main по всему
workspace раньше не проверялась (4 × `unnecessary_cast` в `geometry_rotation.rs`).
