# H-0060 — полный набор проверок consume (§12.3): порядок «подпись → адресат → политика TTL → истечение → расход» при поддельных ttl_sec и мишенях

## Наблюдение

§12.3 (2026-10-22, строка про `serve_request`): «Полный набор проверок — подпись
издателя → адресат → политика TTL → истечение → одноразовый расход — реализован в
экспортируемом типе `Spend::consume`». Это первое предложение в цикле §12.3, где
порядок проверок назван ЯВНО. Подпись издателя мерилась (`adversarial.rs`: чужая
подпись), истечение и расход мерилась (`E-0047`/`E-0058`/`E-0059`), адресат мерился
только на живом гейте `serve_request`. Не мерилось НИЧЕГО из политики TTL:
`TtlOutOfPolicy` нигде в тестах не появляется (grep по `crates/`), хотя спека
обещает ветку. По коду (`rendezvous.rs:232`): `ttl_sec == 0 || ttl_sec > max_ttl_sec`
→ `TtlOutOfPolicy`, и этот гейт стоит ДО `Expired` и ДО spent-таблицы.

## Гипотеза (операационализируемое ядро)

Один живой приём бакета 0 (ttl=300) primary-издателя; на стороне цели — поддельные
переиздания кадра (тело с изменённым `ttl_sec`, подпись издателя честная через
`sign_body(RENDEZVOUS)`). Пороги (buckets(300)=19, buckets(1)=1):

| Шаг | Утверждение (порог) |
|---|---|
| (0) | consume f0@19 → `Ok` (базовая грань, окно 300); spent==1 |
| (1) | подделка ttl=0 при now=19 → `TtlOutOfPolicy(0)`; spent НЕ изменился (гейт до вставки) |
| (2) | подделка ttl=301 при now=19 в цели с `Spend::new(300)` → `TtlOutOfPolicy(301)`; spent 1 |
| (3) | та же подделка ttl=301 в цели с `Spend::new(315)` → `Ok` при now=19 (грань 0+buckets(315)=20 не достигнута), spent3==1 — политика — единственный гейт сверх арифметики |
| (4) | wrong-target при ttl=0 (обе ветки ложны, подпись верна) → `WrongTarget` — адресат ДО политики |
| (5) | wrong-target при now=301 (ложны адресат и истечение) → `WrongTarget` — адресат ДО истечения |
| (6) | ttl=1, consume при now=1 → `Ok` (грань buckets(1)=1); повтор@1 → `AlreadySpent`; теперь@2 → `Expired`; spent6==0 после prune (expires 0+1+1=2 ≤ 2) |
| (7) | кадр без подписи (encode_unsigned) → `Unsigned`; кадр с ttl=0 и подписью ЧУЖОЙ (identity 88) при верном target → `BadSignature` — подпись раньше всех |
| (8) | f0@20 → `Expired`, spent==1 — подделки не оставили следов в памяти расхода |

Различающий ядро — (3): если бы `max_ttl_sec` был только отказом (без влияния на
окно), ttl=301 не имел бы законного покупателя; окно расхода считается ИЗ КАРТКИ
(`acc.ttl_sec`), а не из политики цели. Различающий порядок — (4)/(5): перестановка
гейтов меняет код ошибки при заведомо двойно-ложных полях.

## Фальсификаторы

(а) подделка ttl принята как `Ok` там, где ожидается `TtlOutOfPolicy` — гейт политики
отсутствует (спека обещает ветку);
(б) любой отказ по (1)/(2)/(4)/(5)/(7) изменил spent-таблицу — побочный эффект до
проверок;
(в) (4) или (5) дали не `WrongTarget` — порядок проверок расходится со спекой;
(г) (3) отверг ttl=301 при max=315 — политика читается из `Params`, а не из аргумента;
(д) (6) окно ttl=1 не равно buckets(1) — арифметика карты, а не бакетов;
(е) (7) без-подписной кадр дошёл до тела — `Unsigned` не сработал;
(ж) grant (0)/(3) не связан (seeker/issued_bucket съехали);
(з) (8) spent != 1 — память просорилась чужими ветками.

## Скоуп и границы замера

Прямой `Spend::consume` (не вход `present`: гейт `ADR-0013` мерил перебор держателей,
`E-0051`/`E-0054`). Издатель — одиночный primary, приём живой из-под `Find`. Подделка
— переиздание ТЕЛА с честной подписью издателя: меряется приёмная сторона, а не
устойчивость подписи (это территория `adversarial.rs`). `Params.rendezvous_ttl` здесь
не ограничивает `Spend::new` — у цели независимая политика; связь с живым узлом не
мерится.

## Поправка заморозки (2026-10-22, append — после первого замера, до второго)

Первый зачётный прогон (15:04) прошёл пороги (0)…(7) и упал на (8): `spend.spent() == 1`
дало 0. ДИАГНОЗ: причина — порог (5) предъявлял кадр при `now = 301`, а `consume` первым
делом вызывает `prune(now)` (`E-0059`): запись расхода бакета 0 (`expires = 0 + 19 + 1 =
20`) вычищена задолго до (7)/(8), поэтому «память не просорилась» после движения часов
проверять нельзя. Промах — в композиции заморозки (пороги верны по отдельности, но
нумерация шагов предполагала монотонные часы), а НЕ в поведении гейта. Перезаморозка в
СИЛЬНОЙ форме: все ветки порядка мерятся на живом `now = 19` (до движения часов), а
память расхода проверяется РОВНО на бакетах её жизни — добавлены два новых различающих
порога:

| Шаг | Утверждение (порог, поправка) |
|---|---|
| (0)…(4) | без изменений; каждый шаг сопровождается `spent == 1` (отказы не имеют побочных эффектов) |
| (6) | ttl=1: `Ok`@1 / `AlreadySpent`@1 / `Expired`@2 / `spent == 0` — без изменений |
| (7) | `Unsigned`@19 и чужая подпись@19 → `Unsigned`/`BadSignature`, `spent == 1` — НА ЖИВОМ ВРЕМЕНИ |
| (8) | f0@20 → `Expired` И `spent == 0` — различающий: память покидает таблицу ровно на `expires = 20`; если бы `Expired` стоял до `prune` → `spent == 1`; если бы spent-проверка шла раньше истечения → `AlreadySpent` |
| (9) | свежий `Spend::new(300)`: f0@20 → `Expired`, `spent == 0` — состояние исходной таблицы не зависит от веток |
| (5) | wrong-target при `now = 301` (после (8), память уже пуста) → `WrongTarget`, `spent == 0` — адресат до истечения, отказ не возвращает и не множит память |

Новые фальсификаторы: (и) `spent == 1` после `now = 20` — память переживает окно lease
(против `E-0059`); (й) любой из порогов (8)/(9) вернул `Ok` — политика/истечение
пропущены; (к) `spent > 0` после (5) — отказ по адресату имел побочный эффект.

Смысл гипотезы (порядок «подпись → адресат → политика → истечение → расход» и окно из
карты) не изменился и усилен: к нему добавлен замер точки исчезновения памяти расхода.

## Вердикт (2026-10-22, append)

`E-0060` подтверждает гипотезу по перезамороженной (сильной) форме: порядок проверок
`Spend::consume` ровно тот, что назван в §12.3 ЯВНО — подпись издателя (`Unsigned`,
`BadSignature`) → адресат (`WrongTarget`, сильнее и политики, и истечения) → политика
TTL (`TtlOutOfPolicy(0)` и `TtlOutOfPolicy(> max)`, без побочных эффектов на памяти
расхода) → истечение → одноразовый расход. Различающий (3) подтверждён: политика цели —
только отказ, окно всегда из `ttl_sec` кадра (`ttl=301` законно расходуется при `max=315`,
`ttl=1` живёт ровно `buckets(1)=1` бакет). Новый (8)/(9) закрыли промах композиции:
память расхода покидает таблицу ровно на `expires = issued + buckets(ttl) + 1`, то есть
одноразовость не переживает собственное окно — `E-0059` подтверждён на новом материале.
Четырнадцатое подтверждение §12.3 подряд; второе в этом цикле — через поправку заморозки
(`E-0057`, `E-0059`, `E-0060`). Побочный вывод из падавших прогонов (не порог): подписант
приёмки — ключ узла (`node.rs:1019`), `acc.target` — владелец записи; верная форма вызова
`consume(frame, n.me(), acc.target, now)`. Верификация воркспейса: 566 ok, TEST_EXIT=0,
CLIPPY_EXIT=0.
