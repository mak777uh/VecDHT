# H-0118 — церемония сети должна собираться из CLI, а не из тестового кода

## Боль

Узел нельзя поднять без двух документов: `NodeCert`, подписанного порогом авторитетов (§4.2), и
genesis `MembershipUpdate` (§9.2). Оба умеет собирать только `vecdht-node/src/testing.rs` — то есть
тестовый код, который живёт внутри репозитория и оперирует ключами из `[1u8; 32]…[5u8; 32]`. Оператор
публичной сети, у которого ключи лежат в файлах вне репозитория, не может получить ни того, ни
другого без правки Rust. Это названо в `docs/PLAN-v1.md` карточкой A0: без неё дорожка A
(«узел действительно работает») начинается с невозможного шага.

## Зачем это нужно

Требование владельца — минимальное участие оператора и воспроизводимая церемония. Церемония,
которая требует правки исходников, не воспроизводима: у двух операторов получатся разные документы
при одинаковом составе сети, и расхождение заметит не прибор, а отказ узла в поле.

## Форма утверждения

Проверяется не «команды есть», а четыре свойства каждого документа:

1. приём: выданный файл проходит **узел** (`verify_cert` / `Chain::validate`), а не собственную
   проверку команды;
2. отказ: подпись ниже порога, подписант вне набора и genesis из одного члена отвергаются до
   записи, и диск остаётся как был;
3. детерминизм: те же входы — те же байты, порядок строк файла состава не входит в кадр;
4. совпадение dev-режима: ключи, выведенные `cert issue --dev-keys`, — те же, что у
   `artifact init --dev-keys`, иначе dev-сеть не собрать без ручной подписи.

## Решение по рубрике Lean

`пространство: да` (входы конечны), `без_времени: да`, но `для_всех: нет` — утверждение о двух
конкретных путях CLI и конкретных отказах, а не инвариант над всеми состояниями; `дешевле_стенда:
нет` — проверяющий код узла и есть самый дешёвый оракул, модель Lean проверяла бы копию.
Отказ назван, а не подразумевается.

## Границы

Не утверждает, что узел соберётся целиком: A0 даёт документы, `node run` — отдельная карточка A1.

## Результат

**`supports`** (`E-0118`, дерево до правки `8355c72`, код `9b890be`, зелёный блок
`lab/logs/e0118-all.log`). Пять тестов `tests/node_bootstrap.rs` проходят дважды подряд на
неизменном дереве, а посадка `PASSED=4` в таблицу ожиданий краснеет — значит зелёный прогон
чувствителен к подмене факта, а не просто «тесты не падают».

Четыре свойства из формы утверждения подтверждены так:

* **приём** — выданный `cert issue` файл проходит `verify_cert` с `AuthoritySet` и
  `genesis_hash` артефакта; `genesis build` — `Chain::validate(None, &upd)` с `Params` из
  манифеста; то есть проверяет не команда, а тот же код узла;
* **отказ** — подписант вне набора авторитетов, подпись ниже порога, genesis из одного члена и
  состав с дубликатом владельца дают код 2, и файл на диске не появляется;
* **детерминизм** — два прогона с одним seed дают побайтово равные документы, перестановка строк
  файла состава не меняет кадр;
* **dev-режим** — ключи выводятся тем же `dev_key_seed`, что у `artifact init --dev-keys`, и
  команда церемонии не может вывести чужие ключи иначе, чем через этот путь.

Хвосты, названные при закрытии: (1) формат файла кадра genesis не несёт отправителя — `node run`
(A1) обязан опознать подписанта перебором ключей авторитетов по проверке подписи, иначе кадр не
подать в `ShardNode::on_frame`; (2) расписание-зависимый тест `s53_door_branches`
`a_live_revoke_forgets_the_peer_but_not_the_provider_cache` — кандидат `H-0119`
(`OPEN-QUESTIONS` п. 63), к A0 отношения не имеет.
Не проверяет форматы хранения, которыми узел будет читать эти файлы (A1 выбирает и называет их).
Не заменяет собой `artifact init`: артефакт остаётся входом церемонии, и его собственные ключи
по-прежнему задаются там.
