# H-0040 — `prune_idle` не читает `seen_sec`: выбор жертвы идёт по порядку адресов,
# а «самый молчаливый ключ» — фикция комментария; потолок таблицы — мягкий

## Гипотеза

`E-0039` оставил в границах «рост и prune таблицы per-peer не измерялся». Чтение кода
(`admission.rs`) даёт два проверяемых утверждения:

1. комментарий у поля (`admission.rs:195` «по ней считается "самый молчаливый" при prune») и
   комментарий `peer_mut` (`:344` «prune по нему выбирает "молчаливый" ключ») обещают отбор
   жертвы по `seen_sec`; grep по всему crates показывает, что `seen_sec` только пишется
   (`:207`, `:359`) и нигде не читается, а `prune_idle` (`:368…387`) собирает первые `over`
   idle-строк в обходе `BTreeMap` — то есть в лексикографическом порядке адреса;
2. потолок `MAX_TRACKED_PEERS` (в тесте подменён на малый) мягкий: строка ключа с уже пустым
   бакетом publish (burst 20, refill 1/с — значит 20 секунд не-idle) не вытесняется вовсе, и
   за это время таблица легально держится выше потолка, `forgotten_peers` не двигается.

Проверяемое ядро — расхождение двух правил на подобранной последовательности: три idle-строки
с молчаливым ключом наибольшего адреса и недавним ключа наименьшего. Отбор по адресу удаляет
мелкий адрес; отбор по «молчаливости», как обещает комментарий, удалил бы `X` (seen 0).
Второе ядро — счётчики: после бури из 7 активных ключей вставка 8-й при `t=20` (все бакеты
publish досчитались) обязана забыть ровно `7+1−3 = 5` строк, а до `t=20` — ноль.

Важная оговорка, которую измеряет второй оракул: различие «забытая строка / живая idle-строка»
неотличимо ни одним ответом квоты — забытый ключ возвращается с полным burst (это и есть
инвариант §11.3.1, зафиксированный internal-тестом `the_peer_table_forgets_idle_keys_without_changing_any_decision`).
Значит ложь комментария — дефект документации, а не дыра квоты; но она же означает, что
атрибута «вытесняется именно молчаливый» в системе нет, и порядок жертв контролируется
байтами адреса — то есть атакующий, выбирающий себе ключ, выбирает и то, какие из его
idle-строк переживут prune. На квоту это не влияет (все idle-строки равны новому ключу),
поэтому ожидаемый результат — «подтверждена, без последствий для политики».

## Фальсификатор

Достаточно одного:

- **(а)** internal-оракул: при prune с тремя idle-строками удалён `X` (наиболее молчаливый,
  seen 0) или `Z`, а не `Y` (мелкий адрес, seen 1) — комментарий верен, гипотеза неверна;
- **(б)** в external-оракуле до `t=20` таблица ужалась под потолок или `forgotten_peers > 0`
  — активные строки забылись вопреки §11.3.1;
- **(в)** после вставки 8-го ключа при `t=20` удалено не 5 строк или таблица не равна 3;
- **(г)** вердикты `check_find` для забытого ключа и выжившей idle-строки разошлись —
  инвариант «строка = новая строка» не держится;
- **(д)** grep найдёт чтение `seen_sec` вне инициализации/монотонной правки.

## Оракул

1. internal: `crates/vecdht-node/src/admission.rs`, новый тест
   `prune_among_idle_rows_picks_the_smallest_address_not_the_quietest` — единственный способ
   увидеть состав таблицы (`per_peer` приватен); пороги (а) в терминах множества.
2. external: `crates/vecdht-node/tests/admission_table_over_limit.rs` — пороги (б)(в)(г):
   `with_limits(&testing::params(8), 3, 1)`, семь ключей сжигают publish-burst при `t=0`,
   восьмой входит при `t=20` через `check_find`, затем одинаковость burst-последовательностей
   забытого `0x01` и выжившей idle-строки `0x07` (5 × Allow + `FindQuota { 200 }`).
3. инвентарь в `lab/e0040-run.sh`: grep `seen_sec` по всему `crates/` и окно `prune_idle`.

Изменение в `src/admission.rs` — только тестовая секция `#[cfg(test)]`, продуктовая логика
не трогается (иначе это был бы не оракул, а правка).

## Порог (фиксируется до прогона)

(1) internal: после `peer_mut(W, t=2)` удалён ровно `Y`, `X` и `Z` в таблице,
`X.seen_sec == 0 < Y.seen_sec == 1`, `forgotten_peers == 1`, `tracked_peers == 3`;
(2) external: до `t=20` — `tracked_peers == 7` при потолке 3 и `forgotten_peers == 0`;
(3) external: сразу после вставки при `t=20` — `tracked_peers == 3`, `forgotten_peers == 5`;
(4) external: `find_burst(0x01) == find_burst(0x07) == [Allow×5, FindQuota { 200 }]`, финальные
`tracked_peers == 3` (проба забытого ключа сама вытесняет `0x06` — учтено), `forgotten_peers == 6`;
(5) инвентарь: `seen_sec` встречается только как поле/запись, ноль чтений в `prune_idle`.
Провал (1) = (а), (2) = (б), (3) = (в), (4) = (г), (5) = (д).

## Входы и окружение

Debug-профиль, `-j 2`, `RAYON_NUM_THREADS=2`. Реального `MAX_TRACKED_PEERS = 65 536` прогон не
касается: `with_limits` подменён на 3 ровно потому, что переполнение 65 536 строк меряло бы
память, а не правило (тот же аргумент, что в комментарии конструктора, `admission.rs:233`).
Компиляция-на-месте: `Bucket::refill = 1/с` для publish ⇒ не-idle окно = ровно 20 секунд,
`level_at(20) = 20 = capacity` — арифметика взята из unit-теста
`publish_bucket_gives_a_burst_then_one_per_second`. Часовая модель целочисленная, дробных
секунд нет.

## Вердикт (после `E-0040`)

**Подтверждена.** Пороги (1)…(5) выполнены единственным прогоном без дефектов оракула:
при трёх idle-строках prune удаляет наименьший адрес `Y` (seen 1), а наиболее молчаливый `X`
(seen 0) переживает — отбор по `seen_sec` из комментария не реализован, grep подтвердил:
единственное чтение поля во всём `crates/` — assert самого оракула; 7 активных строк при
потолке 3 держатся над потолком 20 секунд с `forgotten_peers = 0`; всплеск idle при `t=20`
забывает ровно `7+1−3 = 5`; вердикты забытого ключа и выжившей idle-строки идентичны
(Allow×5 + `FindQuota{200}`). Фальсификаторы (а)…(д) не сработали. Итоговая квалификация:
расхождение комментария и кода — дефект документации (поле `seen_sec` — мёртвый код), квотных
последствий нет ровно потому, что забытая строка неотличима от новой (порог (4)); при этом
порядок жертв формально контролируется байтами адреса, и нигде в спеке это не заявлено.
Границы — в `E-0040`: подменные лимиты вместо 65 536, состав таблицы виден только
internal-тесту.
