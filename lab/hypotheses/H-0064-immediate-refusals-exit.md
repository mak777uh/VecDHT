# H-0064 — немаскировка трёх оставшихся немедленных отказов на входе цели (§12.3): `Expired`, `WrongTarget`, `TtlOutOfPolicy` выходят из `serve_request` как `Spend(...)`, порядок «политика → истечение» доживает до выхода

## Наблюдение

Спека §12.3: «`Spend::consume` по списку держателей шарда-кандидатов (перебор кандидатов
только по `BadSignature`; `AlreadySpent`/`Expired`/`WrongTarget`/`TtlOutOfPolicy` отсекаются
немедленно)». На входе цели (`serve_request`) измерялись: `AlreadySpent` (`E-0051`,
`E-0062`), `Malformed`/`WrongKind` (`E-0062`) и маскировка `AlreadySpent` при неполном
списке держателей (`E-0054` — кандидат на ADR). Три остальных немедленных отказа мерились
только на входе `consume`: `Expired` — `E-0047`/`E-0058`/`E-0059`/`E-0060`,
`WrongTarget` — `E-0060`/`adversarial.rs`, `TtlOutOfPolicy` — `E-0060`. grep по
`crates/vecdht-node/tests/` на момент пре-регистрации: комбинаций
`TextError::Spend(AcceptError::Expired | WrongTarget | TtlOutOfPolicy)` — ноль. То есть
утверждение «немедленно» в смысле «не гасится перебором кандидатов на выходе цели» для них
никогда не проверялось: теоретически `serve_request` мог терять их в
`NotSignedByShardHolder`, и гейт бы не ослабевал, но учёт отказов ослеп.

Технический ключ (урок `E-0060`: приёмку подписывает ключ узла, `node.rs:1019`): seed
харнеса известен, `testing::identity(seed)` даёт тот же приватный ключ — пере-подпись
изменённого тела `RendezvousAccept` проходит гейт подписи `consume` и падает ровно на
проверяемом поле. Порог (0) закрепляет различимость базы: пере-подпись НЕизменённого тела
побайтово равна живому кадру (Ed25519 детерминирован; если равенство поплывёт — поплывёт
весь оракул, и это будет видно сразу).

## Гипотеза (операционализируемое ядро)

O — владелец записи (адресат цели), A — seeker, N — ключ узла-primary; живой приём F0
(issued_bucket=0, ttl_sec=300, buckets(300)=19, грань исчезновения spent-памяти now=20 из
`E-0060`). `Spend::new(300)` — политика цели; пороги заморожены (полный текст — docstring
оракула `crates/vecdht-node/tests/immediate_refusals_exit.rs`):

| Шаг | Утверждение (порог) |
|---|---|
| (0а) | `RendezvousAccept::decode(F0)`: seeker=A, target=O, shard=7, issued_bucket=0, ttl_sec=300 |
| (0б) | пере-подпись unchanged-тела ключом N побайтово равна F0 |
| (1) | честное предъявление при now=0 → `Ok` (база живости харнеса) |
| (2) | тот же F0 при now=20 → `Spend(Expired)`, а не `NotSignedByShardHolder` и не `Ok` |
| (3) | приём `target` := чужой ключ (пере-подпись N), now=0 → `Spend(WrongTarget)`, а не `Ok`/`NotSigned...` |
| (4) | приём `ttl_sec` := 0 (пере-подпись N), now=0 → `Spend(TtlOutOfPolicy(0))` |
| (5) | приём `ttl_sec` := 301 при политике 300 (пере-подпись N) → `Spend(TtlOutOfPolicy(301))` — отказ называет фактическое число |
| (6) | приём `ttl_sec` := 0 при now=20 (политика И истечение) → `Spend(TtlOutOfPolicy(0))` — «политика раньше истечения» доживает до выхода цели (сильная форма зеркала `E-0060`) |
| (7) | кадр (4), подписанный ЧУЖИМ ключом → `NotSignedByShardHolder` — маскирующая ветка остаётся единственной |
| (8) | `spend2.spent() == 0` после (2)…(7); `spend1.spent() == 1` после (1); повтор честного → `Spend(AlreadySpent)` |

Различающее ядро: (2)/(3)/(4)/(5)/(6) против `NotSignedByShardHolder` — если бы
немедленный отказ гасся перебором, спека лгала бы про «немедленно», а учёт причин отказов
на цели был бы невозможен; (7) — обязательный контраст: та же сборка кадра с чужим
подписантом ДОЛЖНА гаситься, иначе оракул не различает «прошёл подпись» и «не прошёл».
(6) различает порядок «политика → истечение» на новом входе: при перевёрнутом порядке отказ звался
бы `Expired`.

## Фальсификаторы

(а) (2)/(3)/(4)/(5)/(6) дали `NotSignedByShardHolder` — немедленный отказ замаскирован
перебором, §12.3 нарушен; (б) `spent > 0` в spend2 после отказов — отказ с побочным
эффектом; (в) (2)/(3) дали `Ok` — гейт истечения/адресата пропущен; (г) (4)/(5) дали `Ok`
— политики ttl на входе нет; (д) (6) дал `Spend(Expired)` — порядок перевёрнут на выходе
цели; (е) (7) дал `Spend(Ttl...)` — чужая подпись прошла, харнес подписывает не тем
ключом; (ж) (0б) пере-подпись не равна F0 — база различения не стоит; (з) (8) повтор
честного дан `Ok`.

## Скоуп и границы замера

Меряется выход одной экспортируемой функции (`serve_request`) на пере-подписанных кадрах;
порядок внутри `consume` не перенормируется — он измерен `E-0060` (политика → истечение),
здесь проверяется только его доживаемость до выхода цели. `Malformed`/`WrongKind`/
немаскировка — территория `E-0062`; маскировка при неполном списке издателей — `E-0054`
(кандидат на ADR, здесь не трогается). now=20 — ровно грань исчезновения записи расхода
из `E-0060` (`expires = issued + buckets(ttl) + 1`): при этом now отказ обязан быть
`Expired`, а не `AlreadySpent`, даже на пустой таблице — вторая сторона той же границы.
Пере-подпись своим ключом — не подделка с точки зрения сети (харнес знает сид узла по
построению тестового окружения); стойкость подписи к чужому ключу — (7) и `adversarial.rs`.

## Вердикт (2026-10-22, append)

Подтверждена ПЕРВЫМ замером (rev `c8610a6`, 17:39; `E-0064`): пороги (0а)…(8) совпали,
фальсификаторы (а)…(з) молчат, ДИАГНОЗ и поправка заморозки не понадобились. Обещание
§12.3 «`AlreadySpent`/`Expired`/`WrongTarget`/`TtlOutOfPolicy` отсекаются немедленно»
измерено целиком на обоих концах: причина каждого немедленного отказа доходит до
вызывающего в `TextError::Spend(e)` с точным именем и числом (`TtlOutOfPolicy(301)`
называет фактический ttl), `NotSignedByShardHolder` не подменил ни один из семи отказов, и
только чужая подпись гасится перебором (контраст (7)). Порядок «политика раньше истечения»
с `E-0060` доживает до выхода цели: ttl=0 при now=20 → `TtlOutOfPolicy(0)`, не `Expired`
(порог (6)). ГРАНЬ исчезновения памяти расхода (`E-0060`: `expires = issued +
buckets(ttl) + 1`) держит имя «истёк» и на входе цели (порог (2)). Нулевой побочный
эффект: `spent == 0` после всех отказов, база `Ok → 1 → AlreadySpent` цела. Метод
пере-подписи ключом узла закреплен побайтовым равенством unchanged-кадра (0б).
Восемнадцатое подтверждение §12.3/§12.4 подряд. Правка спеки не нужна: расхождения
спека↔код не обнаружено. Верификация 570 ok / clippy 0.
