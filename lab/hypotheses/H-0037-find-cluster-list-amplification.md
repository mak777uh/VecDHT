# H-0037 — приём `Find` не знает о длине списка кластеров: 65 535 идентификаторов проходят кодек,
# работа узла линейна по длине списка вместе с дублями, а цена в admission — ровно один токен

## Гипотеза

`E-0036` закрыл арифметику `clusters_of_shard`, но в «Границах» прямо оставил: «что делает узел с
пустым или раздутым списком `Find` — отдельный пре-регистрационный цикл». Это он и есть.

Код, читаемый до прогона (пути указаны для проверки, вывод — под замер):

- `crates/vecdht-wire/src/codec.rs:286` — `Reader::u16_list` читает `n` из u16-префикса и крутит
  цикл `0..n` без собственной границы: единственная фактическая верхняя граница числа элементов —
  65 535 (u16 не вмещает больше);
- `crates/vecdht-wire/src/codec.rs:23` — `MAX_BODY_LEN = 4 MiB` ограничивает тело на декоде
  (`frame.rs:218`); список из 65 535 u16 занимает 131 070 байт, то есть телу он не предел;
- `crates/vecdht-wire/src/messages.rs:371` — `Find::decode_body` вызывает `r.u16_list()` и нигде
  не смотрит на длину результата;
- `crates/vecdht-node/src/node.rs:981` — единственная проверка списка на пути поиска:
  `q.clusters.iter().any(|c| shard_of_cluster(*c) != self.shard)` — поэлементная, дубликаты
  «своего» кластера сквозь неё проходят;
- `crates/vecdht-node/src/node.rs:970` — admission списывает **один** токен на кадр `Find` до
  разбора тела; длина списка на цену влияет постольку, поскольку она вообще не входит в цену
  (`admission.rs:206`: бакет `Bucket::new(per_peer_find_rps, per_peer_find_rps)`, в тестовом
  манифесте 5/с, вместимость 5);
- `crates/vecdht-index/src/ivf.rs:465` — `IvfIndex::search` идёт «по запрошенным кластерам → по
  слотам кластера»: одноимённый кластер, повторённый `n` раз, сканируется `n` раз.

Отсюда проверяемое ядро: на узле с 1 104 записями по 16 кластерам шарда (69 на кластер, стенд
гейта §19.1) запрос со списком `[c; n]` возвращает ровно `n · 69` кандидатов при достаточно
большом `top_k` — дубликаты не схлопываются, работа линейна по длине списка; при этом квота
расходуется одинаково для списка длины 1 и длины 4 096, а предельный список в 65 535 элемента
проходит кодек туда-обратно без изменения порядка. Усилитель: 4 096 / 16 = 256× работы на кадр
против законного nprobe-списка того же шарда; потолок по длине — 65 535 / 16 ≈ 4 096×, и его в
приёмном пути никто не ищет.

## Фальсификатор

Достаточно одного:

- **(а)** `Find` со списком из 65 535 идентификаторов не кодируется или не декодируется (значит
  граница длины в приёмном пути всё-таки есть и она ниже предположенной);
- **(б)** тело с 65 536 элементами декодируется без ошибки — молчаливое усечение u16-префикса в
  энкодере (`v.len() as u16`, `codec.rs:136`) тогда создаёт несовместимость кодеков, а не отказ;
- **(в)** при `n > 16` `search` возвращает меньше `n · 69` hits — дубликаты схлопываются,
  линейность по длине списка не выполняется и «усиление» не больше законного запроса;
- **(г)** шестой `Find` с раздутым списком отличается по исходу от шестого с законным (другой код
  ошибки, другой `retry_after_ms`, лишний израсходованный токен) — тогда admission всё-таки
  знает о длине списка и цена зависит от неё.

## Оракул

Три новых тестовых файла, ни сети, ни корпуса, ни `candle`:

1. `crates/vecdht-wire/tests/find_cluster_list.rs` — пороги (1), (2): round-trip списка 65 535
   (порядок «кластер шарда 7 + рандом» не важен, берём детерминированный `(i % 16) + 112`),
   сравнение байтов тела с ручным расчётом, попытка 65 536 с записи ровно variant'а ошибки;
2. `crates/vecdht-index/tests/find_cluster_list_amplification.rs` — порог (3): стенд
   `search_latency.rs` (шард 0, 1 104 записи, `stage_time_mark(1_100)`), `n ∈ {1, 16, 256, 1024,
   4096}`, `clusters = [0; n]`, `top_k = n · 69 + 1`, точное `hits.len() == n · 69`; рядом
   контрольный `top_k = 10` (срез по top_k тоже обязан держаться) и печать p50 задержек как
   справочного свидетельства стоимости (порога по времени нет — см. «Ограничение по профилю»);
3. `crates/vecdht-node/tests/find_admission_price.rs` — пороги (4), и фальсификаторы (а)/(г) на
   живом узле: harness `primary_on` из `tests/admission.rs` (шард 7, кластер 112), два новых
   ключа, каждой — по 6 `Find` при `testing::clock(0)`: первый ключ со списком `[112]`, второй с
   `[112; 4096]`; сравнение кодов ошибок и `retry_after_ms` шестых ответов между собой.

Инвентарь (5) — не тест, а grep по приёмному пути: `crates/vecdht-wire/src/messages.rs`
(`Find::decode_body`), `crates/vecdht-node/src/node.rs` (`handle_find`),
`crates/vecdht-node/src/admission.rs` (`check_find`) на любой код, ограничивающий
`clusters.len()`. Ожидание: ноль вхождений, кроме поэлементного guard'а `shard_of_cluster`.

## Порог (фиксируется до прогона)

(1) список 65 535 элементов кодируется, декодируется, `clusters` побайтово равен исходному, тело
строго меньше `MAX_BODY_LEN`; (2) 65 536 элементов не декодируются как валидный `Find` — variant
ошибки записывается в протокол как есть, каким бы он ни был (прогноз: `TrailingBytes`); (3) для
каждого `n ∈ {1, 16, 256, 1024, 4096}` `hits.len() == n · 69` при `top_k = n · 69 + 1` и
`hits.len() == 10` при `top_k = 10`; (4) ровно 5 первых `Find` каждого ключа проходят, шестой —
`QUOTA_FIND` с `retry_after_ms = 200`, и исход шестого ответа не зависит от того, была ли длина
1 или 4 096; (5) grep даёт 0 ограничений на длину списка в приёмном пути. Провал (1) = (а),
провал (2) = (б), провал (3) = (в), провал (4) = (г).

## Входы и окружение

Дерево после `8209955`, debug, `-j 2`, `RAYON_NUM_THREADS=2`. Профиль release в этом цикле
сознательно не меряется: вывод не зависит от арифметики переполнения (в отличие от E-0036) —
длина списка это `usize` на приёме, а не кольцевой u16; время p50 из пункта (3) печатается как
справочное и порогом не является: debug-число ничего не доказывает (§19.1), а доказательное
свидетельство линейности — точное число hits, оно от профиля не зависит.

## Вердикт (после `E-0037`)

**Подтверждена.** Все четыре порога выполнены на прогоне `E-0037` (см. таблицу там же):
65 535 кластеров проходят кодек побайтово (тело 131 500 < 4 MiB), 65 536 — отказ
(`TagOrder { prev: 117, next: 114 }`), `hits` ровно `n·69` при n ∈ {1, 16, 256, 1024, 4096}
(дубли не схлопываются, усиление ×256 по числу оценок на кадр против законного 16-кластерного
списка; справочно p50 debug ×249), шестой `Find` обоих ключей — `QUOTA_FIND`/200 мс
независимо от длины списка. Инвентарь (5): проверок длины списка в приёмном пути нет ни одной.
Уточнение к формулировке, из измеренного: раздувается CPU запроса, а не память узла (буфер
отбора жёстко ограничен `top_k`, узел срезает `top_k_max`). Открытые следствия: пустой список
(`H-0038`), sybil-совокупность под такими запросами и транспортная достижимость — не измерены.
