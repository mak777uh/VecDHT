# H-0065 — привязка `slot` запроса к предъявленному приёму: обещание §12.4 «NO_SUCH_SLOT» против кода, где константа не конструируется нигде

## Утверждение

Спека §12.4: «`slot` адресует запись в рамках эпизода, в котором был получен `MatchResult` —
старый слот после смены эпохи просто даёт `Error{code:"NO_SUCH_SLOT"}`, а не чужой текст».
Комментарий `ivf.rs:157` (`entry`) ссылается на тот же код ответа. В коде:
`err_code::NO_SUCH_SLOT` объявлена (`messages.rs:41`) и НЕ КОНСТРУИРУЕТСЯ НИГДЕ (grep
`err_code::NO_SUCH_SLOT` по `crates/` пуст на момент пре-регистрации; упоминания — только
объявление и два docstring-комментария); `IntentTextRequest.slot` (`messages.rs:473`) не
читается ни в `session::serve_request`, ни в `Spend::consume` — путь расхода использует
только `present`, а `Grant.slot` приходит из тела приёма (`rendezvous.rs:160`). Предсказание:
на входе цели расход ПРОХОДИТ при любом `req.slot`, не совпадающем со слотом приёма, ни один
отказ не порождается, и `NO_SUCH_SLOT` на этом пути не появляется — то есть обещанный
механизм «старый слот даёт ошибку, а не чужой текст» в библиотеке отсутствует (шестая
спека-фикция семейства `E-0041`…`E-0045`: спека обещает механизм, которого в коде нет).

## Скоуп и отличие от покрытого

`E-0054`/`E-0064` мерили ОТКАЗЫ consume на входе цели (истечение, адресат, политика,
маскировка при неполном списке держателей). `present_serving_gate.rs` (`ADR-0013`) мерил
пустой `present` и перебор кандидатов по `BadSignature`. НЕ мерилось: предъявление
ЧАСТО Валидного приёма под расходящимся `req.slot` — ровно тот вектор, на который
указывает §12.4. Гейт расхода при этом не ослабляется (одноразовость живёт на приёме);
фикция — в отсутствии обещанной сверки и обещанного кода, а не в дыре одноразовости.
Правка спеки/кода — только со слова владельца (черновик ADR в этом же коммите); прогон —
наблюдение и замер, ничего не меняет.

## Пороги (заморожены до первого замера; оракул `crates/vecdht-node/tests/slot_request_accept_binding.rs`)

Обозначения: O — владелец записей и адресат цели (seed 90); A — seeker (seed 91); N — ключ
узла-primary (seed известен харнесу, метод пере-подписи `E-0064`); S0/S1 — слоты двух живых
записей одного владельца по порядку `MatchResult` (бакет 0, часы не двигаются); DEAD_SLOT =
0xFFFF_FFFF; F0 — живой приём бакета 0, выписанный на S0.

| Порог | Утверждение |
|---|---|
| (0) | decode(F0) = (seeker A, target O, shard 7, slot S0, issued_bucket 0, ttl 300); пере-подпись unchanged тела ключом N ПОБАЙТОВО равна F0; MatchResult содержит ровно 2 находки, s0≠s1, ни один не DEAD_SLOT |
| (1) | `serve_request(req.slot=S0, present=F0)` → `Ok`, `grant.slot == S0`, spent == 1 |
| (2) | `serve_request(req.slot=S1, present=reissue(F0))` → `Ok` (НЕ отказ), `grant.slot == S0 ≠ S1` |
| (3) | `serve_request(req.slot=DEAD_SLOT, present=reissue(F0))` → `Ok`, `grant.slot == S0` |
| (4) | spent == 2 после (1)…(3): расходящиеся `req.slot` не плодят записей расхода |
| (5) | повтор (2) на том же инстансе → `Err(Spend(AlreadySpent))` |
| (6) | свежий `Spend`, `req.slot=S1` с тем же приёмом → `Ok`, `grant.slot == S0` |

Фальсификаторы: (а) любой из (2)/(3)/(6) дал `Err` — механизм привязки в коде существует,
фикции нет; (б) `grant.slot == req.slot` в (2)/(3) — привязка всё же читает запрос; (в) spent
≠ 2 в (4) — расхождение слотов тронуло память расхода; (г) (5) дал `Ok` — одноразовость
привязана к паре (приём, slot); (д) пере-подпись unchanged ≠ F0 — харнес подписывает не тем
ключом, база различения не стоит; (е) Dead-slot/слоты некорректны (DEAD_SLOT занят,
находка < 2) — фикстура не зафиксирована.

## Метод

Харнес одиночного primary (как зелёный `immediate_refusals_exit.rs`): `primary_on` возвращает
`(ShardNode, dir, seed)`; две публикации одного владельца с векторами 1 и 2; `Find` вектором 1
при `now=0`; все мутанты — пере-подпись тела приёма ключом узла (`testing::identity(seed)`),
unchanged-база закреплена побайтовым равенством (0). `serve_request` вызывается напрямую с
`issuers = [n.me()]`; живого текстового обслуживания нет — меряется ровно гейт привязки.
Часы не двигаются (урок `E-0060`). Helper `lab/e0065-run.sh`; лог `lab/logs/e0065-all.log`
(append-only); верификация `lab/workspace-verify.sh E-0065`.

## Поправка заморозки (2026-10-22, append после первого замера)

Первый замер (rev `1bab80d`, 18:26) упал на фиксации фикстуры: `assert matches.len()==2`
дал 1 — две публикации векторов 1 и 2 одним владельцем O слились в одну живую запись
(индекс хранит один слот на `(owner, shard)`, перепубликация заменяет на месте —
`ivf.rs:311-340`, юнит-тест `republish_replaces_the_candidate_instead_of_doubling_it`).
Промах артефакта фикстуры, а не гейта (урок `E-0060`): пороги предсказания (1)…(6) о
привязке `slot` не были дощены — прогон умер на assert (е) до них; само предсказание
фикции не подтверждено и не опровергнуто. Фикстура пересобрана СИЛЬНЕ, пороги не ослаблены:

1. вторая запись публикуется ВТОРЫМ владельцем (seed 92); порог (0) усилен фиксацией
   `matches[0].owner != matches[1].owner` (различимость двух слотов по построению);
2. добавлен порог (7) в сильной форме: тот же приём F0 (target = O) предъявляется на входе
   второго владельца B -> `Spend(WrongTarget)` и `spent == 0` на инстансе B — адресат
   привязан подписанным телом приёма, то есть фикция ровно в `slot`, а не в мишени;
   фальсификатор (ж): `Ok` или иной отказ в (7) означал бы отсутствие привязки target;
3. `req.slot = S1` в (2) — теперь запрос чужого текста (запись другого владельца) при СВОЁМ
   валидном приёме: формулировка «старый слот даёт ошибку, а не чужой текст» проверяется в
   сильной версии — чужой текст доступен по чужому слоту, если приём свой.
