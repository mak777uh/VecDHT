# H-0122 — сценарий двух машин исполним командами из README

## Боль

Условие 3 v1 (`ADR-0044`) — один end-to-end сценарий на разных машинах: три узла, агент
публикует и находит, сценарий описан в README и повторяем его командами. До этого цикла README
описывал церемонию кусками, а между seed узла и двумя входами церемонии (`cert issue --owner`,
`cert issue --peer-id`) не было моста: owner и PeerId выводятся из seed только внутри `node run`.
Собрать `members.txt` вручную значило переписать криптографию в bash — то есть сценарий, который
нельзя повторить, не прочитав код.

## Форма утверждения

1. **Мост seed → имена.** `key show --seed` печатает `owner` и `peer_id`, выведенные теми же
   `Identity::from_seed` и `keys::peer_id`, что и `node run`; тест сравнивает вывод команды с
   независимым вызовом этих функций. Приватный ключ не печатается.
2. **Церемония переносима.** `lab/two-hosts.sh ceremony DIR` собирает артефакт, три сертификата,
   genesis (порог 2 из 3) и `keys.txt`, печатает primary и проверяет, что текст сценария лежит в
   шарде 0 через `encode`. Каталог `DIR` можно скопировать на вторую машину: `serve`,
   `publish`, `find` читают только его.
3. **Публикация и поиск между процессами.** Три процесса `node run` на 127.0.0.1 (dry-run одной
   машины), публикация через primary, поиск через другой узел: находка несёт того же владельца и
   тот же слот, `d2 = 0`, совпадение одно.

## Чего утверждение не говорит

* Не заменяет прогон на двух хостах: здесь три процесса на одной машине, сеть — 127.0.0.1.
  Двухмашинный прогон остаётся действием владельца, и README говорит это прямо.
* Не утверждает, что `find` быстрый: наблюдаемая шероховатость — поиск ждёт полный `--timeout`
  (30 с), когда один из провайдеров не отвечает; совпадение от этого не меняется.
* Не проверяет relay/WAN-путь и NAT: только loopback QUIC.
* Не вводит новых байтовых форматов: `key show` — вывод из существующих функций.

## Результат

`supports` (`E-0122`). Сценарий исполним командами из README: `key show` выводит те же owner/PeerId,
что использует `node run` (тест сравнивает с `Identity::from_seed`/`keys::peer_id`); `lab/two-hosts.sh
selfcheck` дважды на неизменном дереве поднял три узла шарда 0, опубликовал карточку через primary и
нашёл её с другого узла: владелец `fa4834…9565` и слот 0 совпали, `d2 = 0`, совпадение одно, текст
сценария — cluster 9 / шард 0. Helper: `WORST_RC=0`, 28 ожиданий без расхождений, `STABLE=1`,
`PLANT_EXIT=1`, PRE_FIX на `faac87e` — ни команды, ни скрипта. Полная верификация — отдельным коммитом
после закрытия.

Что осталось за пределами: прогон на двух настоящих хостах (действие владельца), NAT/relay и время
поиска; шероховатость «`find` ждёт полный `--timeout`, когда один провайдер не отвечает» записана в
README и в лог, но не исправлена.
