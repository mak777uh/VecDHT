# H-0063 — UTF-8-ветка `session::verify_response` как порядок (§12.4): последний гейт цепочки и два имени отказа для битого UTF-8 в двух полях

## Наблюдение

Спека §12.4 называет цепочку ЯВНО: «Ответ принимается только после проверки вида кадра,
наличия подписи, `owner_ed25519 == ожидаемого владельца`, подписи по ключу владельца и
UTF-8; лимит 1000 байт проверяется и при подписании, и при разборе». `E-0062` замерил
первые пять ступеней и имя лимита на разборе; ступень UTF-8 осталась единственной
немеренной как ПОРЯДОК: grep по `crates/vecdht-node/tests/` даёт НОЛЬ `TextError::NotUtf8`
(есть ноль и по соседним веткам порядка, но их закрыл `E-0062`), базовый факт «битый текст
с честной подписью → `NotUtf8`» стоит только юнит-тестом модуля (`session.rs:271`), а
порядковые комбинации (битый текст при чужой подписи / чужом ожидаемом / чужом виде / без
подписи) не измерялись никогда.

Код обещает разделение имён по полям: `text` — `bytes`-поле декодера (`codec.rs:272`:
проверка только длины, содержимое не трогается) и ловится последним гейтом
`session.rs:192` → `NotUtf8`; `model_version` — `string`-поле (`codec.rs:280`:
`String::from_utf8` → `DecodeError`) и ловится на разборе тела `session.rs:175` →
`Malformed`. Значит один и тот же битый байт 0xFF в двух полях одного кадра обязан давать
разные имена в разных местах цепочки. Отдельно молчание спеки: включительность границы
лимита на разборе (1000 байт валидного UTF-8 — `Ok`?) нигде не замерялась; §12.4 говорит
«лимит 1000 байт», `MAX_INTENT_TEXT_BYTES = 1000`, а `sign_response`/декодер используют
строгое `>` — предсказание включительности следует из кода, но не из прямой строки спеки.

## Гипотеза (операционализируемое ядро)

O — издатель ответа, E — чужой ожидаемый ключ, F — третий ключ-подписант. Пороги заморожены
(полный текст — docstring оракула `crates/vecdht-node/tests/utf8_last_gate.rs`):

| Шаг | Утверждение (порог) |
|---|---|
| (0) | раскладка честного кадра («гранит», «abcdef»): длина `8 + тело + 1 + 64`, байт `0xD0` по смещению `8+32+2`; декодер ПРОПУСКАЕТ non-UTF-8 `text` [0xFF,0xFE] (`bytes`-поле), `verify_response(_, &O)` на нём с честной подписью → `NotUtf8` |
| (1) | тот же non-UTF-8 текст, подпись F, ожидаемый O → `BadSignature`, а не `NotUtf8` |
| (2) | тот же кадр при ожидаемом E → `WrongOwner{expected: E, found: O}`, а не `NotUtf8` |
| (3) | non-UTF-8 текст, чужой табличный вид `IntentTextRequest` с честной подписью → `WrongKind` |
| (4) | non-UTF-8 текст без подписи → `Unsigned` |
| (5) | ровно 1000 байт валидного UTF-8 («я»×500) с честной подписью → `Ok`, побайтовый раунд-трип |
| (6) | 999 байт с обрезом («я»×499 + 0xD1) с честной подписью → `NotUtf8` (гейт не сводится к длине) |
| (7) | честный кадр, байт `model_version` := 0xFF in-place: при O → `Malformed`, а НЕ `BadSignature`/`NotUtf8` |
| (8) | тот же кадр при E → `Malformed` (разбор раньше владельца) |
| (9) | `sign_response` → `verify_response` на многобайтовом юникоде → `Ok` с побайтовым раунд-трипом модели и текста |

Различающее ядро: если бы контент проверялся раньше криптографии, (1) дал бы `NotUtf8`;
если бы декодер не проверял строки, (7) дал бы `BadSignature` (подпись покрывает байты
тела, а битая строка их меняет — честная подпись на мутанте не сходится, и `Malformed`
доказывает, что тело умирает раньше подписи); если бы UTF-8-гейт был единственной проверкой
содержимого на разборе, (7) дал бы `NotUtf8`. Порог (5) проверяет включительность границы,
о которой спека молчит, — сильная форма: `Ok` ровно на 1000 и `Malformed` на 1001 (мерено
`E-0062`, порог (8)) задают границу точно.

## Фальсификаторы

(а) (1)/(2) дали `NotUtf8` — контент раньше подписи/владельца, цепочка §12.4 перевёрнута;
(б) (3)/(4) дали не `WrongKind`/`Unsigned` — содержимое лезет в начало цепочки;
(в) (5) отвергнут — лимит не включительный вопреки строгому `>` в коде;
(г) (6) дал `Ok` — UTF-8-гейта нет;
(д) (7) дал `BadSignature` — декодер не проверяет строки, контракт `string`-поля иллюзорен;
(е) (7) дал `NotUtf8` — имя отказа не различает поле и момент;
(ж) (8) дал `WrongOwner` — владелец раньше разбора тела;
(з) (0) декодер отверг non-UTF-8 `text` — `bytes`-поле на деле не bytes;
(и) (5)/(9) раунд-трип не побайтовый.

## Скоуп и границы замера

Меряется одна экспортируемая функция (`verify_response`) плюс подписывающий конец
(`sign_response`); живого узла нет — кадр собирается напрямую, юнит-фикстуры достаточны
(уроков по харнесу `E-0060`/`E-0062` здесь не требуется: часы не участвуют). Порядок
`serve_request`/`consume` закрыт `E-0062`; заголовочные гейты — `E-0061`; TLV-правила —
юнит-тест кодека. Ветки `Structured`/`Markup`/`LineBreak`/`Control`/`Empty`/`TooLong`
(разметка текста на пути `intent_text` выше транспортного ответа) к §12.4 не относятся и
здесь не меряются. Байт `0xFF` выбран как заведомо невалидный стартовый байт UTF-8;
фикстура (6) — корректный префикс с обрезанной последней последовательностью.

## Вердикт (2026-10-22, append)

Подтверждена ПЕРВЫМ замером (rev `47fb686`, 17:10; `E-0063`): пороги (0)…(9) совпали,
фальсификаторы (а)…(и) молчат, ДИАГНОЗ и поправка заморозки не понадобились. UTF-8 —
последний гейт цепочки §12.4: битое содержимое текста не доживает ни до одной более ранней
ступени (чужая подпись → `BadSignature`, чужой ожидаемый → `WrongOwner`, чужой вид →
`WrongKind`, без подписи → `Unsigned`), базовый `NotUtf8` даёт только честный кадр. Один
байт 0xFF в двух полях зовётся разными отказами в разных моментах: `text` (`bytes`-поле)
ловит гейт `verify_response` → `NotUtf8`, `model_version` (`string`-поле) — декодер тела →
`Malformed` до сверки владельца и подписи. Граница лимита измерена точно: ровно 1000 байт
валидного UTF-8 → `Ok` (в паре с 1001 → `Malformed` из `E-0062` — включительная граница, о
которой спека молчит), 999 байт с обрезом → `NotUtf8` (содержимое проверяется не по длине).
`sign_response`→`verify_response` — побайтовый раунд-трип юникода: ветки `NotUtf8` на
подписании нет по построению (`&str`). Семнадцатое подтверждение §12.3/§12.4 подряд. Правка
спеки не нужна: расхождения спека↔код не обнаружено. Верификация 569 ok / clippy 0.
