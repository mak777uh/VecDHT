# H-0034 — граница «номер шарда должен быть свой» стоит в двух слоях без правила: `clusters_of_shard`
# не проверяет вход и маскирует чужой номер через `% NLIST`, а диапазонную проверку при декоде имеют
# только 3 из 13 сообщений с полем `shard`

## Гипотеза

Стадия 1 плана v9 («compile-time геометрия → данные артефакта») упирается в то, сколько мест
незаметно зависят от `SHARDS = 64`. `E-0031` нашёл стену в `Manifest::check()`, `E-0030` —
расхождение двух карт шардов в живом пути `find()`. Здесь третий слой: что происходит с самим
**номером шарда**, когда он приходит извне как `u16`.

По коду (проверено чтением, но не измерением):

- `vecdht-crypto/src/quant.rs:163-166` — `clusters_of_shard(shard: u16)` строит список кластеров как
  `(base..base + CLUSTERS_PER_SHARD).map(|c| c % NLIST)`, где `base = shard * CLUSTERS_PER_SHARD`;
  арифметика `u16`, проверки входа нет, `% NLIST` — то есть номер вне диапазона не отбрасывается, а
  отображается в законный;
- `vecdht-crypto/src/quant.rs:174` — `is_valid_shard(shard) = shard < SHARDS` существует, и, по
  видимому, никем, кроме собственных модульных тестов, не вызывается;
- `vecdht-wire/src/messages.rs` — поле `pub shard: u16` у 13 сообщений; диапазонную проверку при
  декоде (`if shard >= SHARDS` → `BadEnum`) имеют только `LeaseGrant`, `SnapshotOffer`, `ReplicateAck`;
- `vecdht-cli/src/index_cmd.rs:88` — операторский путь проверяет `--shard` сам, до `clusters_of_shard`;
- `vecdht-node/src/node.rs` — приёмка чужих сообщений проверяет равенство своему номеру
  (`incoming.shard != self.shard`, `req.shard != self.shard`, `resp.shard`, `offer.shard`, `ack.shard`,
  `notice.shard`), то есть чужой номер отсекается, но не как «вне диапазона», а как «не мой».

Утверждение (проверяемое ядро), четыре части:

1. `clusters_of_shard` вызывается из нетестового кода только по уже валидированному номеру
   (операторский CLI `index_cmd.rs:88`, либо номер из `group_by_shard`, который по построению < 64),
   и нигде на пути между декодом сообщения и ней нет ни `is_valid_shard`, ни `debug_assert`;
2. `is_valid_shard` вне `vecdht-crypto` не вызывается ни разу (0 сайтов в нетестовом коде других
   crates) — функция-guard есть, но не используется;
3. маска `% NLIST` материальна: `clusters_of_shard(64)` побайтово равен `clusters_of_shard(0)`, а
   `clusters_of_shard(SHARDS + k)` — `clusters_of_shard(k)` для нескольких `k`; то есть чужой номер
   открывает чужой список кластеров, а не пустоту;
4. арифметика `u16` в этом же месте — граница паники: при `shard = 4094` (и ниже) `base + 16`
   умещается в `u16`, при `shard = 4095` — `base = 65_520`, `base + 16 = 65_536` не умещается, и в
   debug-сборке это panic'ом переполнения; измеряется через `catch_unwind`, чтобы видеть и знак, и
   границу.

## Фальсификатор

Достаточно одного:

- **(а)** найдётся вызов `clusters_of_shard` в протокольном пути, куда номер приходит из декодированного
  сообщения без проверки (тогда маскированный список достижим из сети, и это не остаток, а брешь);
- **(б)** `is_valid_shard` вызывается из другого crate (тогда guard работает и пункт (2) ложен);
- **(в)** `clusters_of_shard(64) != clusters_of_shard(0)` — маски нет, функция ведёт себя как
  «пустой/ошибочный ответ», и утверждение (3) ложен;
- **(г)** при `shard = 4095` паники в debug нет (промоция в `usize`, другой порядок операций) —
  тогда пункт (4) ложен и граница риска иная.

## Оракул

`crates/vecdht-crypto/tests/shard_number_admission.rs` (новое; `crypto` зависит от `wire`, так что
сообщения видны отсюда; корпус, `candle` и сеть не поднимаются):

1. для набора номеров `{0, 1, 63, 64, 80, 128, 1024, 4094, 4095, 65535}` — сравнение
   `clusters_of_shard(s)` с `clusters_of_shard(s % 64)` (там, где арифметика законна) и с
   `clusters_of_shard(0)`; всё, что обязано паниковать, снимается через `catch_unwind` с
   `AssertUnwindSafe`, чтобы прогон не обрывался на границе;
2. инвентарь вызовов (`lab/e0034-run.sh`, grep по нетестовому коду): сайты `clusters_of_shard`, сайты
   `is_valid_shard`, число struct'ов с `pub shard: u16` в `messages.rs` и число диапазонных проверок
   при декоде;
3. справочно (порогом не является): где в `node.rs` приёмка сверяет `shard` со своим.

## Порог (фиксируется до прогона)

(1) сайтов `clusters_of_shard` в нетестовом коде ровно 3 (все в `cli/index_cmd.rs`) и у каждого номер
прошёл проверку (`dir_and_shard`, `:88`) или взят из `group_by_shard`; (2) сайтов `is_valid_shard` в
нетестовом коде вне `vecdht-crypto` — 0; (3) оба заявленных равенства выполнены (`clusters_of_shard(64)` равно
`clusters_of_shard(0)`, `clusters_of_shard(80)` равно `clusters_of_shard(16)`), и — сильнее этого —
каждый снятый внедиапазонный номер, не вызвавший паники, побайтово равен списку шарда
`shard % SHARDS`; (4) `catch_unwind` фиксирует панику при `shard =
4095` и отсутствие паники при `shard = 4094`. Провал (1)/(2) = фальсификаторы (а)/(б). Провал (3) =
(в), провал (4) = (г). Если порог (3) выполнен, а (1) тоже, вывод фиксируется как «остаток класса
(H), не эксплуатируется сегодня, но молча переживёт подъём `SHARDS`», и ничего более сильного из этого
прогона не выводится.

## Входы и окружение

Дерево после `0f29519`, debug (для паники переполнения это существенно: в release арифметика `u16`
кольцевая, и вместо паники был бы тихий wrap), `-j 2`, `RAYON_NUM_THREADS=2` (идёт тяжёлая рука
`E-0027`). Измеряется поведение функции-карты и распределение проверок, а не reachability из сети:
для второго нужен вызов протокольного пути, его здесь нет.

(Формулировка порога (3) была уточнена в большую сторону — добавлено требование равенства по всем
снятым внедиапазонным номерам, а не по двум — уже после того, как оракул был написан, но до первого
запуска: замеров на момент правки не существовало.)

## Вердикт (после E-0034) — `supported`

Снято на дереве `68cb4e5`, один прогон, `EXIT=0` (`lab/logs/e0034-all.log`):

- **(3)** из десяти probe-номеров пять внедиапазонных не запаниковали, и все пятеро побайтово равны
  списку шарда `shard % SHARDS`: 64→0, 80→16, 128→0, 1024→0, 4094→62. Маска `% NLIST` материальна:
  чужой номер открывает чужой законный список, а не пустоту и не ошибку;
- **(4)** паника переполнения `u16` зафиксирована при 4095 и 65535, при 4094 список ещё строится —
  граница ровно там, где `shard · 16 + 16` перестаёт умещаться;
- **(2)** `is_valid_shard` в нетестовом коде вне `vecdht-crypto` — 0 сайтов: guard есть и не
  используется;
- **(1)** вызовов `clusters_of_shard` из собранного кода ровно 3, все `cli/src/index_cmd.rs`
  (`:286`, `:307`, `:498`), номер во всех трёх пришёл из `dir_and_shard` с проверкой
  `shard >= SHARDS` (`:88`). Оговорка: grep-инвентарь по предрегистрированному счётному правилу
  выдал 4 строки — четвёртая это `quant.rs:407`, вызов внутри `#[cfg(test)] mod tests` в `src`,
  который фильтр по `/tests/` отличить не мог. Порог по существу выполнен, счётное правило после
  этого прогона нужно уточнять (это дефект формулировки, не кода).

Справочная часть, порогом не бывшая: 13 сообщений с `pub shard: u16`, диапазонных проверок при
декоде — 3 (`LeaseGrant`, `SnapshotOffer`, `ReplicateAck`); в `node.rs` — 8 сайтов сверки
`!= self.shard`. То есть границу «номер свой» держат два других слоя, а не функция карты, и держат
её как «не мой номер», а не как «номер вне диапазона».

Чего вердикт не утверждает: reachability из сети не проверялась (фальсификатор (а) остался
невычисленным, он требует пути от декода непроверенного сообщения до `clusters_of_shard`), поэтому
«сегодня не эксплуатируется» — наблюдение по инвентарю вызовов, а не доказательство. Правка
`clusters_of_shard` на явную ошибку при `!is_valid_shard(shard)` — изменение протокольного кода, оно
вне полномочий измерительного цикла и требует решения владельца.
