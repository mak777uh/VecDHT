# H-0061 — байтовая неканоничность кадра приёмки: хвост после подписи не даёт второго расхода, а `WrongKind`/`Malformed` отсекают дефекты заголовка до криптографии (§5.1, §5.2, §12.3)

## Наблюдение

Грех предшественников измерим: grep по `crates/` даёт НОЛЬ упоминаний
`AcceptError::WrongKind` и НОЛЬ `AcceptError::Malformed`, тогда как остальные ветки
`Spend::consume` мерились (`AlreadySpent` — 15 вызовов в тестах, `Expired` — 8,
`WrongTarget` — 3, `TtlOutOfPolicy` — 2, `Unsigned`/`BadSignature` — по 1; `E-0047`,
`E-0058`, `E-0059`, `E-0060`). Две первые проверки `consume` — `decode_frame` и сверка
`kind` — не измерялись никогда.

Спека формулирует три обещания, из которых следует содержание порогов: §5.1 —
«`[u8 sig_len][sig]` // только Ed25519: sig_len обязан быть 64, другие значения — ошибка
декода» и «бит 0: поле подписи присутствует; биты 1..15: зарезервированы, MUST быть 0»;
§5.2 — «`sig_input = blake3(DOMAIN ‖ kind ‖ version ‖ flags ‖ body_bytes)` — тело
декодировано-и-пересобрано canonically перед подписанием; подпись всегда по
canonical-байтам, а не по пришедшим». Из §5.2 прямо НЕ следует отказа байтов после
подписи: `sig_input` их не содержит, а `decode_frame` (`frame.rs:226-251`) берёт
`body` по `body_len` и подпись по `sig_len`, хвост игнорирует. Значит кадр с хвостом —
это ДРУГИЕ байты при ТОМ ЖЕ теле, а `Key` расхода (`{seeker, target, shard, slot,
issued_bucket}`) собран из тела. Предсказание: одноразовость переживает побайтовую
мутацию — и в ту, и в другую сторону.

## Гипотеза (операационализируемое ядро)

Живой приём A бакета 0 (ttl=300) от одиночного primary; цель — `Spend::new(300)`,
`consume(frame, n.me(), acc.target, now = 5)`. Часы в прогоне НЕ двигаются (урок
`E-0060`: `prune(now)` внутри `consume` вычищает память расхода при большом `now`, и
поздние проверки `spent` становятся ложными). Пороги (раскладка: тело 76 = 32+32+2+4+4+2
по `encode_body`, кадр 8+76+1+64 = 149):

| Шаг | Утверждение (порог) |
|---|---|
| (0) | `decode_frame(f0).header.body_len == 76`, `flags == 0x0001`, `f0.len() == 149`, байт `sig_len == 64`, последний байт тела `== 0x01` (старший байт ttl=300 LE) |
| (1) | consume f0@5 → `Ok`; spent == 1; grant = (seeker=A, shard=7, slot, issued_bucket=0) |
| (2) | f0 + 8 мусорных байт хвоста: разбирается, тело и подпись не сдвинуты, `RendezvousAccept::decode` == карта из (1); consume → `AlreadySpent`, spent == 1 |
| (3) | обратный порядок на чистой цели: padded → `Ok` и grant ПОЛЕВО РАВЕН grant из (1); затем чистый f0 → `AlreadySpent`; spent == 1 |
| (4) | инверсия последнего байта подписи → `BadSignature` |
| (5) | инверсия первого байта `target` в теле → `BadSignature`, НЕ `WrongTarget` |
| (6) | кадр усечён на 1 байт → `Malformed` |
| (7) | `sig_len := 63` → `Malformed` (§5.1: обязан быть 64) |
| (8) | `sig_len := 65` → `Malformed` |
| (9) | `flags := 0x0003` (зарезервированный бит) → `Malformed`, хотя flags входят в `sig_input` |
| (10) | `version := 7` → `Malformed` |
| (11) | `kind := 0xFE` (нет в таблице §5.3) → `Malformed`, а НЕ `WrongKind` |
| (12) | `kind := Publish` при честном теле и честной подписи → `WrongKind`; тот же kind без подписи → `WrongKind` (заголовок `kind` ДО проверки подписи) |
| (13) | `body_len` занижен на 1 → `Malformed` (длина подписи читается из последнего байта тела = `0x01`) |
| (14) | `spent == 1` в обеих целях после всех веток: ни один отказ не оставил записи |

Различающее ядро — (2)/(3): если бы ключ расхода собирался из байтов кадра (или подпись
проверялась бы по пришедшим байтам целиком), предъявление «того же приёма с хвостом»
прошло бы как новое и цель получила бы второй `Grant` на один lease. Различающее по
порядку — (11) против (12): «kind вне таблицы» умирает на декодере заголовка
(`Malformed`), «табличный, но не тот kind» — на сверке вида (`WrongKind`); перестановка
этих двух проверок меняет код отказа. Различающее по приоритету криптографии — (5)
против (4) и (9)/(10): `BadSignature` обязан быть позже разбора заголовка, а адресат —
позже подписи (`E-0060` мерил порядок телесных проверок, здесь — порядок заголовочных).

## Фальсификаторы

(а) (2) вернул `Ok` — ключ расхода собран из байтов кадра, мутация обходит
одноразовость;
(б) (3) чистый кадр после padded вернул `Ok`, либо grant из padded отличается полями —
то же самое в другую сторону: другой lease из того же приёма;
(в) любой отказ (4)…(13) изменил `spent` — побочный эффект до проверок;
(г) (4) или (5) вернули `Ok` — подпись не покрывает байты тела/подписи;
(д) (5) дал `WrongTarget` — адресат проверён до подписи, порядок §12.3 нарушен;
(е) (7)/(8) дали `Ok` или `BadSignature` — гейт длины подписи (§5.1) отсутствует;
(ё) (9)/(10) дали `BadSignature` — заголовочные гейты идут после криптографии;
(ж) (11) дал `WrongKind`, либо (12) дал `Malformed` — судьбы «kind вне таблицы» и «не тот
kind» перепутаны;
(з) (0) не сошлось — раскладка кадра не та, и вся арифметика мутаций держится на неверных
смещениях;
(и) grant (1)/(3) не связан с A (seeker/slot/issued_bucket съехали);
(й) padded распался не в то же `RendezvousAccept`, либо тело/подпись сдвинулись;
(к) `spent > 1` в (14) — память расхода разрослась за прогон.

## Скоуп и границы замера

Меряется приёмный конец (`Spend::consume`) на кадрах, собранных из ЖИВОГО приёма
мутацией байтов; подпись не подделывается — подделки с честной пере-подписью тела
измерены `E-0060`, стойкость подписи к чужому ключу — `adversarial.rs`. Лимит 512 байт на
поле `present` (`ADR-0013`) здесь НЕ меряется: он измерен `present_serving_gate.rs`
(порог (6)) и `E-0051`; хвост в 8 байт заведомо внутри лимита, и «сколько именно можно
надуть» — территория разбора запроса, а не расхода. TLV-хвост внутри ТЕЛА (§5.1 правило
4: неизвестный тег игнорируется) — другой объект: он входит в `sig_input`, и его мутация
даёт `BadSignature`; здесь меряется хвост ПОСЛЕ подписи, который в подпись не входит.
Отказ `serve_request` маскирует `AcceptError` как `NotSignedByShardHolder` (кандидат на
ADR из `E-0054`) — маскировка не меряется, чтобы не смешивать два неизмеренных факта.
