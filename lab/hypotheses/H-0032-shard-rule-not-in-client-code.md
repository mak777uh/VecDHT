# H-0032 — правило выбора шардов §7.5.1 («минимум `l2_sq` по 16 строкам шарда», fan-out ровно
# `nprobe`) живёт только в стенде гейта; собранный клиентский код выбирает **кластеры**
# (`Centroids::top`), и по таблице §7.5 это ровно та строка «пересечение кластеров», которая
# гейт (ii) не проходит: значит PASS-числа `E-0012` (0,9645 / 0,9790) относятся к политике,
# которой в протокольном коде нет, а политика, которая в коде есть, на протокольной карте не
# измерена никогда

## Гипотеза

Спека §7.4.1 («Карта шардов — это порядок строк, а не формат»: строка `i` — кластер `i`,
шард `i / 16`) и §7.5 («Правило выбора шардов — общее для обеих политик … Fan-out равен числу
выбранных шардов: при `nprobe = 16` это 16 владельцев») предписывают клиенту выбирать **шарды**
правилом §7.5.1 — минимум `l2_sq` по 16 опубликованным строкам шарда. В `vecdht-embed/src/shardmap.rs:79`
это сформулировано буквально: «клиентская политика §7.5.1 считает минимум по 16 строкам шарда».

Собранный код делает другое, и везде одно и то же:

- `vecdht-artifact/src/centroids.rs:93` — `Centroids::top(vec_q, nprobe)` возвращает **топ-`nprobe`
  кластеров** (сортировка `(d2 ASC, cluster ASC)`), никакой агрегации по шардам;
- `vecdht-embed/src/model.rs:275` — `encode_query` (отсуда пайплайна §6.2, та же, что у SDK) строит
  `clusters = centroids.top(...)` и `per_shard = quant::group_by_shard(&clusters)`, то есть шарды
  **производные от выбранных кластеров**, а не выбираемые самостоятельно;
- `vecdht-cli/src/index_cmd.rs:489` — собранный вызывающий путь клиента: `let top = a.centroids.top(q, nprobe)`;
- владелец на другой стороне сканирует ровно присланное: `vecdht-node/src/node.rs:986`
  `self.store.search(&q.query_vector, &q.clusters, top_k)`, а `IvfIndex::search`
  (`vecdht-index/src/ivf.rs:465-477`) перебирает переданные `clusters` и не знает про «все 16
  кластеров шарда».

Это ровно строка таблицы §7.5 «пересечение кластеров» (цена 1,6 % кластеров корпуса, гейт (ii)
**не проходит**: 0,8303 на 50 000 и 0,8892 на 807 596 — `E-0004`/`E-0006`). Проходные числа гейта относятся к строке «полный скан шарда» (`E-0012`: 0,9645 / 0,9790 при fan-out ровно 16,0/16), а
её — по этому коду выразить нельзя: клиент шлёт список кластеров длины `nprobe`, а не `nprobe × 16`.

Утверждение (проверяемое ядро), четыре части:

1. реализации правила §7.5.1 (минимум по 16 строкам шарда) **вне** `vecdht-embed` нет — 0 сайтов в
   нетестовом коде `artifact`/`net`/`node`/`index`/`cli`; в `embed` она существует как комментарий и
   как локальная логика стенда (`p0_real_corpus.rs:1603`, `:2141`), то есть гейт считает своей
   копией правила, несмотря на принцип `ADR-0004` («стенд не имеет собственной копии решателя»);
2. все собранные клиентские вызовы выбора идут через `Centroids::top` (ожидается ровно 2 нетестовых
   сайта: `embed/model.rs:275` и `cli/index_cmd.rs:489`), и ни один не передаёт владельцу 16
   кластеров одного шарда;
3. на эталонном артефакте для `nprobe ∈ {4, 16, 32}` средний fan-out кластерного правила **строго
   меньше** `nprobe` (столкновения нескольких ближайших кластеров в одном шарде), а шардового
   правила — ровно `nprobe` по построению;
4. множества выбранных шардов у двух правил не совпадают хотя бы на половине запросов (иначе
   различие было бы несущественным).

## Фальсификатор

Достаточно одного:

- **(а)** вне `vecdht-embed` найдётся реализация «минимум по 16 строкам шарда», используемая
  протокольным путём (тогда код реализует §7.5.1, и гипотеза опровергнута);
- **(б)** найдётся собранный вызывающий код, который шлёт владельцу все 16 кластеров шарда (тогда
  «полный скан» выражим и реализован, и утверждение о невыразимости pass-политики ложно);
- **(в)** на эталонном артефакте кластерное правило даёт fan-out `== nprobe` для всех трёх значений
  (тогда различие двух правил — только в составе кластеров внутри шарда, а не в fan-out, и §7.5
  «fan-out ровно 16» выполняется кодом случайно);
- **(г)** правило §7.5.1 в `embed` вызывается из собранного SDK-пути, а не из стенда (тогда
  расхождение — вопрос упаковки кода, а не семантики).

## Оракул

`crates/vecdht-artifact/tests/fanout_rule.rs` (новое; корпуса, `candle` и сети нет — только
опубликованные строки эталонного артефакта):

1. для 256 детерминированных запросов (LCG по `i8`) посчитать кластерное правило
   (`Artifact::centroids.top`) и шардовое правило (минимум `l2_sq` по 16 строкам каждого из 64
   шардов, топ-`nprobe` шардов), и для `nprobe ∈ {4,16,32}` напечатать средний/медианный/минимальный
   fan-out обоих правил, долю запросов с `fan_out == nprobe` и среднее совпадение множеств шардов
   (Jaccard);
2. проверка выразимости: зафиксировать, что `IvfIndex::search` принимает список кластеров (никакого
   «16 кластеров шарда» в протокольном типе нет) — измеряется как длина запроса, который составил бы
   полный скан: `nprobe · CLUSTERS_PER_SHARD` против фактического `nprobe`;
3. вызовы `Centroids::top` вне `vecdht-embed` — grep в `lab/e0032-run.sh` (нетестовый код), и grep
   сайтов `§7.5.1` / «минимум … по 16 строкам» по всем crates.

## Порог (фиксируется до прогона)

(1) 0 реализаций правила §7.5.1 вне `vecdht-embed` (grep по нетестовому коду); (2) ровно 2
нетестовых сайта `centroids.top(` (`embed/model.rs`, `cli/index_cmd.rs`) и 0 мест, где клиент шлёт
`nprobe · 16` кластеров; (3) средний fan-out кластерного правила строго `< nprobe` для 4, 16 и 32,
у шардового правила `== nprobe`; (4) Jaccard двух множеств шардов `< 1,0` хотя бы на 50 % запросов.
Провал (1)/(2)/(г) — гипотеза опровергнута; провал (3) — фальсификатор (в); провал (4) — различие
есть, но оно несущественно по составу (записывается как есть).

## Входы и окружение

Дерево после `f10af3e`, debug, `-j 2`, `RAYON_NUM_THREADS=2` (идёт тяжёлая рука `E-0027` из
другого дерева). Числа пункта (3) относятся к **структуре** выбора на синтетических центроидах
эталонного артефакта (`reference_artifact()`), а не к recall на реальном корпусе: recall по этой
гипотезе не измеряется и остаётся незакрытым (гейт (ii) требует корпуса и другой политики).
