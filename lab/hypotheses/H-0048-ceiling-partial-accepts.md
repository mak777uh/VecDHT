# H-0048 — потолок таблицы при ≥2 совпадений: `MatchResult` полон, отказа нет, а
# недостающие приёмы — детерминированный хвост отсортированного списка (выпуск идёт
# порядком контракта сортировки, `node.rs` handle_find: цикл по `res.matches` с `continue`)

## Гипотеза

`E-0044` закрыл потолок на одной записи: «ноль приёмов, MatchResult цел». Спека §12.3
формулирует деградацию во множественном числе — «Find по-прежнему возвращает MatchResult,
просто **без части приёмов**» — но нигде (ни в спеке, ни в тестах) не зафиксировано,
**какой именно части**. Код отвечает неявно: приёмы выпускаются циклом по `res.matches`
в порядке контракта сортировки `(d2, slot)`, а отказ — `continue`. Проверяемое ядро:

- при 3 живых записях в кластере и таблице, где свободно ровно 2 слота, `Find` обязан
  вернуть `MatchResult` с `matches.len()==3` (контракт сортировки подписан до цикла
  приёмов — отказ не распространяется на находки);
- ровно 2 приёма, и их `(target, slot)` — **первая пара списка matches** (не произвольная:
  отказ бьёт по хвосту сортировки детерминированно);
- `refused_full` вырастет ровно на 1 (третий match), `live` останется `MAX_ACCEPTS`;
- повтор `Find` тем же seeker'ом в том же бакете: таблица полна ⇒ приёмы 0 оба раза не
  бывают «тем же» — это новый отказ, `refused_full` +1 (идемпотентность `E-0044` работала
  через `seen` ДО потолка; здесь строки в таблице нет, и «тот же приём» выдать нечем).

## Фальсификатор

- **(а)** `matches.len() < 3` — отказ в приёме просочился в находки (спека обещает обратное);
- **(б)** приёмы есть, но не первые два matches — «какая часть теряется» не порядок сортировки
  (тогда хвост списка теряет приоритет видимость для seeker'а, и это свойство надо вписывать
  в спеку с точным определением);
- **(в)** `refused_full` вырос не на 1 за прогон (недосчёт/пересчёт отказов — метрика §12.3
  врёт о давлении);
- **(г)** `live` превысил `MAX_ACCEPTS` (мягкий потолок — повтор (в) из `E-0044` на новом месте);
- **(д)** `ProtocolError` адресованный seeker'у в ответе (graceful degradation нарушена не
  на пустой, а на частичной выдаче).

## Оракул

`crates/vecdht-node/tests/ceiling_partial_accepts.rs` (новый; harness `tests/rendezvous.rs`):

1. publish ×3 (seed 77/78/79, векторы 1/2/3, кластер 112, `clock(0)`);
2. дозаполнение `issue()` до `live == MAX_ACCEPTS − 2`;
3. `Find` seeker A (seed 88, top_k=8) при `clock(0)` → разбор: 3 matches, 2 приёма,
   пары `(target,slot)` приёмов == первым двум `matches`; `refused_full` +1;
4. повтор того же `Find` при `clock(0)` → 3 matches, 0 приёмов, `refused_full` ещё +1,
   `live == MAX_ACCEPTS`.

## Порог (фиксируется до прогона)

(1) шаг 3: `matches.len()==3`, приёмов 2, их `(target,slot)` == `matches[0..2]`;
(2) шаг 3: `refused_full` +1 ровно; (3) шаг 4: приёмы 0, `refused_full` +1, `live==100 000`;
(4) ни в одном ответе нет `ProtocolError`, адресованного A. Провал (1)= (а)/(б), (2)/(3)= (в),
(3)-последнее= (г), (4)= (д).
