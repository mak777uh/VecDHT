# H-0057 — потолок из строк одного бакета снимается по бакету за шаг: после ухода бакета 0 выдача возвращается НОВЫМИ строками, а побайтовая идемпотентность живёт только внутри текущего бакета

## Наблюдение

`E-0056` забил всю таблицу строками бакета 0 и на `now = 20` увидел: выдача вернулась,
`live = 3`, повтор побайтовый. Но там голова префикса состояла из ЧУЖИХ строк-заполнителей
(`issue(junk, …)`), а seeker получал новые приёмы бакета 20. Что происходит, когда бакет 0
занят НАСТОЯЩИМИ приёмами того же seeker'а, не мерилось. Из кода (`rendezvous.rs`):
`Key` включает `issued_bucket`, `issue()` вызывает `prune` ДО проверки `seen`, а `prune`
чистит и `seen`. Значит после ухода строки `(A, t, shard, slot, 0)` её повтор в `seen` нет —
тот же `Find` на `now = 20` обязан выдать НОВЫЕ строки бакета 20, байтово отличные от
довоенных (в отличие от `E-0046`, где рестарт узла НЕ трогал ключ и кадр совпал побайтово).

## Гипотеза (операационализируемое ядро)

Таблица: 3 строки seeker'а A бакета 0 + 99 997 чужих строк того же бакета (потолок ровно);
`ttl_buckets = buckets(300) = 19`. Поведение живого `Find`-пути:

| Шаг | Утверждение (порог) |
|---|---|
| (1) `Find` A при `now = 19` | 3 приёма побайтово = довоенные (бакет 0 ещё жив: `0 < 19−19` ложно), `live == MAX_ACCEPTS`, `refused_full == 0` (идемпотентный повтор не отказывает) |
| (2) `Find` A при `now = 20` | 3 приёма НОВЫМИ строками бакета 20: `issued_bucket == 20`, байты ≠ довоенные, `live == 3`, отказов нет |
| (3) `Find` A при `now = 21` | повтор побайтовый строкам бакета 20 (cutoff 2, бакет 20 жив), `live == 3` |
| (4) `Find` B (второй seeker) при `now = 21` | 3 приёма новыми строками бакета 21 (дыра, возвращённая prune, кормит любого), `live == 6`, отказов нет |

Различающий порог (2): если байты совпадут с довоенными — `prune` не чистит `seen` (или
ключ не включает бакет), и тогда вывод `E-0046` о «побайтовом кадре после потери таблицы»
окажется общим свойством, а не следствием рестарта. Порог (4) проверяет, что возврат дыры
не привязан к автору истёкших строк.

## Фальсификаторы

(а) выдача при пустой таблице отказывает / `live != 3` после выдачи A / дыра осталась после
достройки — таблица собрана нечестно.
(б) на `now = 19` повтор не побайтовый или строки бакета 0 выброшены — граница `checked_sub`
неверна.
(в) на `now = 20` дыра не вернулась, байты совпали с довоенными, или `live != 3` — prune
или ключ устроены не так, как читается код.
(г) на `now = 21` повтор бакета 20 не побайтовый или строки выброшены раньше cutoff 2.
(д) B на шаге (4) получает 0 приёмов или отказ при свободных ~99 997 слотах — возврат дыры
не сработал для чужого seeker'а; `MatchResult` потерялся.
(е) `buckets(300) != 19` или `Params.rendezvous_ttl != 300` — чужая арифметика бакетов.
(ж) пустая выдача на любом шаге обернулась кадром `Kind::Error`.

## Скоуп и границы замера

Одиночный primary (`SEEDS=[1,2,3]`, `SHARD=7`, `POW=8`), 3 записи бакета 0 от
`OWNER_SEEDS=[77,78,79]`; seeker A `identity(88)` получает голову живым `Find`-путём,
достройка — ручным `issue(junk, identity(90), …)` бакета 0, seeker B `identity(89)`.
Меряется взаимодействие выдачи с `prune` на шагах 19/20/21; расход приёмов через `Spend`
не меряется (территория `E-0044`…`E-0047`, `E-0051`).
