# H-0035 — весь вход `clusters_of_shard` раскладывается ровно на два исхода: 0…4094 дают молчаливо
# законный список шарда `s mod 64`, 4095…65535 паникуют; третьих исходов и новых выходов у `u16` нет

## Гипотеза

`E-0034` подтвердил маску `% NLIST` на пяти точках и панику на двух, и в «Границах» оставил прямую
оговорку: «утверждение следует из арифметики, но полным перебором 64…4094 не проверялось». Это
единственный способ сделать вывод по `E-0034` доказательным, а не правдоподобным, и он дёшев: вход
функции — `u16`, 65 536 значений, тело функции — `base..base + 16` c `% NLIST`, без обращения к
данным или сети.

Арифметика, подлежащая проверке перебором (`CLUSTERS_PER_SHARD = 16`, `NLIST = 1024`,
`SHARDS = 64`):

- паника переполнения `u16` наступает, когда `base + 16 > 65 535` при `base = s · 16`, то есть при
  `s ≥ 4095` (для `s = 4095` `base` ещё умещается — `65 520`, а `base + 16` уже нет; для `s ≥ 4096`
  не умещается уже `base`);
- для `s ≤ 4094` каждый элемент списка равен `(s · 16 + j) mod 1024`, а `1024 = 64 · 16`, поэтому
  `(s · 16) mod 1024 = 16 · (s mod 64)` и весь список побайтово равен списку шарда `s mod 64`;
- отсюда множество всех выходов функции на `0 ≤ s ≤ 4094` — ровно 64 законных списка, ничего иного
  она произвести не может.

Утверждение (проверяемое ядро): перебор по всем `u16` не оставляет ни одного номера, который вёл бы
себя иначе, — то есть класс исходов ровно два, граница ровно на 4095, а число различных выходов
ровно `SHARDS`.

## Фальсификатор

Достаточно одного:

- **(а)** найдётся `s ≤ 4094`, который паникует, или список которого не равен списку `s mod 64`
  (граница или маска устроены иначе, чем выведено);
- **(б)** найдётся `s ≥ 4095`, который возвращает список вместо паники (тогда верхняя часть входа —
  не авария, а ещё один тихий исход, и вывод `E-0034` о «границе риска» неполон);
- **(в)** различных выходов на `0 ≤ s ≤ 4094` получится не 64 (тогда маска порождает список, которого
  среди законных нет — например усечённый или не из 16 кластеров).

## Оракул

`crates/vecdht-crypto/tests/shard_number_exhaustive.rs` (новое; сети, корпуса, `candle` нет):

1. цикл `s = 0…4094`: вызов через `catch_unwind` с заглушённым хуком, сравнение с
   `clusters_of_shard(s % SHARDS)`, проверка длины 16, накопление множества различных выходов;
2. цикл `s = 4095…65535`: ожидание паники, First-panic позиция, список тех, кто паниковать не стал;
3. печатаются счётчики и время перебора (это единственный замер, который может встать в разумное время:
   около 61 тысячи unwind'ов).

## Порог (фиксируется до прогона)

(1) среди `0…4094` неожиданной паники 0, несоответствий маске 0, все списки длины 16;
(2) среди `4095…65535` значений без паники 0, первая паника — ровно на 4095, последний живой номер —
ровно 4094; (3) различных выходов на всём нижнем множестве ровно 64. Провал (1) = (а), провал (2) =
(б), провал (3) = (в). Ограничение по профилю заранее признано: перебор снимает поведение debug-сборки,
в release арифметика `u16` кольцевая, и там верхнее множество было бы не паникой, а ещё одним
замаскированным списком; отдельного замера release в этом цикле нет (он потребовал бы пересборки и
отнял бы время у идущей руки `E-0027`), поэтому утверждение про release остаётся арифметическим.

## Входы и окружение

Дерево после `914967d`, debug, `-j 2`, `RAYON_NUM_THREADS=2`. Время прогона ожидается секундным; если
окажется минутным, это фиксируется в записи как стоимость метода, а не как повод сократить перебор.

## Вердикт (после E-0035) — `supported`

Снято на дереве `a4fb1d3`, debug, `-j 2`; прогон и повтор после lint-правки в
`lab/logs/e0035-all.log`, пороги не менялись (`lab/experiments/E-0035-shard-number-exhaustive.md`):

- **(а) не сработал:** среди 4095 входов `0…4094` неожиданных паник 0 и несоответствий маске
  `s % SHARDS` 0, все списки длины 16 — то есть ниже границы функция ведёт себя ровно так, как
  выведено арифметикой, без исключений;
- **(б) не сработал:** среди 61 441 входа `4095…65535` значений, вернувших список, — 0; первая
  паника зафиксирована ровно на 4095, последний живой номер ровно на 4094;
- **(в) не сработал:** различных выходов на нижнем множестве ровно 64 = `SHARDS`, усечённых или
  «незаконных» списков перебор не нашёл.

Класс исходов `u16` ровно два, и это теперь перечисленный факт, а не вывод из десяти точек
`E-0034`. Стоимость метода подтвердила опасение пре-регистрации как ложное: 65 536 `catch_unwind`
за 0.3 с, сокращать перебор не пришлось.

Чего вердикт не утверждает: поведение `release`-профиля (там переполнение `u16` кольцевое, и верхнее
множество обязано стать не аварией, а ещё одним замаскированным списком — арифметическое
рассуждение, замер вынесен в `H-0036`/`E-0036`) и достижимость `clusters_of_shard` из сети (кадр с
чужим номером шарда этим прогоном не отправлялся; `E-0034` оставил этот вопрос фальсификатором (а)
открытым).
